# 任务提取规则详解

本文档详细说明如何从会议内容中智能提取待办任务，包括提取标准、识别模式、质量控制机制等。通过遵循这些规则，可以确保提取的任务信息准确、完整、可执行。

## 任务提取概述

任务提取是会议纪要生成中最关键也是最复杂的环节。一个优秀的任务提取系统需要准确识别发言中的任务意图、明确责任归属、设定合理的时间节点、定义可衡量的完成标准。本规则库基于大量真实会议数据训练，涵盖了职场中最常见的任务表达模式。

任务提取的核心挑战在于自然语言的复杂性和多样性。同样是分配任务，人们可能用不同的方式表达：有人直接说“我来负责”，有人用委婉的语气“要不我试着做一下”，还有人用第三人称“让小李去处理”。一个好的提取系统必须能够理解这些多样化的表达，并将其转化为结构化的任务信息。

## 任务要素定义

### 必需要素

每个提取的任务必须包含以下三个必需要素，缺一不可。

任务描述是任务的核心内容，必须清晰、具体、可执行。好的任务描述应该使用动词开头，明确说明要做什么。例如“完成竞品分析报告”比“关于竞品的事情”要好得多。任务描述中应该包含足够的背景信息，让责任人能够理解任务的全貌，但又不宜过于冗长。

责任人是指执行该任务的具体个人。责任人必须是发言中明确提到的人，不能是模糊的团队或部门。如果发言中说“让市场部去处理”，应该尽可能细化到具体的个人，比如“小李负责”或“市场部张经理负责”。如果确实无法确定具体个人，可以标注为“待指定”，但需要在报告中提示需要补充。

截止时间是任务必须完成的时间节点。没有截止时间的任务往往会被无限期拖延。好的截止时间应该是具体的日期，而不是模糊的“尽快”或“下周”。如果发言中提到“尽快”，应该根据任务复杂度推测一个合理的截止时间，并在报告中标注为“推断”。

### 可选要素

除必需要素外，以下要素可以增强任务的完整性和可追踪性。

协作人是指需要配合责任人完成任务的其他人。有些任务需要多人协作才能完成，此时需要明确列出所有参与人员及其角色。协作人的识别通常通过发言中的并列表达来确定，比如“小李和小王一起负责”或“小李负责，张经理配合”。

完成标准定义任务完成的衡量条件。没有明确标准的任务往往会导致执行方和验收方对“完成”的理解不一致。好的完成标准应该是可量化的，比如“报告不少于20页，包含以下章节：”。如果发言中没有明确标准，可以根据任务性质推测合理的验收条件。

优先级表示任务紧急程度和重要程度。高优先级任务通常与会议核心决策或紧迫问题相关。优先级的判断需要综合考虑发言中的语气、上下文和任务本身的性质。

关联决策将任务与会议中的具体决策关联起来。这有助于追溯任务的来源，理解任务产生的背景。关联决策通常通过发言中的“因为”或“所以”等因果关联词来识别。

## 识别模式库

### 直接分配模式

直接分配是最清晰的任务分配方式，识别准确率最高。

当发言人使用明确的指向性语言时，通常意味着直接的任务分配。例如“小李负责”、“张三来做”、“交给王经理”、“这个由我来做”等表达都属于直接分配。这些表达的特点是主语明确、动词通常是“负责”、“做”、“处理”等动作词。

```markdown
示例1：
发言："小李负责整理这次会议的纪要，下周三之前发给大家。"
提取结果：
- 任务描述：整理会议纪要并发送给团队成员
- 责任人：小李
- 截止时间：下周三

示例2：
发言："这个方案由我来跟进，大家有意见随时提。"
提取结果：
- 任务描述：跟进方案
- 责任人：发言人（假设为[姓名]）
- 截止时间：待确定（发言中未提及）
```

### 承诺执行模式

当发言人表示自己将执行某项任务时，属于承诺执行模式。

承诺执行通常出现在发言人主动承担任务的情况下。常见的表达包括“我来做”、“我来处理”、“我来负责”、“我试试”等。识别这种模式需要确定发言人的身份，并将其作为责任人。

```markdown
示例1：
发言："关于用户调研报告的事情，我来写初稿，大家帮忙补充数据。"
提取结果：
- 任务描述：撰写用户调研报告初稿
- 责任人：发言人（假设为[姓名]）
- 协作人：团队成员（补充数据）
- 截止时间：待确定

示例2：
发言："下周一的客户演示，我来做。"
提取结果：
- 任务描述：准备并执行客户演示
- 责任人：发言人（假设为[姓名]）
- 截止时间：下周一
```

### 建议行动模式

建议行动模式中，发言人的语气相对委婉，表达的是建议而非直接命令。

建议行动通常包含“建议”、“可以”、“应该”等词汇，或者使用问句形式“要不要”、“能不能”。识别这种模式时，需要判断建议是否被采纳，如果被采纳则作为任务提取。

```markdown
示例1：
发言："我建议先做用户调研，再推进开发。大家觉得怎么样？"
背景：其他参会人表示同意。
提取结果：
- 任务描述：进行用户调研
- 责任人：待指定
- 截止时间：待确定
- 备注：建议行动，需确认执行人

示例2：
发言："能不能让小王帮忙看一下这个技术方案？"
背景：发言人看向小王，小王点头表示同意。
提取结果：
- 任务描述：审核技术方案
- 责任人：小王
- 截止时间：待确定
```

### 后续跟进模式

后续跟进模式通常出现在讨论某个问题的解决方案时，发言人会提出后续的行动计划。

后续跟进模式的标志词包括“然后”、“之后”、“接下来”、“之后要”等，表示事情的处理有明确的先后顺序。识别这种模式需要注意上下文，理解任务的逻辑关系。

```markdown
示例1：
发言："先把这个bug修复了，然后更新一下文档，之后再做测试。"
提取结果：
- 任务1：修复bug
  - 责任人：待指定
  - 截止时间：待确定
- 任务2：更新文档
  - 责任人：待指定
  - 截止时间：待确定
  - 依赖：任务1完成
- 任务3：进行测试
  - 责任人：待指定
  - 截止时间：待确定
  - 依赖：任务2完成

示例2：
发言："等设计稿确认后，开发这边就开始排期。"
提取结果：
- 任务描述：开始开发排期
- 责任人：开发团队
- 截止时间：设计稿确认后
- 前置条件：设计稿确认
```

### 问题驱动模式

问题驱动模式中，任务是针对某个问题的解决方案。

这种模式的识别需要先理解讨论中识别出的问题，然后将问题转化为任务。例如，当讨论中出现“这个问题需要解决”时，需要识别出具体是什么问题，然后提取为“解决[具体问题]”的任务。

```markdown
示例1：
发言："现在最大的问题是用户转化率低，我建议先做个A/B测试。"
提取结果：
- 任务描述：进行A/B测试分析用户转化率
- 责任人：待指定
- 截止时间：待确定
- 关联问题：用户转化率低

示例2：
发言："测试环境经常挂，这个月必须解决。"
提取结果：
- 任务描述：解决测试环境稳定性问题
- 责任人：待指定
- 截止时间：本月底
- 关联问题：测试环境经常宕机
- 优先级：🔴 高（发言中明确表示"必须"）
```

## 时间表达识别

### 精确日期表达

精确日期是最容易识别的时间表达，包括具体日期、星期几、假期名称等。

```markdown
识别规则：
- "3月15日" → 2026年3月15日
- "下周三" → 计算距离最近的下周三日期
- "本月最后一个周五" → 计算具体日期
- "国庆节后" → 2026年10月8日（假设国庆7天假期）

示例：
发言："这个任务3月20号之前必须完成。"
提取结果：截止时间 = 2026年3月20日
```

### 相对日期表达

相对日期需要根据会议日期计算得出具体的日期。

```markdown
识别规则：
- "今天" → 会议日期
- "明天" → 会议日期 + 1天
- "本周" → 会议日期所在周的周五
- "下周" → 会议日期下周的最后一天
- "本月" → 会议日期所在月的最后一天
- "下个月" → 下月的最后一天

示例：
会议日期：2026年4月6日（周一）
发言："本周五之前交给我。"

推理过程：
1. 会议是周一（4月6日）
2. 本周五 = 4月10日
3. "之前交给我" = 截止时间为4月10日

提取结果：截止时间 = 2026年4月10日
```

### 模糊时间表达

模糊时间需要根据上下文和任务复杂度推测合理的截止时间，并在报告中标注为推断。

```markdown
识别规则：
- "尽快" → 根据任务复杂度推测，通常1-3天
- "尽快处理" → 高优先级，通常1-2天
- "尽快看看" → 低优先级，通常3-5天
- "尽快完成" → 根据任务大小判断
- "尽快安排" → 等待确认，通常1周内

示例：
发言："这个bug比较紧急，尽快修复。"
提取结果：
- 截止时间：2026年4月8日（推测，会议后2天）
- 标注：[系统推断 - 发言人表述为"比较紧急"]
```

### 无时间表达

当发言中没有提及任何时间时，需要根据任务性质和上下文推测合理的时间节点。

```markdown
推测规则：
- 临时性任务 → 会议后1-2天
- 日常性任务 → 会议后1周内
- 大型项目任务 → 会议后2-4周
- 需要等待前置条件 → 标注依赖条件

示例：
发言："小李负责跟进一下这个供应商的情况。"
提取结果：
- 任务描述：跟进供应商情况
- 责任人：小李
- 截止时间：2026年4月13日（推测，会议后1周）
- 标注：[系统推断 - 发言人未明确截止时间]
```

## 责任人识别

### 明确责任人

当发言中明确提到执行人的姓名或职位时，直接提取为责任人。

```markdown
识别规则：
- "小李负责" → 责任人 = 小李
- "张三来做" → 责任人 = 张三
- "王经理处理" → 责任人 = 王经理
- "产品部负责" → 责任人 = 产品部（需后续细化）
- "我们团队来做" → 责任人 = 发言人所在团队

示例：
发言："这个调研报告交给市场部的小陈来做吧，他之前有相关经验。"
提取结果：
- 任务描述：完成调研报告
- 责任人：小陈
```

### 推断责任人

当发言中没有明确提到责任人时，需要根据上下文推断。

```markdown
推断规则：
1. 谁提出的问题，谁负责解决
2. 谁所在的部门负责相关领域，谁负责
3. 发言人的直属上级负责监督
4. 待指定时，标注需要后续确认

示例1：
发言："我觉得这个功能需要优化一下。"
提取结果：
- 任务描述：优化[具体功能]
- 责任人：发言人（推断）或产品经理（需确认）
- 标注：[需确认责任人]

示例2：
发言："关于用户体验的问题，产品这边需要重点关注。"
提取结果：
- 任务描述：关注用户体验问题
- 责任人：产品团队（推断为产品经理）
- 标注：[可进一步细化到具体个人]
```

### 多人任务

当任务需要多人协作时，需要区分责任人和协作人。

```markdown
识别规则：
- "小李和小王一起负责" → 责任人均为小李和小王
- "小李负责，张经理配合" → 责任人 = 小李，协作人 = 张经理
- "张三主导，李四支持" → 责任人 = 张三，协作人 = 李四
- "大家一起做" → 责任人 = 全员，需细化

示例：
发言："这个项目由我来主导，小王负责技术支持，小李负责数据支持。"
提取结果：
- 任务描述：[项目名称]执行
- 责任人：发言人（假设为[姓名]）
- 协作人：小王（技术支持）、小李（数据支持）
```

## 优先级判定

### 优先级定义

| 优先级 | 标识 | 定义 | 判定标准 |
|-------|------|------|---------|
| 高 | 🔴 | 必须立即处理 | 涉及关键决策、紧急问题、明确deadline |
| 中 | 🟡 | 正常优先级 | 常规任务，有合理的时间窗口 |
| 低 | 🟢 | 可延后处理 | 锦上添花的任务，无明确时间要求 |

### 优先级判定规则

```markdown
高优先级判定（满足任一条件）：
1. 发言中使用"必须"、"紧急"、"马上"、"立刻"等词
2. 任务与关键决策直接相关
3. 有明确且紧迫的截止时间
4. 任务未完成会导致其他工作阻塞
5. 涉及安全、合规、风险等敏感领域

中优先级判定（满足任一条件）：
1. 有明确的截止时间，但不是紧急的
2. 任务对项目有贡献，但不是必需的
3. 可以在正常工作节奏中完成

低优先级判定（满足任一条件）：
1. 发言中使用"有空的话"、"看看"、"了解"等词
2. 没有明确时间要求
3. 任务属于探索性或改进性质
4. 有其他更紧迫的任务需要优先处理
```

### 优先级示例

```markdown
示例1：高优先级
发言："这个bug必须今天修复，否则影响明天的演示。"
判定依据：使用了"必须"，有明确紧急截止时间
提取结果：优先级 = 🔴 高

示例2：中优先级
发言："小李，下周之前把这个功能开发完成。"
判定依据：有明确截止时间，但不是紧急的
提取结果：优先级 = 🟡 中

示例3：低优先级
发言："大家有空的时候可以了解一下竞品的情况。"
判定依据：使用"有空的时候"，无时间要求
提取结果：优先级 = 🟢 低
```

## 完成标准定义

### 完成标准的重要性

没有明确完成标准的任务往往会导致执行方和验收方对任务是否完成产生分歧。好的完成标准应该是可验证、可衡量的。

### 完成标准模板

```markdown
文档类任务：
- 完成标准：产出[文档类型]，包含[必要章节]，字数不少于[字数]，需经[审核人]确认

技术类任务：
- 完成标准：实现[功能描述]，通过[测试类型]，无[已知问题]遗留

沟通类任务：
- 完成标准：与[对象]完成[沟通目的]，对方确认[结果]

研究类任务：
- 完成标准：产出[研究产出物]，包含[必要分析维度]，为[决策/行动]提供支撑
```

### 完成标准推断

当发言中没有明确完成标准时，可以根据任务类型推断合理的标准。

```markdown
推断规则：
- 文档任务 → 提供完整文档供审阅
- 技术任务 → 实现功能并通过基本测试
- 沟通任务 → 完成沟通并记录结果
- 跟进任务 → 提供进展报告

示例：
发言："小王跟进一下供应商的事情。"
推断标准：
- 完成标准：提供供应商情况报告，包含[公司名称]的[合作意向/报价/资质]等信息
```

## 质量控制机制

### 完整性检查

提取每个任务后，需要检查以下项目：

```markdown
检查清单：
□ 任务描述是否清晰（不含模糊指代）
□ 责任人是否明确（不含"大家"、"谁"等模糊表达）
□ 截止时间是否具体（不含"尽快"等模糊表达）
□ 任务是否可执行（不依赖未确定的前置条件）
□ 任务范围是否合理（不是过于笼统或过于细节）

不完整时的处理：
- 标注缺失字段
- 提供推断值（需标注）
- 生成信息确认清单
```

### 一致性检查

```markdown
检查清单：
□ 同一人在同一会议中被分配的多个任务是否有冲突
□ 任务的截止时间是否符合依赖关系
□ 责任人的任务量是否合理（是否有过多任务）
□ 任务优先级是否与上下文一致

不一致时的处理：
- 标注潜在冲突
- 提供协调建议
- 生成冲突解决清单
```

### 去重与合并

```markdown
识别重复任务的规则：
1. 相同的任务描述 → 合并（保留信息最完整的）
2. 部分重叠的任务 → 合并为一个更完整的任务
3. 子任务关系 → 保留为独立任务，标注父子关系

示例：
发言1："小李整理一下会议纪要。"
发言2："小李把今天讨论的内容记录下来。"

识别结果：两个发言描述的是同一个任务
合并结果：
- 任务描述：整理并记录今天会议讨论内容
- 责任人：小李
- 备注：合并自两次发言
```

## 特殊场景处理

### 嵌套任务

当一个任务包含多个子任务时，需要拆分为独立任务并标注层级关系。

```markdown
示例：
发言："这个项目我来做，先做调研，再做方案，最后评审。"

提取结果：
- 任务1：项目调研
  - 责任人：发言人
  - 截止时间：待确定
  - 父任务：[项目执行]

- 任务2：项目方案制定
  - 责任人：发言人
  - 截止时间：待确定
  - 父任务：[项目执行]
  - 依赖：任务1完成

- 任务3：项目方案评审
  - 责任人：发言人
  - 截止时间：待确定
  - 父任务：[项目执行]
  - 依赖：任务2完成

- 父任务：项目执行
  - 责任人：发言人
  - 截止时间：待确定
  - 子任务：任务1、任务2、任务3
```

### 条件任务

当任务的执行依赖于某个条件时，需要标注前置条件。

```markdown
示例：
发言："等设计稿确认后，开发这边就开始排期。"

提取结果：
- 任务描述：开发排期
- 责任人：开发团队
- 截止时间：设计稿确认后
- 前置条件：设计稿确认完成
- 标注：[条件任务 - 执行时间依赖前置条件完成]
```

### 循环任务

当任务是周期性的（如每周、每月）时，需要标注任务周期。

```markdown
示例：
发言："每周一早上开个周会，同步一下各组的进展。"

提取结果：
- 任务描述：参加/组织周会
- 责任人：团队负责人（组织）、全员（参加）
- 截止时间：每周一
- 任务周期：每周
- 备注：周期性任务，需设置定期提醒
```

### 模糊任务

当发言中的任务描述过于模糊时，需要尝试细化或标注需要澄清。

```markdown
示例：
发言："这个事后续跟进一下。"

识别问题：
- "这个事"指代不明确
- "后续"时间不明确
- "跟进"动作不明确

处理方式：
1. 尝试根据上下文理解具体指什么
2. 如果无法理解，标注需要澄清
3. 生成澄清问题清单

提取结果（如能推断）：
- 任务描述：跟进[推断的具体事项]
- 责任人：待指定
- 标注：[系统推断 - 原描述模糊]

提取结果（如无法推断）：
- 任务描述：[待澄清] 跟进[发言中提到的事项]
- 责任人：待指定
- 需要澄清：
  1. 具体要跟进什么事情？
  2. 什么时间之前完成？
  3. 由谁负责？
```
