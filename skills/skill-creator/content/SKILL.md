# 技能创建器（MatrixAgent 工程版）

像软件产品一样构建技能，而非一次性提示。

此技能用于创建或改进技能，具有明确的质量门槛、可重复的验证、测试覆盖率、打包规范和发布就绪的输出。

## 运营原则

1. **为可重复性而工程化**
   - 对于重复或脆弱的操作，优先使用确定性脚本。
   - 当行为可以自动检查时，减少"模糊"指令。

2. **分片交付**
   - 快速生成可运行的草稿，然后使用客观反馈进行迭代。
   - 避免过度拟合某个演示提示词。

3. **保持上下文精简**
   - 保持 `SKILL.md` 简洁，专注于工作流程决策。
   - 将大量细节移到 `references/`；保持从 `SKILL.md` 出发的一跳链接。

4. **打包前通过质量门槛**
   - 验证必须通过。
   - 测试必须通过（或用户明确接受已知差距）。
   - 打包必须可重现且安全。

5. **默认安全**
   - 不打包 secrets、本地凭证或无关文件。
   - 拒绝或跳过不安全的文件系统结构（例如符号链接逃逸 root）。

## 目录契约

除非有充分理由，否则使用以下结构：

```text
skill-name/
├── SKILL.md
├── _meta.json                # 必填：{"id":"...","version":"..."}
├── scripts/                  # 确定性自动化
│   ├── init_skill.py         # 可选：脚手架辅助工具
│   ├── quick_validate.py     # 如果存在自定义约束则必填
│   ├── package_skill.py      # 分发输出必填
│   └── test_*.py             # 脚本的回归测试
├── references/               # 可选：详细文档/模式
└── assets/                   # 可选：输出资产/模板
```

## 端到端工作流程

除非用户要求跳过，否则按顺序遵循以下阶段。

### 阶段 1：发现与范围锁定

澄清：
- 目标成果（技能实现的目标）
- 触发边界（何时应触发，何时不应触发）
- 预期输出/产物
- 确定性 vs 启发式部分（什么应变为脚本）
- 完成定义（"就绪"意味着什么）

本阶段输出：
- 最终技能名称（连字符格式，<= 64 字符）
- 由 `generate_skill_id` 工具生成的技能 ID（仅限新技能）
- 带明确触发短语的 frontmatter 描述草稿
- 初始验收标准列表

### 阶段 2：技能架构

设计三层：
1. **元数据层**：`name`、`description` 用于触发质量
2. **执行层**：`SKILL.md` 中的简洁工作流程
3. **资源层**：用于详细内容的 scripts/references/assets

规则：
- 将所有"何时使用"的逻辑放在 frontmatter `description` 中。
- 不要在 `SKILL.md` 和 `references/` 中重复大型文档。
- 如果工作流程脆弱，提供基于脚本的执行路径。
- 每个技能必须包含带有 `id` 和 `version` 的 `_meta.json`。

### 阶段 3：脚手架与实现

1. 对于新技能，首先调用 `generate_skill_id` 并保留返回的 ID。
2. 创建/更新 `SKILL.md` 骨架。
3. 创建 `_meta.json`：

```json
{
  "id": "<generate_skill_id 返回的 id>",
  "version": "1.0.0"
}
```

注意：
- `id` 在首次创建后不可变。
- `version` 遵循语义化版本，在发布更新时递增。

4. 仅在有重复逻辑或严格可靠性需求时添加 `scripts/`。
5. 为模式、边缘情况和长示例添加 `references/`。
6. 在验证前删除占位符和无效内容。

### 阶段 4：质量门槛（必填）

首先运行验证，然后运行测试：

1. **Frontmatter + 结构验证**
   - **Frontmatter 必须在第一行** - 在 `---` 之前不能有 markdown 标题（`#`）
   - 必填 frontmatter 键：`name`、`description`
   - 必填 `_meta.json` 键：`id`、`version`
   - 命名、长度和格式检查
   - 资源和路径合理性检查

   **常见错误检查：**
   - ❌ SKILL.md 以 `# Title` 开头而非 `---`
   - ❌ Frontmatter 缺少 `description` 字段
   - ❌ Frontmatter 放在 markdown 内容之后

2. **脚本测试通过**
   - 至少包含验证器和打包器的冒烟测试
   - 为已修复的 bug 添加回归测试

3. **打包试运行**
   - 确认归档内容和新文件夹布局
   - 验证不包含构建垃圾/secrets

如有任何门槛失败，修复后重新运行再继续。

### 阶段 5：行为评估循环

对于新的或重大修改的技能：

1. 准备 3-10 个现实的评估提示
2. 使用技能执行运行
3. 在相关时，比较基线（无技能或先前版本）
4. 尽可能使用客观检查进行评分
5. 为主观维度收集定性反馈
6. 修改技能并重新运行

避免过拟合：
- 保留一个独立的迷你集用于确认。
- 优先考虑跨提示泛化的改进。

### 阶段 6：发布打包

仅在门槛为绿后打包。

预期命令模式：

```bash
python scripts/package_skill.py <path/to/skill>
```

发布检查清单：
- 归档干净打开
- 仅包含预期文件
- `SKILL.md` frontmatter 与文件夹名称和意图匹配
- 用户收到最终 `.skill` 产物的路径

## 此技能的工程标准

创作或重构 `skill-creator` 风格的技能时：

- **验证优先**：提供机器可检查的约束，而非仅散文描述
- **可测试脚本**：为关键脚本包含单元/回归测试
- **失败透明**：错误应明确且可操作
- **幂等命令**：在实用时重新运行应安全
- **最小信任面**：避免宽泛的文件包含规则

## 技能内容编写指南

优先：
- 祈使句、面向任务的指令
- 具有现实提示的具体示例
- 决策点（"如果 X，做 Y"）

避免：
- 没有执行价值的长篇理论
- 对于脆弱任务的模糊"尽力而为"
- 关于环境/工具的隐藏假设

## 安全更新现有技能

改进现有技能时：

1. 除非要求重命名，否则保留现有技能标识。
2. 在重大编辑前进行快照或分支。
3. 为行为变更保留兼容性说明。
4. 在每次实质性修订后重新运行验证/测试/打包。

## 完成定义

只有满足以下所有条件时，技能变更才算完成：

- `SKILL.md` 简洁、清晰、触发准确。
- `_meta.json` 存在且包含有效的 `id` 和语义化 `version`。
- 可复用逻辑在适当情况下外部化为 scripts/references。
- 验证通过。
- 脚本测试通过（或用户记录的例外已批准）。
- 打包成功并产生可用的 `.skill` 文件。
- 用户面向的摘要包括变更内容、原因以及如何运行各个门槛。

## 快速执行检查清单

在内部任务跟踪中使用此检查清单：

- [ ] 范围和验收标准已确认
- [ ] 名称 + 丰富触发描述已定稿
- [ ] `SKILL.md` 草稿已完成/重构
- [ ] 已添加或清理 scripts/references/assets
- [ ] 验证通过
- [ ] 测试通过
- [ ] 评估循环完成（如适用）
- [ ] 包已生成
- [ ] 交付摘要已准备
