## 生成规则

### 🚨 核心原则：需求优先，公约为辅

**重要**：测试点生成必须遵循以下优先级顺序：

1. **第一优先级 - 本需求功能点**：从需求中提取所有功能点，确保每个功能点都有对应的测试点
2. **第二优先级 - 测试理论方法**：应用等价类、边界值、状态转换等测试方法
3. **第三优先级 - 需求公约补充**：参考公约补充可能遗漏的通用测试场景

### 基本规则

1. 只生成测试点（TEST_POINT）
2. 生成的测试点必须与参考节点关联
3. 每个测试点必须有明确的验证目标和可执行性
4. 测试点应具备原子性，不可再分解

## 测试点生成流程

### 步骤1：需求功能点提取（最重要）

**必须首先完成**：从需求分析内容中提取所有功能点

1. **识别功能模块**：从需求中识别所有功能模块和子模块
2. **提取功能点**：为每个模块提取具体的功能点
3. **识别界面元素**：提取页面、按钮、字段、查询条件等
4. **识别业务规则**：提取业务逻辑、约束条件、规则说明
5. **识别数据流**：提取数据的输入、处理、输出流程

### 步骤2：为功能点生成测试点

**基于需求功能点生成测试点**：

1. **功能验证测试点**：验证每个功能点是否按需求实现
2. **界面验证测试点**：验证界面元素是否正确显示和交互
3. **业务规则测试点**：验证业务逻辑和规则是否正确执行
4. **数据验证测试点**：验证数据的输入、处理、输出是否正确

### 步骤3：应用测试理论方法

**基于测试理论补充测试点**：

1. **等价类划分**：为每个输入字段设计有效和无效等价类测试点
2. **边界值分析**：为数值、长度等设计边界值测试点
3. **状态转换**：为状态变化设计状态转换测试点
4. **错误推测**：基于经验推测可能的错误场景

### 步骤4：参考公约补充遗漏

**最后一步**：参考需求公约补充可能遗漏的通用测试场景

1. **读取公约文件**：使用 `read_file` 读取 `generators/conventions.md` 文件
2. **匹配公约章节**：根据 `matched_conventions` 参数中的公约类型，定位到对应的章节
3. **检查遗漏场景**：对比已生成的测试点，检查是否有公约要求的必测场景遗漏
4. **补充遗漏测试点**：仅补充确实遗漏的通用测试场景

### 公约应用规则

1. **补充性原则**：公约仅用于补充遗漏的通用测试场景，不能替代需求功能点的测试
2. **需求优先原则**：当公约规则与具体需求冲突时，以具体需求为准
3. **特殊说明优先**：需求文档中有特殊说明的，以需求文档为准
4. **避免重复**：已从需求功能点生成的测试点，不需要再从公约中重复生成

## 输出要求

**🚨 关键规则 - 确保输出稳定性**：

1. **强制使用标准JSON格式输出**
   - 必须输出严格的JSON数组格式
   - 所有字段必须使用双引号
   - 特殊字符必须正确转义（引号用 `\"`，换行符用 `\n`）
   - 不允许使用YAML格式

2. **输出格式验证**
   - 输出必须是可直接解析的JSON数组
   - 每个测试点节点必须包含所有必需字段：`uid`, `name`, `description`, `kind`, `parent_uid`
   - 必须为每个节点生成唯一的 `uid` 字段

3. **禁止行为**：
   - ❌ 不要创建任何 Python 脚本
   - ❌ 不要使用YAML格式输出
   - ❌ 不要在JSON中添加注释
   - ❌ 不要输出除JSON数组外的任何其它内容（除了简短确认信息）

4. 直接输出到临时文件中

## 测试点类型

根据测试理论和验证需要，可生成以下类型的测试点：

### 1. 功能验证测试点

- **正向功能测试点** - 验证功能正常执行路径
- **反向功能测试点** - 验证功能异常处理能力
- **业务规则测试点** - 验证业务逻辑和规则正确性

### 2. 数据验证测试点

- **输入验证测试点** - 验证输入数据的有效性检查
- **输出验证测试点** - 验证输出数据的正确性和完整性
- **数据转换测试点** - 验证数据处理和转换逻辑

### 3. 边界条件测试点

- **边界值测试点** - 验证边界值和临界值处理
- **等价类测试点** - 验证等价类划分的代表性数据
- **极限值测试点** - 验证系统在极限条件下的表现

### 4. 状态验证测试点

- **状态转换测试点** - 验证状态机的转换逻辑
- **状态保持测试点** - 验证状态的持久性和一致性
- **并发状态测试点** - 验证并发访问下的状态管理

### 5. 接口交互测试点

- **接口调用测试点** - 验证接口的调用和响应
- **参数传递测试点** - 验证参数的传递和解析
- **协议兼容测试点** - 验证协议的兼容性和标准性

### 6. 性能验证测试点

- **响应时间测试点** - 验证系统响应时间要求
- **吞吐量测试点** - 验证系统处理能力
- **资源消耗测试点** - 验证系统资源使用情况

### 7. 安全验证测试点

- **权限控制测试点** - 验证访问权限和授权机制
- **数据安全测试点** - 验证数据加密和保护措施
- **攻击防护测试点** - 验证系统安全防护能力

## 测试点设计原则

1. **原子性** - 每个测试点验证单一明确的功能点
2. **可执行性** - 测试点必须可以被具体执行和验证
3. **独立性** - 测试点之间相互独立，不存在依赖关系
4. **可重复性** - 测试点可以重复执行并得到一致结果
5. **可验证性** - 测试点有明确的通过/失败判断标准
6. **需求覆盖完整性** - 必须覆盖需求中定义的所有功能点（最重要）
7. **公约补充完整性** - 补充公约要求的通用测试场景（次要）

## 测试点生成策略

### 一、基于测试理论的生成策略

#### 1. 等价类划分法

- 识别输入条件的有效等价类和无效等价类
- 为每个等价类设计代表性测试点
- 确保覆盖所有有效和无效的输入情况

#### 2. 边界值分析法

- 识别输入/输出的边界值
- 设计边界值、边界值±1的测试点
- 考虑空值、最大值、最小值等特殊情况

#### 3. 状态转换法

- 识别系统的所有状态
- 设计状态转换路径的测试点
- 验证状态转换的条件和结果

#### 4. 错误推测法

- 根据经验推测可能存在的错误
- 设计针对潜在错误的测试点
- 考虑异常情况和边界情况

### 二、基于节点类型的生成策略

#### 基于模块节点生成测试点

- 分析模块的核心功能和关键逻辑
- 识别模块的输入输出和处理流程
- 考虑模块的异常情况和边界条件
- 覆盖模块的各种使用场景和配置

#### 基于场景节点生成测试点

- 分解场景中的具体验证步骤
- 识别场景中的关键验证点
- 考虑场景执行过程中的状态变化
- 覆盖场景的正常和异常分支

#### 基于需求节点生成测试点

- 解析需求的具体功能要求
- 识别需求的验收标准和质量要求
- 分析需求的约束条件和限制
- 考虑需求实现的技术细节

### 三、基于功能类型的生成策略

#### 列表/表格类功能

- 排序验证：默认排序、字段排序、多字段排序
- 分页验证：分页显示、翻页、每页条数
- 筛选验证：查询条件、组合查询、重置
- 展示验证：字段显示、格式化、空值处理
- 操作验证：勾选、批量操作、单条操作

#### 表单类功能

- 字段验证：必填、格式、长度、范围
- 提交验证：成功提交、失败提示、重复提交
- 取消验证：取消操作、数据清空
- 编辑验证：数据回显、修改提交

#### 权限类功能

- 菜单权限：菜单显示、菜单隐藏
- 数据权限：数据隔离、查询条件隔离
- 操作权限：按钮显示、操作限制

#### 接口类功能

- 参数验证：必填参数、参数类型、参数范围
- 响应验证：响应格式、响应状态、响应数据
- 异常处理：超时、错误码、重试机制

## 标准输出格式

**必须严格遵循以下JSON格式**：

```json
[
  {
    "uid": "test_point-abc123",
    "name": "验证登录页面正常显示",
    "description": "验证登录页面能够正常加载，包含用户名、密码输入框和登录按钮",
    "kind": "TEST_POINT",
    "parent_uid": "scene_12345"
  },
  {
    "uid": "test_point-def456",
    "name": "验证用户名输入有效性",
    "description": "验证用户名输入框能够正确接受有效的用户名格式",
    "kind": "TEST_POINT",
    "parent_uid": "scene_12345"
  },
  {
    "uid": "test_point-ghi789",
    "name": "验证密码输入安全性",
    "description": "验证密码输入框能够正确隐藏密码字符，显示为*号",
    "kind": "TEST_POINT",
    "parent_uid": "scene_12345"
  }
]
```

## 字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `uid` | string | ✅ | 节点唯一标识，格式：`test_point-{随机字符}` |
| `name` | string | ✅ | 测试点名称，简洁明确 |
| `description` | string | ✅ | 测试点详细描述 |
| `kind` | string | ✅ | 固定值：`TEST_POINT` |
| `parent_uid` | string | ✅ | 必须使用 `ref_nodes` 参数中提供的节点 uid |

## 特殊字符处理规则

在JSON字符串中，以下字符必须转义：
- 双引号：`"` → `\"`
- 反斜杠：`\` → `\\`
- 换行符：不允许使用真实换行，用 `\n` 或用逗号/分号分隔
- 制表符：`\t`

**示例**：
```json
{
  "name": "验证\"密码\"输入安全性",
  "description": "验证密码输入框能够正确隐藏密码字符，显示为*号或其它安全符号"
}
```

## 临时文件处理

**重要**：生成测试点后，需要进行遗漏检测，因此需要保存临时文件。

### 临时文件保存

- **保存时机**：生成测试点后，立即保存到临时文件
- **临时文件路径**：`.testbuddy/md/.temp_testpoints_{需求ID}.md`
- **保存方式**：使用 `write_file` 工具保存
- **文件格式**：Markdown格式（与最终输出格式一致）

### 临时文件读取

- **读取时机**：遗漏检测步骤需要读取临时文件
- **读取方式**：使用 `read_file` 工具读取
- **用途**：基于临时文件中的测试点进行遗漏检测

### 临时文件清理

- **清理时机**：最终测试点保存完成后
- **清理方式**：使用 `DeleteFile` 工具删除临时文件
- **注意**：确保临时文件被正确清理，避免占用存储空间

## 遗漏测试点检测

**重要**：生成测试点后，必须执行遗漏检测，确保测试覆盖的完整性。

**关键要求**：必须使用任务列表机制，逐个检测所有维度，汇总所有遗漏的测试点。

### 创建检测任务列表

**必须**：使用 `todo_write` 工具创建检测任务列表，确保所有维度都被检测。

**标准任务列表**：
```json
[
  {"id": "1", "content": "需求功能点覆盖检测", "status": "pending", "priority": "high"},
  {"id": "2", "content": "参考需求对比检测", "status": "pending", "priority": "high"},
  {"id": "3", "content": "参考文档对比检测", "status": "pending", "priority": "high"},
  {"id": "4", "content": "需求公约应用检测", "status": "pending", "priority": "high"},
  {"id": "5", "content": "测试方法覆盖检测", "status": "pending", "priority": "medium"},
  {"id": "6", "content": "汇总遗漏测试点", "status": "pending", "priority": "high"},
  {"id": "7", "content": "生成最终测试点列表", "status": "pending", "priority": "high"}
]
```

### 检测流程

#### 任务1：需求功能点覆盖检测

**执行步骤**：
1. 标记任务1为`in_progress`
2. 提取需求分析中的所有功能点
3. 对比现有测试点是否覆盖所有功能点
4. 识别未覆盖的功能点
5. 记录遗漏的测试点
6. 标记任务1为`completed`

**检测清单**：
- [ ] 需求中的每个功能模块是否都有对应的测试点？
- [ ] 每个功能模块的核心功能是否都被覆盖？
- [ ] 功能点的优先级是否合理？

#### 任务2：参考需求对比检测

**执行步骤**：
1. 标记任务2为`in_progress`
2. 分析参考需求中的测试点或用例
3. 识别参考需求中有但当前需求中没有的测试点
4. 考虑业务场景的相似性和差异性
5. 记录遗漏的测试点
6. 标记任务2为`completed`

**检测清单**：
- [ ] 参考需求中的关键测试场景是否都被覆盖？
- [ ] 参考需求中的业务规则是否都被考虑？
- [ ] 参考需求中的异常场景是否都被覆盖？

#### 任务3：参考文档对比检测

**执行步骤**：
1. 标记任务3为`in_progress`
2. 分析参考文档（XMind、Excel等）中的测试点或用例
3. 识别参考文档中有但当前测试点中没有覆盖的内容
4. 考虑业务规则和数据场景
5. 记录遗漏的测试点
6. 标记任务3为`completed`

**检测清单**：
- [ ] 参考文档中的测试场景是否都被覆盖？
- [ ] 参考文档中的数据场景是否都被考虑？
- [ ] 参考文档中的业务规则是否都被应用？

#### 任务4：需求公约应用检测

**执行步骤**：
1. 标记任务4为`in_progress`
2. 检查匹配的需求公约是否都已应用
3. 识别公约要求但未生成的测试点
4. 确保公约的完整性应用
5. 记录遗漏的测试点
6. 标记任务4为`completed`

**检测清单**：
- [ ] 匹配的公约类型是否都已应用？
- [ ] 公约要求的必测场景是否都已生成？
- [ ] 公约的测试方法是否都已应用？

#### 任务5：测试方法覆盖检测

**执行步骤**：
1. 标记任务5为`in_progress`
2. 检查是否应用了正向测试、反向测试、边界值测试等
3. 识别缺少的测试方法场景
4. 确保测试方法的全面性
5. 记录遗漏的测试点
6. 标记任务5为`completed`

**检测清单**：
- [ ] 是否覆盖了正向测试（正常流程）？
- [ ] 是否覆盖了反向测试（异常流程）？
- [ ] 是否覆盖了边界值测试？
- [ ] 是否根据需求特点应用了其他测试方法？

#### 任务6：汇总遗漏测试点

**执行步骤**：
1. 标记任务6为`in_progress`
2. 汇总所有5个维度检测到的遗漏测试点
3. 去重：移除重复的测试点
4. 优先级排序：按照优先级（高/中/低）排序
5. 生成遗漏测试点列表
6. 标记任务6为`completed`

#### 任务7：生成最终测试点列表

**执行步骤**：
1. 标记任务7为`in_progress`
2. 将遗漏的测试点追加到步骤5生成的测试点列表中
3. 生成最终的测试点列表
4. 标记任务7为`completed`

### 检测结果输出

如果检测到遗漏的测试点，必须在测试点报告中增加"遗漏测试点检测"章节：

```markdown
## 遗漏测试点检测结果

### 一、检测概要

| 检测项 | 结果 | 数量 |
|--------|------|------|
| 需求功能点覆盖 | ✅完整 / ⚠️有遗漏 | {数量}个 |
| 参考需求对比 | ✅完整 / ⚠️有遗漏 | {数量}个 |
| 参考文档对比 | ✅完整 / ⚠️有遗漏 | {数量}个 |

| 测试方法覆盖 | ✅完整 / ⚠️有遗漏 | {数量}个 |

### 二、遗漏测试点列表

**重要**：以下测试点可能被遗漏，建议补充：

| 序号 | 遗漏类型 | 遗漏内容 | 建议测试点 | 优先级 | 说明 |
|------|---------|---------|-----------|--------|------|
| 1 | 功能点遗漏 | {遗漏的功能点} | {建议的测试点} | 高/中/低 | {为什么遗漏} |
| 2 | 公约遗漏 | {遗漏的公约} | {建议的测试点} | 高/中/低 | {公约要求} |

**建议补充以下测试点**：

1. {建议补充的测试点1}
2. {建议补充的测试点2}
```

### 处理原则

1. **优先级判断**：
   - 需求功能点遗漏：高优先级，必须补充
   - 需求公约遗漏：高优先级，必须补充
   - 参考需求遗漏：中优先级，建议补充
   - 参考文档遗漏：中优先级，建议补充
   - 测试方法遗漏：低优先级，选择性补充

2. **补充方式**：
   - 高优先级遗漏：直接追加到测试点列表中
   - 中优先级遗漏：在遗漏检测章节列出，由用户决定
   - 低优先级遗漏：在遗漏检测章节列出，由用户决定

3. **完整性标准**：
   - 所有需求功能点都有对应的测试点
   - 所有匹配的公约都已应用
   - 至少覆盖正向测试和反向测试
