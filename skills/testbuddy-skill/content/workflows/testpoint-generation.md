# 测试点生成工作流

**触发关键词**：`生成测试点`、`创建测试点`、`根据模块生成测试点`、`根据场景生成测试点`

**工作流简介**：基于参考节点（模块、场景或需求）和需求分析，生成原子性的测试点（TEST_POINT类型节点），明确具体的测试验证目标

## 执行清单规划

在开始执行前，工作流需要：
1. 使用 `todo_write` 工具创建执行清单，将下述执行步骤转化为 TODO 列表
2. 执行应该按照列表的顺序进行执行，禁止跳过步骤
3. 每完成一个步骤后，需检查步骤是否执行，检查通过后更新对应 TODO 的状态为 `completed`
3. 开始新步骤时，将对应 TODO 状态更新为 `in_progress`

**标准 TODO 清单模板**：

Demo:
```json
[
  {"id":"1", "status":"pending", "content":"step1"},
  {"id":"2", "status":"pending", "content":"step2"},
  ...
]
```

## 执行流程

**步骤 1：确认参考节点列表**
需根据实际用户的意图选择合适的方式
- **方式一**：从对话上下文中读取（SKILL加载时已执行 load_session，结果在上下文中）
- **方式二**：使用 `load_session` 工具（位于 `tools/load_session.md`）读取会话信息
- **方式三**：使用 `search_nodes` 工具（位于 `tools/search_nodes.md`）从脑图节点中查询
- 节点信息包含：uid, name, kind, instance
- 如未找到节点信息或信息不完整，提示用户并终止流程
- 参考节点可能是单个、也可能是多个
- **禁止**：从其他文件中获取参考节点列表

**步骤 2：查找关联需求或用例**
需根据实际用户的意图选择合适的方式

**2.1 识别需求类型**
- **主需求**：用户明确要求生成测试点的需求
- **参考需求**：用户提供作为参考的其他需求（关键词：`参考需求`、`参考`、`类似需求`、`参照需求`）
- **参考用例**：用户提供作为参考的测试用例（关键词：`参考用例`、`参考测试用例`、`类似用例`）

**2.2 获取主需求信息**
- **方式一**：从对话上下文中读取（SKILL加载时已执行 load_session，结果在上下文中）
- **方式二**：使用 `load_session` 工具（位于 `tools/load_session.md`）读取会话信息
- **方式三**：使用 `search_nodes` 工具（位于 `tools/search_nodes.md`）从脑图查询 STORY 或 BUG 类型节点
- **方式四**：用户直接提供了TAPD需求ID或需求文档路径
  - **TAPD需求ID**：使用 `fetch_tapd_issue.py` 脚本获取需求内容
    - 执行：`python scripts/fetch_tapd_issue.py --issue-id <需求ID> --save --output markdown`
    - 保存位置：`.testbuddy/md/STORY-<需求ID>.md`
  - **需求文档路径**：直接读取用户提供的文档
    - 文本文件：直接读取内容
    - Excel文件：使用 `parse_excel.py` 解析
    - XMind文件：使用 `parse_xmind.py` 解析
- 如未找到主需求信息：
  - 如果用户提供了TAPD ID，使用方式四获取
  - 否则提示用户并终止

**2.3 获取参考需求信息（如有）**
- **重要**：必须主动识别用户是否提供了参考需求，如有则必须获取
- **识别方式**：
  - 关键词识别：`参考需求`、`参考`、`类似需求`、`参照需求`
  - TAPD需求ID识别：用户提到其他需求ID
  - 文件路径识别：用户提供了其他需求文档路径
- **获取方式**：
  - **TAPD需求ID**：使用 `fetch_tapd_issue.py` 脚本获取
    - 执行：`python scripts/fetch_tapd_issue.py --issue-id <需求ID> --save --output markdown`
    - 读取保存的文件内容作为参考需求
  - **需求文档路径**：直接读取用户提供的文档
    - 文本文件：直接读取内容
    - Excel文件：使用 `parse_excel.py` 解析
    - XMind文件：使用 `parse_xmind.py` 解析
- **输出**：`reference_requirements` 列表

**2.4 获取参考用例信息（如有）**
- **重要**：必须主动识别用户是否提供了参考用例，如有则必须获取
- **识别方式**：
  - 关键词识别：`参考用例`、`参考测试用例`、`类似用例`
  - 文件路径识别：用户提供了用例文档路径
- **获取方式**：
  - **用例文档路径**：直接读取用户提供的文档
    - Excel文件：使用 `parse_excel.py` 解析
    - XMind文件：使用 `parse_xmind.py` 解析
- **输出**：`reference_cases` 列表

**2.5 输出结果**
- **主需求信息**：需求ID、需求名称、需求内容
- **参考需求列表**：`reference_requirements`（如有）
- **参考用例列表**：`reference_cases`（如有）
- **禁止**：从其他文件中获取需求信息（除非用户明确提供）

**步骤 3：需求分析**
- **使用工具**：`select_rule`（位于 `tools/select_rule`），传入关键词"需求分析"
- **根据返回结果**：
  - 如果返回自定义规则路径（`.codebuddy/rules/xxx`）：使用 `read_rules` 读取规则内容
  - 如果返回默认Generator路径（`generators/xxx`）：使用 `read_file` 读取 Generator 内容
- **执行方式**：按获取到的规则/Generator定义执行需求分析
- **标准输入参数**
  ```python
  {
    "issue_uid": "{需求节点的uid}",
    "issue_kind": "STORY 或 BUG",
    "raw_issue": "{需求详情内容或文件路径 @file:xxx}"
  }
  ```
- **输出**：需求分析文档结果
- **复用逻辑**：如该需求已分析过，直接使用历史分析文档

**步骤 4：检索需求知识库**
- **使用工具**：`RAG_search`（位于 `tools/rag_search.md`）
- **检索目标**：从需求分析结果中提取关键词进行检索
  - **关键词提取方法**：
    - 从步骤3的需求分析结果中识别核心功能模块
    - 提取关键业务术语和专业词汇
    - 识别技术要点和验证目标
    - 建议提取 3-5 个最具代表性的关键词
  - **检索策略**：
    - **优先策略**：使用 2-3 个核心关键词组合检索，获取高相关性内容
    - **补充策略**：如组合检索结果不足，可针对单个重要关键词补充检索
    - 检索历史需求描述、业务规则、技术规范等相关文档
  - **结果合并**：将检索到的知识库内容与步骤3的需求分析结果合并
    - 在需求分析文档末尾追加 "## 知识库参考信息" 章节
    - 整理检索内容，标注来源和关联性
    - 合并后的完整文档作为后续测试点生成的输入
- **说明**：工具内部会自动判断是否有可用的知识库，无需手动判断

**步骤 4.5：需求公约匹配（自动判断）**
- **目的**：根据需求分析内容自动识别需求类型，匹配适用的公约规则
- **执行方式**：分析需求分析文档中的关键词和功能特征
- **公约文件**：`generators/conventions.md`
- **判断逻辑**：
  | 公约类型 | 判断关键词 | conventions.md 对应章节 |
  |---------|-----------|------------------------|
  | 数据权限类 | 数据权限、权限隔离、核算主体、数据隔离 | 1.1 数据权限 |
  | 菜单权限类 | 菜单权限、菜单配置、权限分配 | 1.2 菜单权限 |
  | 列表类 | 列表、弹窗列表、树形结构、分页、排序 | 1.3 列表（包含弹出框） |
  | 按钮操作类 | 导出、导入、提交、删除、启用、禁用、查询、重置 | 1.4 按钮 |
  | 详情页面类 | 详情页、弹框、钻取、单据详情 | 1.5 详情页面及字段 |
  | 字段类 | 字段校验、必填、唯一性、长度、多选 | 1.6 字段 |
  | 兼容性类 | 移动端、浏览器、IE、微信 | 1.7 兼容性 |
  | 数据处理类 | 锁数据、双开页面、并发、数据修改 | 1.8 数据处理 |
  | 多语言类 | 多语言、国际化、语言切换 | 1.9 多语言处理 |
  | 接口类 | API、接口、接口字段、接口校验、接口请求、接口超时 | 2.1-2.8 接口类 |
- **匹配规则**：
  1. 扫描需求分析文档，识别上述关键词出现频率
  2. 出现频率较高的类型作为匹配的公约类型
  3. 一个需求可能匹配多个公约类型，需组合应用
  4. 将匹配结果作为输入参数传递给测试点生成器
- **输出**：`matched_conventions` 字段，包含匹配的公约类型列表，如 `["数据权限类", "列表类", "按钮操作类"]`


**步骤 5：生成测试点**
- **使用工具**：`select_rule`（位于 `tools/select_rule`），传入关键词"测试点生成"
- **根据返回结果**：
  - 如果返回自定义规则路径（`.codebuddy/rules/xxx`）：使用 `read_rules` 读取规则内容
  - 如果返回默认Generator路径（`generators/xxx`）：使用 `read_file` 读取 Generator 内容
- **执行方式**：按获取到的规则/Generator定义执行测试点生成
- **标准输入参数**：
  ```python
  {
    "ref_nodes": [  # YAML格式的参考节点数组
      {
        "uid": "feature_123",
        "name": "用户登录模块",
        "kind": "FEATURE"
      },
      {
        "uid": "scene_456",
        "name": "密码验证场景",
        "kind": "SCENE"
      }
    ],
    "issue_analysis": "{步骤3生成的需求分析文档完整内容（已包含步骤4合并的知识库参考信息，如有）或文件路径 @file:xxx}",
    "knowledge_context": "{步骤5检索到的历史测试点参考（如有）}",
    "matched_conventions": ["数据权限类", "列表类", "按钮操作类"],  # 步骤4.5匹配的公约类型列表
    "reference_requirements": ["参考需求1内容", "参考需求2内容"],  # 步骤2.5解析的参考需求
    "reference_cases": ["参考用例1内容", "参考用例2内容"]  # 步骤2.5解析的参考用例
  }
  ```
- **输出要求**：
  - ✅ **必须输出Markdown格式**
  - ✅ 包含汇总信息和详细测试点列表
  - ✅ **必须根据匹配的公约规则生成对应的测试点**
  - ✅ **必须参考用户提供的参考文档内容**
  - ❌ 禁止输出JSON格式
  - ❌ 禁止添加到脑图
- **临时保存**：
  - **重要**：将生成的测试点保存到临时文件，便于后续步骤读取和处理
  - 临时文件路径：`.testbuddy/md/.temp_testpoints_{需求ID}.md`
  - 使用 `write_file` 工具保存临时文件
  - 此文件将在步骤6完成后自动删除

**步骤 5.5：检测遗漏测试点（质量保证）**

**目的**：基于现有测试点，根据需求、关联需求、文档、需求公约等，自动检测遗漏的测试点，确保测试覆盖的完整性。

**重要**：必须使用任务列表机制，逐个检测所有维度，汇总所有遗漏的测试点。

**读取临时文件**：
- 使用 `read_file` 工具读取步骤5保存的临时测试点文件
- 临时文件路径：`.testbuddy/md/.temp_testpoints_{需求ID}.md`
- 基于临时文件中的测试点进行遗漏检测

**创建检测任务列表**：
- 使用 `todo_write` 工具创建检测任务列表
- 标准任务列表：
  ```json
  [
    {"id": "1", "content": "需求功能点覆盖检测", "status": "pending", "priority": "high"},
    {"id": "2", "content": "参考需求对比检测", "status": "pending", "priority": "high"},
    {"id": "3", "content": "参考文档对比检测", "status": "pending", "priority": "high"},
    {"id": "4", "content": "需求公约应用检测", "status": "pending", "priority": "high"},
    {"id": "5", "content": "测试方法覆盖检测", "status": "pending", "priority": "medium"},
    {"id": "6", "content": "汇总遗漏测试点", "status": "pending", "priority": "high"},
    {"id": "7", "content": "生成最终测试点列表", "status": "pending", "priority": "high"}
  ]
  ```

**逐个检测所有维度**：

**任务1：需求功能点覆盖检测**
- 标记任务1为`in_progress`
- 提取需求分析中的所有功能点
- 对比现有测试点是否覆盖所有功能点
- 识别未覆盖的功能点
- 记录遗漏的测试点
- 标记任务1为`completed`

**任务2：参考需求对比检测**
- 标记任务2为`in_progress`
- 分析参考需求中的测试点或用例
- 识别参考需求中有但当前需求中没有的测试点
- 考虑业务场景的相似性和差异性
- 记录遗漏的测试点
- 标记任务2为`completed`

**任务3：参考文档对比检测**
- 标记任务3为`in_progress`
- 分析参考文档（XMind、Excel等）中的测试点或用例
- 识别参考文档中有但当前测试点中没有覆盖的内容
- 考虑业务规则和数据场景
- 记录遗漏的测试点
- 标记任务3为`completed`

**任务4：需求公约应用检测**
- 标记任务4为`in_progress`
- 检查匹配的需求公约是否都已应用
- 识别公约要求但未生成的测试点
- 确保公约的完整性应用
- 记录遗漏的测试点
- 标记任务4为`completed`

**任务5：测试方法覆盖检测**
- 标记任务5为`in_progress`
- 检查是否应用了正向测试、反向测试、边界值测试等
- 识别缺少的测试方法场景
- 确保测试方法的全面性
- 记录遗漏的测试点
- 标记任务5为`completed`

**任务6：汇总遗漏测试点**
- 标记任务6为`in_progress`
- 汇总所有5个维度检测到的遗漏测试点
- 去重：移除重复的测试点
- 优先级排序：按照优先级（高/中/低）排序
- 生成遗漏测试点列表
- 标记任务6为`completed`

**任务7：生成最终测试点列表**
- 标记任务7为`in_progress`
- 将遗漏的测试点追加到步骤5生成的测试点列表中
- 生成最终的测试点列表
- 标记任务7为`completed`

**输出格式**：

```markdown
## 遗漏测试点检测结果

### 一、检测概要

| 检测项 | 结果 | 数量 |
|--------|------|------|
| 需求功能点覆盖 | ✅完整 / ⚠️有遗漏 | {数量}个 |
| 参考需求对比 | ✅完整 / ⚠️有遗漏 | {数量}个 |
| 参考文档对比 | ✅完整 / ⚠️有遗漏 | {数量}个 |
| 需求公约应用 | ✅完整 / ⚠️有遗漏 | {数量}个 |

#### 3. 参考文档遗漏

|------|---------|-----------|--------|------|
| 1 | {遗漏的场景} | {建议的测试点} | 高/中/低 | {参考文档来源} |
```

**处理方式**：
- 如果检测到遗漏的测试点，将遗漏测试点追加到步骤5生成的测试点列表中
- 在测试点报告中增加"遗漏测试点检测"章节
- 提示用户查看并确认是否需要补充

**重要说明**：
- 此步骤是质量保证环节，确保测试点的完整性
- 遗漏检测基于需求、参考文档、需求公约等多维度分析
- 检测结果仅供参考，最终由用户决定是否补充

**步骤 6：保存测试点（Markdown格式）**
