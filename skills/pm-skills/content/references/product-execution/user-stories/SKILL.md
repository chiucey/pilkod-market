# 用户故事

系统性的用户故事编写方法，帮助团队创建清晰、可测试、可维护的产品Backlog项。

## 用户故事基础

### 标准格式

```
作为 [用户类型]，
我想要 [目标]，
以便 [收益/原因]。
```

### 3C's 原则

| 原则 | 描述 | 应用 |
|-----|------|-----|
| **Card (卡片)** | 将需求写在卡片上 | 简短、聚焦 |
| **Conversation (对话)** | 通过沟通澄清细节 | 面对面讨论 |
| **Confirmation (确认)** | 定义明确的验收标准 | 可测试 |

### INVEST 原则

| 原则 | 首字母 | 描述 | 检查 |
|-----|-------|-----|-----|
| Independent | I | 独立的 | 不依赖其他故事 |
| Negotiable | N | 可协商的 | 不是固定规格 |
| Valuable | V | 有价值的 | 对用户或业务有价值 |
| Estimable | E | 可估算的 | 团队能评估工作量 |
| Small | S | 小的 | 可在1个Sprint完成 |
| Testable | T | 可测试的 | 有明确的验收标准 |

## 用户故事拆分

### 拆分维度

| 维度 | 方法 | 示例 |
|-----|-----|-----|
| **用户角色** | 按用户类型拆分 | 管理员 vs 普通用户 |
| **功能路径** | 按使用路径拆分 | 新建 vs 编辑 vs 删除 |
| **数据范围** | 按数据量拆分 | 单条 vs 批量 |
| **验收条件** | 按条件拆分 | 不同条件的处理 |
| **工作流程** | 按流程阶段拆分 | 提交 → 审批 → 生效 |
| **复杂程度** | 按实现复杂度拆分 | 简单版 vs 完整版 |

### 拆分示例

**原始故事**:
```
作为管理员，我想要管理用户账户，
以便我可以添加、编辑、删除用户。
```

**拆分后**:

```
US-001: 作为管理员，我想要查看用户列表，
以便我可以了解所有用户的情况。

US-002: 作为管理员，我想要添加新用户，
以便我可以创建新账户。

US-003: 作为管理员，我想要编辑用户信息，
以便我可以更新用户数据。

US-004: 作为管理员，我想要删除用户，
以便我可以移除不需要的账户。
```

## 用户故事估算

### 故事点估算

```markdown
### 斐波那契数列
1, 2, 3, 5, 8, 13, 21...

### 估算参考

| 故事点 | 描述 | 时间参考 |
|-------|-----|---------|
| 1 | 非常简单，1-2小时 | 1小时 |
| 2 | 简单，半天 | 4小时 |
| 3 | 中等，1天 | 8小时 |
| 5 | 复杂，2-3天 | 16-24小时 |
| 8 | 很复杂，1周 | 40小时 |
| 13 | 非常复杂，2周 | 80小时 |
```

### 相对估算 vs 绝对估算

| 方法 | 适用场景 | 优点 | 缺点 |
|-----|---------|-----|-----|
| **相对估算** | 大多数场景 | 快速、一致性 | 不精确 |
| **绝对估算** | 需要精确计划 | 精确 | 耗时 |
| **T恤尺码** | 快速估算 | 直观 | 粗糙 |

### T恤尺码估算

| 尺码 | 描述 | 故事点范围 |
|-----|------|----------|
| **XS** | 非常小，1-2小时 | 1 |
| **S** | 小，半天 | 2 |
| **M** | 中等，1-2天 | 3-5 |
| **L** | 大，3-5天 | 8 |
| **XL** | 非常大，1周+ | 13+ |

## 用户故事状态

### 状态流转

```
Backlog → Ready → In Progress → In Review → Done
  │          │          │            │         │
  │          │          │            │         └── 可交付
  │          │          │            └── 待验收
  │          │          └── 开发中
  │          └── 准备就绪，待开发
  └── 产品Backlog
```

### 状态定义

| 状态 | 描述 | 进入条件 |
|-----|------|---------|
| **Backlog** | 待排入Sprint | 创建完成 |
| **Ready** | 准备就绪 | 验收标准明确、技术可行 |
| **In Progress** | 开发中 | 开始实现 |
| **In Review** | 待验收 | 开发完成，提交测试 |
| **Done** | 完成 | 验收通过 |
| **Blocked** | 阻塞 | 遇到阻碍 |

### 创建步骤

1. **识别用户**: 谁会使用这个产品？
2. **识别活动**: 用户会用产品做什么？
3. **分解任务**: 每个活动包含哪些具体任务？
4. **编写故事**: 将任务转化为用户故事
5. **组织发布**: 按优先级组织到发布计划

## Backlog 管理

### Backlog 层级

```markdown
# 产品Backlog

## 层级结构

### Vision (愿景)
[产品愿景描述]

### Epic (史诗)
- [ ] Epic 1: [名称]
- [ ] Epic 2: [名称]

### Feature (特性)
#### Epic 1 下
- [ ] Feature 1.1: [名称]
- [ ] Feature 1.2: [名称]

### User Story (用户故事)
#### Feature 1.1 下
- [ ] US-001: [标题]
- [ ] US-002: [标题]
```

### Backlog 整理

```markdown
### 整理会议 (Backlog Grooming)

**频率**: 每周1-2次
**时长**: 1-2小时
**参与**: PM、设计师、技术负责人

**议程**:
1. [ ] 检查故事完整性 (10分钟)
2. [ ] 估算故事点 (30分钟)
3. [ ] 确定优先级 (30分钟)
4. [ ] 拆分过大故事 (20分钟)
5. [ ] 识别依赖 (10分钟)
```

### 优先级框架

| 优先级 | 描述 | 资源分配 |
|-------|-----|---------|
| **P0** | 必须有，MVP核心 | 最高 |
| **P1** | 应该有，重要但非核心 | 高 |
| **P2** | 可以有，提升体验 | 中 |
| **P3** | 最好有，低优先级 | 低 |

## 质量检查清单

### 故事编写检查

- [ ] 故事遵循"As a, I want, so that"格式
- [ ] 故事对用户或业务有价值
- [ ] 故事独立，不依赖其他故事
- [ ] 故事可估算，团队理解需求
- [ ] 故事足够小，可在1个Sprint完成
- [ ] 故事有明确的验收标准
- [ ] 验收标准可测试

### 验收标准检查

- [ ] 覆盖主流程
- [ ] 覆盖异常流程
- [ ] 覆盖边界条件
- [ ] 标准明确，无歧义
- [ ] 可转化为测试用例
- [ ] 所有标准被满足=故事完成
