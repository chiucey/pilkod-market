# OKRs 头脑风暴

系统性地创建与公司战略对齐的团队OKRs，确保目标清晰、可衡量、有挑战性。

## OKRs 基础

### OKR 结构

```
         目标 (Objective)
              │
    ┌─────────┼─────────┐
    │         │         │
    │         ▼         │
    │  关键结果 1 (KR1)   │
    │         │         │
    │         ▼         │
    │  关键结果 2 (KR2)   │
    │         │         │
    │         ▼         │
    │  关键结果 3 (KR3)   │
    │                   │
    └───────────────────┘
```

### O vs KR 定义

| 维度 | 目标 (O) | 关键结果 (KR) |
|-----|---------|--------------|
| **性质** | 定性的 | 定量的 |
| **描述** | 鼓舞人心 | 可衡量 |
| **时间** | 一个周期 | 周期性里程碑 |
| **数量** | 3-5个 | 每个O有3-5个 |
| **负责人** | 团队共同 | 明确责任人 |

## OKRs 创建流程

### 第一步：理解公司战略

```markdown
### 公司级 OKRs

**目标 O1**: [公司目标]
- KR1: [关键结果]
- KR2: [关键结果]

**目标 O2**: [公司目标]
- KR1: [关键结果]
```

### 战略对齐检查

| 问题 | 回答 |
|-----|-----|
| 公司本季度最重要的3件事是什么？ | 1. ... 2. ... 3. ... |
| 团队如何支持这些目标？ | [描述] |
| 有哪些跨团队依赖？ | [描述] |

---

### 第二步：头脑风暴目标

#### 好的目标特征

| 特征 | 描述 | 示例 |
|-----|------|-----|
| **鼓舞人心** | 能激励团队 | "成为用户最信赖的平台" |
| **清晰明确** | 团队理解含义 | "提升用户留存" |
| **有挑战性** | 超越舒适区 | "DAU翻倍" |
| **可达成** | 现实可行 | "用户满意度>90%" |
| **有期限** | 明确时间 | "Q2结束时" |

#### 目标分类

| 类型 | 描述 | 示例 |
|-----|------|-----|
| **业务结果** | 直接业务影响 | 增加收入 |
| **用户价值** | 用户体验改善 | 提升满意度 |
| **能力建设** | 团队能力提升 | 建立数据能力 |
| **基础设施** | 系统和技术基础 | 提升系统稳定性 |

#### 目标草案

```markdown
### 目标草案池

**O1**: [鼓舞人心的目标描述]
**O2**: [鼓舞人心的目标描述]
**O3**: [鼓舞人心的目标描述]

[继续头脑风暴更多候选目标]
```

---

### 第三步：设计关键结果

#### KR 设计原则

| 原则 | 描述 | 检查 |
|-----|------|-----|
| **具体** | 明确描述 | ✅/❌ |
| **可衡量** | 有明确数值 | ✅/❌ |
| **有挑战** | 需要努力达成 | ✅/❌ |
| **可验证** | 可以验证完成 | ✅/❌ |
| **上下对齐** | 支撑上级目标 | ✅/❌ |

#### KR 类型

| 类型 | 描述 | 示例 |
|-----|------|-----|
| **收入类** | 营收和增长 | MRR增长30% |
| **用户类** | 用户量和活跃度 | DAU达到100万 |
| **质量类** | 质量和效率 | 错误率<1% |
| **速度类** | 交付和响应 | 发布周期缩短50% |
| **能力类** | 团队和系统 | 建立自动化测试 |

#### KR 评分

| 分数 | 描述 | 含义 |
|-----|------|-----|
| **1.0** | 完全达成 | 过于简单？ |
| **0.7** | 接近达成 | 挑战性适中 |
| **0.5** | 50%达成 | 有挑战性 |
| **0.3** | 明显未达 | 需要调整 |
| **0** | 完全没有进展 | 方向错误 |

---

### 第四步：对齐和协调

#### 纵向对齐

```
公司 O
   │
   ▼
部门 O1 ──► 团队 O1.1
   │              │
   │              ▼
   │         KR1.1.1
   │
   ▼
部门 O2 ──► 团队 O1.2
              │
              ▼
         KR1.2.1
```

#### 横向协调

| 团队 | 需要支持 | 能提供 |
|-----|---------|-------|
| 团队A | 团队B的API | 团队C的数据 |
| 团队A | 团队D的设计 | 团队E的测试 |

## 进度追踪

### 周度更新模板

| 目标 | KR | 上周进度 | 本周进展 | 阻碍 | 信心 |
|-----|-----|---------|---------|-----|-----|
| O1 | KR1.1 | 20% | 30% | [阻碍] | 🟢高 🟡中 🔴低 |
| O1 | KR1.2 | 15% | 25% | [阻碍] | 🟢高 🟡中 🔴低 |
| O2 | KR2.1 | 10% | 20% | [阻碍] | 🟢高 🟡中 🔴低 |

### 信心指数

| 指数 | 含义 | 行动 |
|-----|-----|-----|
| 🟢 高 (80%+) | 非常有信心 | 保持节奏 |
| 🟡 中 (50-80%) | 中等信心 | 关注风险 |
| 🔴 低 (<50%) | 信心不足 | 重新评估 |

## OKRs 示例库

### SaaS 产品团队

```
O1: 成为用户最信赖的项目管理平台

KR1: NPS 分数从 45 提升到 60
KR2: 客户留存率从 85% 提升到 92%
KR3: 系统可用性保持在 99.9%
KR4: 核心功能使用率提升 30%
```

### 增长团队

```
O1: 实现产品主导的可持续增长

KR1: 月活跃用户 (MAU) 从 50万 增长到 70万
KR2: 自然增长占比从 30% 提升到 45%
KR3: 用户获取成本 (CAC) 降低 20%
KR4: 病毒系数 (K因子) 从 0.8 提升到 1.2
```

### 技术团队

```
O1: 建立可扩展、高性能的技术基础设施

KR1: API 响应时间 P99 从 500ms 降低到 200ms
KR2: 系统可用性从 99.5% 提升到 99.9%
KR3: 自动化测试覆盖率从 60% 提升到 85%
KR4: 部署频率从每周1次提升到每天3次
```

## OKRs vs KPIs

| 维度 | OKRs | KPIs |
|-----|-----|-----|
| **目的** | 变革和突破 | 维持和监控 |
| **心态** | 目标导向 | 基线导向 |
| **期望** | 100% = 挑战性目标 | 达标 = 正常 |
| **失败容忍** | 鼓励失败和学习 | 不容忍偏差 |
| **数量** | 有限的目标 | 可以很多 |
| **应用** | 创新和探索 | 运营和维护 |

## 常见问题

### Q: OKRs 和日常工作有什么区别？

**A**: OKRs 代表超越日常工作的额外努力。如果所有日常工作都在 OKRs 里，那说明 OKRs 不够有挑战性。

### Q: 信心指数低怎么办？

**A**:
1. 分析信心低的原因
2. 调整策略或举措
3. 如果确实不可行，可以调整目标值
4. 不要等到周期末才发现

### Q: 如何处理跨团队 OKRs？

**A**:
1. 明确一个主导团队
2. 其他团队设定支撑性的 OKRs
3. 建立定期同步机制
4. 共享成功和责任
