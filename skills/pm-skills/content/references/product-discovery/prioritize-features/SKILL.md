# 功能优先级排序

系统性地对产品功能进行优先级排序，帮助团队在资源有限的情况下做出正确的决策。

## 优先级框架概览

| 框架 | 适用场景 | 核心逻辑 |
|-----|---------|---------|
| ICE | 快速决策 | Impact × Confidence / Ease |
| RICE | 资源规划 | (Reach × Impact × Confidence) / Effort |
| MoSCoW | 范围定义 | Must / Should / Could / Won't |
| Kano | 用户满意度 | 基本/期望/兴奋 |
| WSJF | 敏捷团队 | Business Value / Job Size |
| Value vs Effort | 投资回报 | Value / Effort |
| Opportunity Score | 价值驱动 | Value × Desirability |

---

## ICE 框架

### 公式
```
ICE Score = (Impact × Confidence × Ease) / 100
```

### 评分标准

#### Impact (影响力): 1-10
| 分值 | 描述 |
|-----|------|
| 1 | 对指标无影响 |
| 3 | 轻微影响 |
| 6 | 中等影响 |
| 9 | 重大影响 |
| 10 | 变革性影响 |

#### Confidence (信心度): 1-10
| 分值 | 描述 |
|-----|------|
| 1 | 完全猜测 |
| 5 | 50% 把握 |
| 8 | 有一些数据支持 |
| 10 | 有明确数据支持 |

#### Ease (难易度): 1-10
| 分值 | 描述 |
|-----|------|
| 1 | 需要数月努力 |
| 5 | 需要数周努力 |
| 8 | 需要数天努力 |
| 10 | 几小时能完成 |

### ICE 评估表

```markdown
| 功能 | Impact | Confidence | Ease | ICE Score | 优先级 |
|-----|--------|-----------|-----|----------|-------|
| F1  | 8      | 7         | 5   | 28        | P1    |
| F2  | 6      | 9         | 3   | 18        | P2    |
| F3  | 9      | 5         | 6   | 22.5      | P2    |
```

## RICE 框架

### 公式
```
RICE Score = (Reach × Impact × Confidence) / Effort
```

### 评分标准

#### Reach (触达量): 用户数/季度
| 分值 | 描述 |
|-----|------|
| 100 | 影响100%用户 |
| 50 | 影响50%用户 |
| 10 | 影响10%用户 |
| 1 | 影响1%用户 |

#### Impact (影响力): 0.25-4
| 分值 | 描述 |
|-----|------|
| 4 | 4x 提升 |
| 2 | 2x 提升 |
| 1 | 1x 提升 |
| 0.5 | 0.5x 提升 |
| 0.25 | 0.25x 提升 |

#### Confidence (信心度): %
| 分值 | 描述 |
|-----|------|
| 100% | 充分数据支持 |
| 80% | 部分数据支持 |
| 50% | 基于假设 |

#### Effort (人力月): 人/月
| 分值 | 描述 |
|-----|------|
| 1 | 1人月 |
| 3 | 3人月 |
| 6 | 6人月 |
| 12 | 12人月 |

### RICE 评估表示例

```markdown
| 功能 | Reach | Impact | Confidence | Effort | RICE | 优先级 |
|-----|-------|--------|-----------|-------|------|-------|
| F1  | 1000  | 2      | 80%       | 2     | 800  | P0   |
| F2  | 500   | 3      | 70%       | 4     | 262.5| P1   |
| F3  | 2000  | 1      | 90%       | 3     | 600  | P0   |
```

## MoSCoW 框架

### 定义

| 类别 | 描述 | 比例建议 |
|-----|------|---------|
| **Must Have** (必须有) | 核心功能，没有产品不可用 | 60% |
| **Should Have** (应该有) | 重要功能，但不是致命缺失 | 20% |
| **Could Have** (可以有) | 增强功能，提升体验 | 15% |
| **Won't Have** (不会有) | 本次不做的功能 | 5% |

### 判定标准

#### Must Have
- ✅ 法律或合规要求
- ✅ 安全关键功能
- ✅ 没有则产品无法使用
- ✅ 用户明确表示必须有的

#### Should Have
- ⚠️ 显著提升用户体验
- ⚠️ 有替代方案但不理想
- ⚠️ 用户强烈期望

#### Could Have
- 💡 增强功能
- 💡 用户期望但非必需
- 💡 可以提升满意度

#### Won't Have
- ❌ 资源不足
- ❌ 战略优先级低
- ❌ 超出范围

## Kano 模型

### 功能类型

| 类型 | 描述 | 用户反应 |
|-----|------|---------|
| **基本型** | 没有会引起不满，有了也不会增加满意度 | "这是应该有的" |
| **期望型** | 越多越好，直接影响满意度 | "我期待这个功能" |
| **兴奋型** | 超出预期，带来惊喜 | "哇，没想到有这个" |

### 问卷设计

对每个功能问两个问题：

```
问题1: 如果有这个功能，你的感受是？
A. 我喜欢这样
B. 这样我无所谓
C. 这样我能接受
D. 这样我不太满意
E. 我不喜欢这样

问题2: 如果没有这个功能，你的感受是？
A. 我喜欢这样
B. 这样我无所谓
C. 这样我能接受
D. 这样我不太满意
E. 我不喜欢这样
```

### 结果解读

| 问题1 | 问题2 | 功能类型 |
|-------|-------|---------|
| 喜欢 | 不喜欢 | 兴奋型 |
| 喜欢 | 无所谓 | 期望型 |
| 无所谓 | 不喜欢 | 基本型 |
| 无所谓 | 无所谓 | 无差异型 |
| 不喜欢 | 喜欢 | 反向型 |

## Value vs Effort 矩阵

### 二维评估

```
                    价值
              高          低
          ┌─────────┬─────────┐
      高  │  ⭐ 做   │  🔄 计划 │
  努      │ (大收益) │ (成本高) │
 力       ├─────────┼─────────┤
      低  │  ✅ 做   │  ❌ 放   │
          │ (快速赢) │ (快速失) │
          └─────────┴─────────┘
```

### 评估标准

#### 价值维度 (1-10)
- 用户问题严重性
- 解决后用户收益
- 对北极星指标的贡献
- 竞争优势

#### 努力维度 (1-10)
- 开发复杂度
- 依赖关系
- 维护成本
- 资源需求

## 优先级维护

### 定期回顾
- **每周**: 检视紧急变更
- **每月**: 重新评估所有待定项
- **每季度**: 审视评估框架有效性

### 触发重新评估的情况
1. 战略方向重大调整
2. 新竞品/市场变化
3. 资源可用性变化
4. 用户反馈重大发现
5. 数据揭示新洞察

### 沟通原则
1. 透明: 让团队理解优先级逻辑
2. 解释: 说明为什么做/不做
3. 记录: 记录决策历史
4. 迭代: 接受不确定性，愿意调整
