## 核心设计原则

### 1. 结构优于装饰

信息依靠字号对比、字体差异、网格留白来区分层次，不依赖阴影、浮动卡片等装饰效果。保持界面干净、专业。

### 2. 克制优于炫技

动画和特效只在必要时使用，避免过度设计干扰信息传达。翻页动画简洁流畅，数据动画突出关键变化。

### 3. 主题色预设优先

从预定义的主题色中选择，而不是自由指定颜色。这确保了色彩搭配的专业性和视觉一致性。

### 4. 场景化内容结构

不同场景类型对应不同的内容逻辑框架，不是千篇一律的"封面-目录-内容-总结"模式。

### 5. 数据驱动决策

用具体数据说明成效，而非空洞的描述。数据可视化是展示成果的核心手段。

## 麦肯锡方法论：专业咨询PPT的设计哲学

> **"好的PPT不是展示你做了什么分析，而是帮助决策者做了什么决策。"**

作为专业的演示文稿生成器，本Skill遵循麦肯锡等顶级咨询公司的PPT设计方法论，确保生成的每一页都能有效传递信息、推动决策。

### 核心原则：金字塔原理

| 原则 | 含义 | 在PPT中的应用 |
|------|------|---------------|
| **结论先行** | 先说结论，再说支撑 | 每页顶部放核心观点/标题 |
| **MECE法则** | 相互独立、完全穷尽 | 分论点不重叠、不遗漏 |
| **以上统下** | 上层是下层的抽象 | 标题→支撑数据→详情 |

### 信息三层次设计

每一页PPT都应该包含三个层次的信息：

| 层次 | 位置 | 内容要求 | 示例 |
|------|------|----------|------|
| **标题层** | 页眉/大标题 | 核心观点（动宾短语） | "数据孤岛制约业务协同" |
| **支撑层** | 正文首行 | 关键论据（数据/事实） | "当前系统集成率仅35%" |
| **详情层** | 图表/列表 | 展开说明 | 系统清单、对接现状 |

**设计要点**：
- 领导可能只读标题就够做判断
- 执行层需要知道具体怎么做
- 内容一样，但叙事角度因受众而异

### 叙事结构设计

根据汇报目的选择合适的叙事结构：

| 结构类型 | 适用场景 | 框架逻辑 |
|----------|----------|----------|
| **问题-解决方案** | 汇报问题现状 | 痛点 → 根因 → 对策 |
| **现状-目标-路径** | 汇报规划 | 现在 → 目标 → 路线 |
| **对比-选择-论证** | 方案比选 | 选项 → 评估 → 建议 |
| **时间线结构** | 里程碑汇报 | 过去 → 现在 → 未来 |

### 受众差异化策略

| 受众层级 | 关注点 | PPT策略 |
|----------|--------|---------|
| **一把手** | 战略价值、ROI、风险 | 数据驱动、结论先行、减少细节 |
| **分管领导** | 实施方案、资源需求 | 详细路径、责任矩阵、预算分解 |
| **执行层** | 操作步骤、时间节点 | 详细流程图、任务清单、FAQ |

### 数据可视化规范

**图表选择决策树**：
```
需要展示什么？
├── 趋势 → 折线图/面积图
├── 构成 → 饼图/环形图
├── 比较 → 柱状图/条形图
├── 关系 → 散点图/气泡图
└── 流程 → 流程图/甘特图
```

**数据标注规范**：
- 数据标签放在柱/扇区内部或上方
- 坐标轴标明单位（如：万元、%）
- 图表右下角标注数据来源
- 一图一结论，不要混合多种信息

### 麦肯锡PPT的7条铁律

1. **一页一主题**：不要试图在一页上塞入太多信息
2. **标题即结论**：让读者扫一眼就明白这页在说什么
3. **用数据说话**：每一个观点都需要数据支撑
4. **图表优先**：能用图表就别用文字
5. **删到极致**：每一行字都要问"删掉行不行"
6. **对齐第一**：排版不整齐，其他都白费
7. **受众导向**：永远问"这个信息对这个受众有价值吗"

## 工作流程

本Skill采用**7步工作流程**，核心原则是**"先规划确认，后逐页生成"**：

```
步骤一：需求澄清（必须）→ 收集6个关键信息
步骤二：场景识别 → 确定内容框架模板
步骤三：内容规划 → 生成详细大纲
步骤四：用户确认大纲 → ⚠️ 必须确认后才能进入下一步
步骤五：逐页生成 → 每3-5页让用户确认一次
步骤六：自检与优化 → 对照检查清单
步骤七：交付与迭代 → 最终交付和调整
```

> **⚠️ 关键原则**：AI必须在用户确认内容大纲后才能开始生成页面。未确认就生成可能导致大量返工，浪费时间。

### 步骤一：需求澄清（必须）

生成PPT前，必须收集以下6个关键信息。缺少任何一项都会影响生成质量。

**1. 受众是谁**

明确PPT的阅读或演示对象。不同受众需要不同的表达方式和信息深度：

- 高管决策层：关注战略价值、投资回报、风险控制
- 业务部门：关注执行细节、操作流程、具体收益
- 技术团队：关注技术架构、实施路径、可行性分析
- 外部客户：关注产品价值、差异化优势、合作方式
- 评审专家：关注规范符合性、数据支撑、论证逻辑

**2. 分享时长多久**

时长决定PPT的页数和每页的信息密度：

- 5-10分钟：约5-8页，每页1个核心信息点
- 15-20分钟：约10-15页，可展开2-3个子点
- 30分钟以上：约20页以上，需要章节过渡页
- 45秒闪电版：3-5页，只展示最核心的1-3个要点

**3. 有没有原始素材**

提供可用的素材可以大幅提高生成效率：

- 文档资料：Word、PDF、Markdown等
- 数据表格：Excel、CSV等
- 旧版PPT：可提取结构和内容
- 文章链接：可提取关键信息
- 竞品资料：作为参考对比

**4. 有没有图片素材**

图片是PPT视觉的重要组成部分：

- 产品图片：用于产品展示页
- 数据截图：用于成果展示页
- 流程图/架构图：用于说明页面
- 图标资源：是否需要特定风格的图标
- 无图片：使用占位符或纯文字布局

**5. 想要使用哪套主题色**

从references/themes.md的6套预设主题色中选择：

- 墨水经典：通用默认，商业发布
- 政务庄重：政务汇报，官方场合
- 科技未来：科技产品，技术发布
- 教育清新：教育培训，知识分享
- 数据专业：数据分析，运营报告
- 创意艺术：创意展示，艺术呈现

**6. 有没有硬约束**

明确必须包含或必须避免的内容：

- 必须包含：特定数据、关键页面、公司名称等
- 不能出现：竞品名称、敏感信息、特定词汇等
- 格式要求：特定尺寸、必须导出PDF等
- 品牌规范：公司Logo位置、品牌色值等

## 步骤零：需求收集（确认关键信息）

> **重要提醒**：在开始制作PPT前，AI必须主动向用户确认以下关键信息。缺少任何一项都可能导致PPT不符合实际需求。

### 核心确认清单

| 类别 | 确认问题 | 为什么要问 |
|------|----------|------------|
| **汇报场景** | 这次汇报的目标是什么？（揭示问题/展示方案/申请预算/汇报进度） | 目标决定叙事结构和内容重点 |
| **汇报场合** | 是正式会议、项目评审还是日常沟通？ | 决定PPT的详细程度和风格 |
| **汇报时长** | 预计讲多长时间？（5分钟/15分钟/30分钟以上） | 决定页数和内容详略 |
| **听众分析** | 听众是谁？（一把手/分管领导/执行层/外部客户） | 受众决定表达方式和信息深度 |
| **核心主题** | PPT要解决什么核心问题？（一句话概括） | 确定PPT的主线和大纲 |
| **素材情况** | 有哪些现成素材可以提供？（文档/数据/旧版PPT） | 提高生成效率和质量 |
| **数据支撑** | 有哪些具体数据或案例可以提供？ | 数据支撑才能让PPT有说服力 |
| **设计偏好** | 倾向哪种风格？（麦肯锡商务/科技前沿/政务庄重） | 确定视觉风格和配色方案 |
| **硬约束** | 有没有页数限制、必须包含/排除的内容？ | 避免返工，确保交付符合要求 |

### 麦肯锡风格专项确认

如果用户选择"麦肯锡商务"风格，还需要额外确认：

| 确认项 | 问题示例 |
|--------|----------|
| **核心结论** | 你希望听众听完汇报后记住哪3个核心观点？ |
| **数据来源** | 关键数据是否有权威来源？（内部统计/第三方报告/行业基准） |
| **决策人** | 汇报结束后，听众需要做出什么决定或采取什么行动？ |
| **风险敏感度** | 听众对风险的接受程度如何？（激进型/稳健型/保守型） |

### 需求确认检查点

生成PPT前，AI必须确认以下检查点：

- [ ] 受众已明确（是谁、关心什么）
- [ ] 时长已确认（决定页数）
- [ ] 核心信息已收集（主题、数据、素材）
- [ ] 风格已选定（7套主题色选1套）
- [ ] 硬约束已记录（页数限制、必须包含/排除）

> **警告**：如果用户没有提供足够的确认信息，AI应该主动追问，而不是直接开始生成。否则可能导致返工，浪费双方时间。

### 需求追问机制

当用户提供的信息不完整时，AI应按以下优先级追问：

#### 第一优先级（必须追问）

| 缺失项 | 追问话术 |
|--------|----------|
| **受众不明** | "请问这个PPT主要是给谁看的？（一把手/分管领导/执行层/外部客户）" |
| **时长不明** | "预计汇报多长时间？（5分钟/15分钟/30分钟以上）" |
| **主题模糊** | "这个PPT的核心主题是什么？（比如：汇报进展/申请预算/展示方案）" |

#### 第二优先级（建议追问）

| 缺失项 | 追问话术 |
|--------|----------|
| **数据缺失** | "有哪些具体数据可以支撑？（如：效率提升百分比、成本节省金额）" |
| **风格不明** | "倾向哪种视觉风格？（商务麦肯锡/科技前沿/政务庄重/清新教育）" |
| **页数限制** | "对页数有限制吗？（通常10-20页为佳）" |

#### 第三优先级（可选追问）

| 缺失项 | 追问话术 |
|--------|----------|
| **素材情况** | "有没有现成的文档、数据报表或旧版PPT可以提供？" |
| **硬约束** | "有没有必须包含或必须排除的内容？" |

### 分步追问策略

**策略一：假设合理默认值**
对于非关键信息，可以先假设合理默认值，待生成后再确认。

```
场景：用户只说"做一个数据中台的PPT"
假设默认值：受众=分管领导（技术线）、时长=15分钟、风格=商务麦肯锡
回复：好的，我先按"15分钟、麦肯锡风格、向技术分管领导汇报"来生成，
      如果不符合请告诉我调整。
```

**策略二：快速二选一**
对于模糊选择，提供二选一选项让用户快速确认。

```
场景：用户说"做一个汇报PPT"
追问："好的！请问是：
  A. 向领导汇报工作进展（偏商务汇报）
  B. 申请项目预算（偏项目提案）
请选择或描述您的具体场景。"
```

**策略三：补充式追问**
先接受用户已提供的信息，再逐步补充缺失项。

```
场景：用户说"做一个15分钟的汇报，受众是领导"
追问（接受已知）：好的，15分钟、面向领导。
追问（补充未知）：还需要确认：
  1. 汇报目标是什么？（揭示问题/展示方案/申请预算）
  2. 有哪些数据可以支撑？
  3. 倾向什么风格？（麦肯锡/科技/政务）
```

### 常见场景的快速确认

| 场景 | 快速确认问题 |
|------|-------------|
| 政务汇报 | "是向领导汇报进展还是项目评审？" |
| 商务汇报 | "本次汇报是季度总结还是年度总结？" |
| 项目提案 | "汇报后希望听众做出什么决定？" |
| 产品发布 | "是内部发布还是对外宣传？" |
| 麦肯锡风格 | "希望听众记住哪3个核心观点？" |

### 追问底线规则

> **AI必须在收到至少以下3项信息后才能开始生成**：
> 1. 受众（至少知道是一把手/分管领导/执行层）
> 2. 时长（至少知道是5分钟/15分钟/30分钟）
> 3. 核心主题（至少知道要做什么主题）
>
> **缺少以上任意一项，AI必须追问，不得跳过。**

### 政务汇报场景化设计原则（专项）

政务信息化汇报应按**具体场景类型**组织内容，不同场景有特定的内容逻辑框架，并按需参考麦肯锡方法论。

#### 政务信息化汇报6大场景

| 场景类型 | 汇报目标 | 麦肯锡方法应用 | 核心内容框架 |
|----------|----------|----------------|--------------|
| **项目立项汇报** | 申请立项/预算 | 结论先行、MECE分类 | 问题诊断→解决方案→ROI分析 |
| **可行性分析** | 论证项目可行 | 数据驱动、对比论证 | 多方案比选→推荐方案→风险评估 |
| **进度汇报** | 展示阶段性成果 | 量化指标、数据可视化 | KPI仪表盘→里程碑完成率→下阶段计划 |
| **成果汇报** | 展示建设成效 | 以上统下、对比论证 | 前后对比→量化指标→效益分析 |
| **方案评审** | 技术方案论证 | 逻辑树、架构图 | 五横三纵架构→技术选型→评审要点 |
| **年度总结** | 全面工作总结 | 执行摘要、分类汇总 | 时间线→分类统计→经验总结 |

#### 场景一：项目立项汇报

**目标**：向领导申请项目立项和预算

**麦肯锡方法应用**：
- **结论先行**：封面即核心结论，如"投资2800万，18个月回本"
- **MECE分类**：问题不重叠、不遗漏
- **数据驱动**：每个观点都有数据支撑

**推荐页面结构**（约15-20页，20-30分钟）：
```
1. 封面（结论先行）
   └── "投资[XX]万，实现[XX]%效率提升，[X]年回本"

2. 执行摘要（4个核心结论）
   ├── 问题1：[数据] → 影响
   ├── 问题2：[数据] → 影响
   ├── 问题3：[数据] → 影响
   └── 建议：投入[XX]万，预期[XX]收益

3. 问题诊断（每个痛点1页）
   ├── 痛点：系统孤岛 → 数据：集成率仅35%
   ├── 痛点：效率低下 → 数据：人工操作占比60%
   └── 痛点：决策滞后 → 数据：报表周期14天

4. 解决方案概述
   └── 一句话方案：构建统一[XX]平台

5. 实施路径（3阶段）
   ├── 阶段一：基础夯实
   ├── 阶段二：能力提升
   └── 阶段三：优化迭代

6. ROI分析（数据可视化）
   ├── 投入：[XX]万
   ├── 年度节省：[XX]万
   └── 投资回收期：[X]年

7. 风险与对策
   ├── 风险1 → 对策
   ├── 风险2 → 对策
   └── 风险3 → 对策

8. 行动计划
   └── 4项关键行动
```

**麦肯锡铁律应用**：
- 标题即结论："系统孤岛导致集成率仅35%"
- 用数据说话：每个痛点配具体数字
- 一页一主题：不混搭问题

---

#### 场景二：可行性分析

**目标**：论证项目实施方案的可行性

**麦肯锡方法应用**：
- **对比论证**：多方案并列比选
- **数据驱动**：技术指标量化对比
- **逻辑树**：问题拆解到最小单元

**推荐页面结构**（约12-15页，15-20分钟）：
```
1. 封面（项目名称 + 可行性分析）

2. 执行摘要
   ├── 方案A：单体架构（成本低/扩展差）
   ├── 方案B：微服务架构（成本高/扩展强）
   └── 推荐：方案B（综合最优）

3. 需求分析
   └── 业务需求 → 技术需求（逻辑树拆解）

4. 方案对比（核心页面）
   └── 4个维度对比：A vs B vs C

5. 技术可行性
   ├── 技术成熟度
   ├── 人才储备
   └── 生态支持

6. 经济可行性
   ├── 成本估算
   ├── 收益预测
   └── ROI分析

7. 风险评估
   ├── 风险识别
   └── 应对措施

8. 结论与建议
   └── 推荐方案 + 前提条件
```

**图表选择**：
- 方案对比 → 雷达图/对比表格
- 成本分析 → 堆叠柱状图
- 风险评估 → 矩阵图

---

#### 场景三：进度汇报

**目标**：展示项目阶段性建设成果

**麦肯锡方法应用**：
- **量化指标**：KPI完成率清晰展示
- **数据可视化**：图表替代文字
- **结论先行**：开场即关键进展

**推荐页面结构**（约10-12页，15分钟）：
```
1. 封面（项目名称 + 汇报周期）

2. 执行摘要（3个关键进展）
   ├── 进度：已完成[XX]%，超计划[XX]%
   ├── 质量：测试通过率[XX]%
   └── 成本：预算执行率[XX]%

3. KPI仪表盘（核心页面）
   ├── 进度指标：甘特图
   ├── 质量指标：饼图/环形图
   └── 成本指标：折线图

4. 本周期完成工作
   └── 完成清单 + 关键里程碑

5. 亮点成果展示
   ├── 创新亮点1
   ├── 创新亮点2
   └── 创新亮点3

6. 问题与风险
   ├── 已识别风险 → 应对措施
   └── 遗留问题 → 解决方案

7. 下阶段计划
   └── 里程碑预览 + 关键行动
```

**数据可视化要点**：
- 进度完成率 → 环形进度图
- 多维度KPI → 仪表盘布局
- 趋势变化 → 折线图

#### 场景四：成果汇报

**目标**：展示项目建设取得的成效

**麦肯锡方法应用**：
- **以上统下**：成效总览→分类成效→案例详情
- **对比论证**：建设前 vs 建设后
- **数据驱动**：量化指标说明成效

**推荐页面结构**（约12-15页，20分钟）：
```
1. 封面（项目名称 + 建设成效）

2. 执行摘要（核心成效）
   ├── 服务效率提升：[XX]%
   ├── 数据共享交换：[XX]万条
   └── 群众满意度：[XX]分

3. 建设成效总览
   └── 一句话概括：实现了[XX]目标

4. 分类成效展示
   ├── 成效1：[数据] → 说明
   ├── 成效2：[数据] → 说明
   └── 成效3：[数据] → 说明

5. 前后对比（核心页面）
   ├── 指标A：建设前[XX] → 建设后[XX]
   ├── 指标B：建设前[XX] → 建设后[XX]
   └── 指标C：建设前[XX] → 建设后[XX]

6. 典型案例
   └── 案例1：应用场景 → 效果数据

7. 创新亮点
   ├── 亮点1：[创新内容] → [成效]
   └── 亮点2：[创新内容] → [成效]

8. 经验总结
   └── 3条可复制经验
```

**对比图表选择**：
- 单指标前后对比 → 前后柱状图
- 多指标对比 → 雷达图
- 时间序列变化 → 折线图

#### 场景五：方案评审

**目标**：向评审专家展示技术方案

**麦肯锡方法应用**：
- **逻辑树**：架构分层清晰
- **架构图**：五横三纵结构可视化
- **专业规范**：符合评审标准

**推荐页面结构**（约20-25页，30分钟）：
```
1. 封面（方案名称 + 评审类型）

2. 目录（汇报提纲）

3. 项目概述
   ├── 建设背景
   ├── 需求分析
   └── 建设目标

4. 总体架构（核心页面）
   └── 五横三纵架构图

5. 技术架构
   ├── 基础设施层
   ├── 数据层
   ├── 支撑层
   ├── 应用层
   └── 交互层

6. 技术路线
   ├── 技术选型依据
   └── 技术指标对比

7. 安全体系
   ├── 安全架构
   ├── 等保设计
   └── 隐私保护

8. 建设内容
   ├── 分层建设内容
   └── 重点功能模块

9. 实施计划
   ├── 阶段划分
   └── 里程碑节点

10. 投资预算
    ├── 投资估算
    └── 资金来源

11. 风险评估
    ├── 风险识别
    └── 应对措施

12. 结论与建议

13. 专家问答
```

**架构图选择指南**：
| 汇报类型 | 推荐架构 | 核心要素 |
|----------|----------|----------|
| 全面汇报 | 五横三纵 | 五层横向 + 三纵贯穿 |
| 业务梳理 | 业务架构 | 业务域 + 业务能力 |
| 数据相关 | 数据架构 | 数据源 + 中台 + 应用 |
| 技术评审 | 技术架构 | 基础设施 + 中间件 |

**麦肯锡方法应用**：

#### 政务汇报通用设计原则

| 原则 | 说明 | 设计要点 |
|------|------|----------|
| **严肃性** | 政府机构视觉表现为庄严神圣 | 减少干扰元素，色调与政府网站一致 |
| **简约性** | "简约而不简单"，兼顾严肃与大气 | 留白充足，层次分明 |
| **数据驱动** | 以图表为主，直观展示成效 | 万字汇报不如5页图表 |
| **结论先行** | 每页顶部放核心观点 | 领导扫一眼就理解 |
| **一页一主题** | 不在一页上塞入太多信息 | 聚焦一个核心信息点 |

> **重要提醒**：政务汇报应简洁有力，避免冗余。每页聚焦一个核心信息，麦肯锡方法论按需应用，不要教条化。

### 步骤二：场景识别与内容框架

#### 用户确认机制

**每批次确认内容**：

| 确认项 | 检查重点 |
|-------|---------|
| **内容准确性** | 数据是否正确、逻辑是否通顺 |
| **结构合理性** | 信息层级是否清晰、重点是否突出 |
| **视觉风格** | 配色是否合适、布局是否美观 |
| **技术正确性** | HTML代码是否有错误、类名是否正确 |

**用户反馈处理**：

| 用户反馈 | AI处理方式 |
|---------|-----------|
| 满意，继续 | 进入下一批次生成 |
| 微调 | 调整指定页面的内容/样式 |
| 较大幅度修改 | 调整当前章节，重新生成 |
| 大幅修改 | 暂停，评估是否需要调整大纲 |

#### AI应用深度差异说明

**全流程AI应用**的特点：
- AI作为业务主流程的核心驱动
- 从输入到输出全程自动化
- 适合流程标准化、决策规则明确的场景
- 汇报重点：端到端效果、自动化程度、人机协同

**部分业务AI应用**的特点：
- AI作为人工辅助工具
- 仅在特定环节提供AI能力
- 适合流程复杂、部分环节可自动化的场景
- 汇报重点：局部提效、精准度提升、人机协作方式

**数据层面AI应用**的特点：
- AI作用于数据工作本身
- 不直接改变业务流程
- 适合数据量大、分析需求强的场景
- 汇报重点：数据治理效果、分析准确性、决策支撑能力

## 常见错误与解决方案

### 错误一：类名不匹配

**现象**：布局样式全部丢失，大标题变成默认字体，数据卡片样式异常。

**原因**：layouts.md中的类名在template.html中没有定义。

**解决**：确保template.html被正确复制到项目目录，所有类名来自template.html中已定义的样式。

### 错误二：图片路径错误

**现象**：图片无法显示，显示破图图标或空白。

**原因**：图片路径不存在或URL无法访问。

**解决**：使用正确的相对路径或绝对URL，确保图片文件存在于指定位置。

### 错误三：字体加载失败

**现象**：标题显示为系统默认字体，视觉风格不统一。

**原因**：Google Fonts等外部字体CDN无法访问。

**解决**：确保网络环境正常，或使用本地字体文件作为备选。

### 错误四：响应式布局异常

**现象**：在移动端或平板上布局错乱，内容溢出或被遮挡。

**原因**：响应式断点设置不当，或使用了固定像素值。

**解决**：使用相对单位（vw/vh/em/rem）而非固定像素值，确保各断点下布局正常。

### 错误五：动画效果过载

**现象**：动画过于花哨，干扰信息传达，观众注意力被分散。

**原因**：每页都添加了复杂动画，缺少节奏感。

**解决**：只在关键页面使用动画，保持大部分页面简洁静态，形成张弛有度的节奏。

## 质量标准

本Skill生成的HTML PPT应满足以下质量标准：

### 内容质量

- 信息完整：涵盖用户要求的所有核心内容
- 逻辑清晰：结构层次分明，逻辑关系明确
- 数据支撑：用具体数据说明成效，避免空洞描述
- 重点突出：核心信息醒目，次要信息辅助

### 视觉质量

- 风格统一：整体视觉风格一致，无突兀元素
- 层次分明：字号、颜色、间距形成清晰层次
- 留白适当：内容与留白比例适当，呼吸感强
- 对齐精确：元素对齐规范，无明显偏差

### 技术质量

- 代码规范：HTML语义化，CSS变量化，结构清晰
- 性能优良：文件体积适中，加载速度快
- 兼容性良好：主流浏览器显示正常
- 响应式适配：不同设备均有良好体验

### 交互质量

- 翻页流畅：动画平滑，无卡顿感
- 导航清晰：页码、进度指示明确
- 键盘支持：支持键盘翻页操作
- 触摸友好：移动端触摸滑动流畅

### 麦肯锡7条铁律速查

1. **一页一主题**：不塞入太多信息
2. **标题即结论**：扫一眼就理解
3. **用数据说话**：每个观点配数字
4. **图表优先**：能用图表就别用文字
5. **删到极致**：每一行问"删掉行不行"
6. **对齐第一**：排版不整齐都白费
7. **受众导向**：问"这个信息对受众有价值吗"
