# 手拍照纸质文档批量处理

把一批"手机拍的多页纸质表单"变成一批命名规范的 PDF：
裁掉桌面背景 → 手写签名只留姓氏 → 按份合并 → 按 `姓氏_文档名_序号` 命名。

## 三条质量口径（用户已确认，不要提高标准）

1. **签名认不出就标大概，不要死磕。** 草书容易混（谭/覃、己/已/巳）。
   读不准时在交付说明里写"疑似 X"，不要反复放大、反复追问。
   更快的路径是直接问用户要姓氏——研究类表单通常用户自己知道。
2. **裁切只需"看不到桌面 + 文字完整"。** 不做透视矫正，不追打印机扫描品质。
   轴对齐矩形 + 2% 内缩两步就够。纸在照片里是斜的、边不齐，视为可接受。
3. **黑条宽松即可。** 目标是完全盖住名字，遮住一点姓氏边缘无妨。
   宁可左边界往左多留 2%，也不要反复测量笔画位置。调两轮还不对就直接问用户。
4. **姓氏拿不准就问，不要自己定。** 手写签名读不准时，一次性列出所有
   存疑的 key 和候选姓氏让用户确认，再继续执行。签字有法律效力，
   这项不该 agent 拿主意（用户 2026-10-10 明确要求）。

## Inputs to collect

开工前只确认这几项，其余从上下文推断：

- **照片目录**：源文件路径
- **分页规则**：每张照片拍了几页、页面顺序（如"从左到右"）
- **命名规则**：输出文件名模式（如 `簇X_X号_第一面`）
- **姓氏清单**：每份文件签名者的姓。**优先直接问用户**，比读图快得多
- **模板是否复用**：同一批表单版式相同时，签名 ROI 只测一次

版式完全一致时，把上一次的 `config.json` 复制过来改文件名即可，不要重新测量。

## 命名规则（方案二）

分组键和文件名里的编号一律用**项目编号（Booking Code）**，不要自造"簇一/簇二"这类标签。

```
{姓氏}_知情同意书_{BookingCode}.pdf
{姓氏}_支付凭证[_流水号].pdf        # 支付凭证保持原文件名
```

同一 Booking Code 内多人撞名时加序号后缀 `(2) (3)`，按用户给的编号升序排列，
保证顺序稳定可复现。例：

```
26CB077/知情同意书/王_知情同意书_26CB077.pdf
26CB077/知情同意书/谭_知情同意书_26CB077.pdf
26CB077/知情同意书/谭_知情同意书_26CB077(2).pdf
```

**Booking Code 是关联主键**：同意书右上角 `Internal Booking Code`、
支付凭证右下角客户摘要，两边 OCR 出来对上即归为一组，跨批次也通用。
金额和日期不可靠（多人金额相同、同日多笔），只能做旁证。

## Procedure

1. **读配置**：复制 `references/config-example.json` 到工作目录，按实际照片改
   `src_root` / `photo` / `pages` / `mask`。字段含义见 `references/config-example.md`。

2. **首次遇新模板：测签名 ROI**
   裁切前先出 1 张缩略预览，人工读出签名在页面内的相对位置（归一化 0~1），
   写成 `[y0, y1, x0, x1]`。同一版式复用。测量只做一次，不要逐张微调。

3. **跑裁切打码**：
   ```bash
   python3 scripts/process.py config.json ./out
   ```
   产出 `out/crops/`（裁切图 + `*_masked.jpg` 打码图）。
   PDF 合并用 key 作文件名（`簇一_1号.pdf`），重命名留到打包那步做。

4. **OCR 项目编号**：
   ```bash
   python3 scripts/ocr_booking.py ./out/crops -o codes.json
   ```
   输出 `{page_key: "26CB077"}`。支付凭证上的编号要放大后 OCR，脚本内置该处理。

5. **确认姓氏**：从手写签名读，读不准的**一次性列全问用户**，拿到答复写
   `surnames.json`（`{page_key: 姓}`）。不要逐个追问，也不要自行拍板。

6. **按 Booking Code 打包**：
   ```bash
   python3 scripts/package.py \
     --pdf-dir ./final --codes codes.json --surnames surnames.json --sort sort_key.json \
     --vouchers ./支付凭证目录 --voucher-codes vcodes.json \
     -o out.zip
   ```
   每个 code 一个目录，内含 `知情同意书/` 与 `支付凭证/` 两个子目录。

## Output contract

- 交付包：`<BookingCode>/知情同意书/*.pdf` + `<BookingCode>/支付凭证/*.pdf`
- 回复中给出「Booking Code ↔ 份数 ↔ 姓氏」对照表，并列出向用户确认过的存疑项

## Failure handling

- **某张照片检出页数与配置不符**：脚本会打印告警并按配置截取。
  核对照片是否漏页/多页，向用户确认后再重跑，不要自行猜测。
- **边缘还露出桌面**：把 `inset` 调到 0.03。斜得厉害、内缩吃不掉时，
  直接告知用户"这页角落有桌面残留"，让他自行框选，别自己加图像处理。
- **PDF 合并缺依赖**：`pip install img2pdf pypdf opencv-python-headless pillow`（建议用国内镜像）。
- **Booking Code OCR 失败**：脚本会列在 `failed` 里；裁一张该页右上角确认实际位置，
  调 `ocr_booking.py` 的 `box` 参数。同一版式只需调一次。
- **支付凭证编号识别不出**：优先跑一次 `--voucher-codes` 手工映射（放大 OCR 对
  机器打印的小字不稳），不要反复调参数。
- **模板变化大**：说明重测 ROI 的成本，问用户是否值得继续自动化。

## Examples

用户给了 10 张知情同意书照片 + 13 张支付凭证照片，要求裁切、签名只留姓氏、
按项目编号归类打包。用户只提供了编号，姓氏由 agent 读签名，读不准的**问用户确认**。

- OCR 出三个项目：26CB077（6 人）、26CB060（6 人）、26CB070（1 人）
- 问用户确认存疑姓氏后得到：王×2、谭×2、陈×3、林×3、张×3
- 输出 26 个 PDF，按 Booking Code 分三个目录，同 code 内撞名加 `(2)(3)`
- 交付时说明："谭/陈 的 signature 最初读作'覃/陈'，已按你确认的结果写入"

详细配置字段见 `references/config-example.md`。
