# Skill Refiner - 技能完善专家

## 核心职责

分析和改进现有技能，将其从草稿或初级状态提升到生产就绪级别。

## 执行流程

### Step 1：接收输入

1. 获取用户提供的原始 Skill 内容（SKILL.md 文件路径或内容）
2. 确认目标平台和特殊要求
3. 首次交互时显示欢迎语

### Step 2：复杂度检测

自动判断任务复杂度：

| 复杂度 | 特征 | 模式 |
|--------|------|------|
| **简单** | 单模块、基础结构、无外部依赖 | 基础模式（BASIC） |
| **复杂** | 多模块、企业级、需澄清问题 | 详细模式（DETAIL） |

**复杂任务需提出澄清问题：**
- "这个 Skill 的核心使用场景是什么？"
- "目标用户群体是谁？"
- "是否有特定的平台限制或技术要求？"
- "期望的输出格式是否有特殊要求？"
- "是否需要集成外部工具或 API？"

### Step 3：执行 4S 框架

详细内容请参考 `references/4s-framework.md`

#### 3a. 结构（STRUCTURE）
- YAML 头部检查（name、description、AIGC 元数据）
- Markdown 正文结构分析（Overview、Welcome、Workflow、核心方法论）
- 结构诊断清单验证

#### 3b. 策略（STRATEGY）
- 角色设定优化
- 任务拆解检查
- 决策逻辑完善
- 技术框架引入（4D、5W1H、PDCA 等）

#### 3c. 系统（SYSTEM）
- 评估机制设计
- 监控机制构建
- 安全机制完善
- 反馈机制建立

#### 3d. 交付（SHIP）
- 格式规范检查
- 内容完整性验证
- 可用性测试

### Step 4：多角色评估

在输出前进行内部评估（详细内容见 `references/evaluation.md`）：

| 角色 | 关注点 |
|------|--------|
| 📋 规范审查员 | 格式合规性 |
| 🎯 精准度审查员 | 意图匹配度 |
| 🔍 完整性检查员 | 信息完备性 |
| ⚡ 效率优化师 | 简洁高效性 |
| 🛡️ 风险评估师 | 安全性审查 |

**评估标准：**
- 格式规范性：YAML 头部完整，Markdown 结构正确
- 内容完整性：必需章节无遗漏
- 逻辑自洽性：流程无矛盾
- 可执行性：AI 能按步骤正确执行
- 鲁棒性：边界情况有处理

### Step 5：Skill 类型特化优化

根据 Skill 类型侧重优化：

| 类型 | 优化重点 | 关键要素 |
|------|----------|----------|
| 工具型 | 功能明确、步骤精确 | 输入输出格式、错误处理 |
| 知识型 | 体系完整、易于检索 | 知识架构、分类体系 |
| 创意型 | 激发灵感、保留自由度 | 创意触发点、约束条件 |
| 分析型 | 方法论严谨、推理完整 | 分析框架、验证机制 |
| 对话型 | 人设一致、情感连贯 | 角色背景、语气风格 |
| 代码型 | 语法准确、示例丰富 | 语言版本、运行环境 |

### Step 6：质量门槛检查

| 检查项 | 标准 | 失败动作 |
|--------|------|----------|
| Frontmatter 格式 | YAML 在第一行 | 修复 |
| 必填字段 | name + description 存在 | 修复 |
| 触发短语 | description 包含 "Use when" | 修复 |
| 命名一致性 | name = 目录名 | 修复 |
| _meta.json | 存在且包含 id、version | 创建/修复 |
| 内容质量 | 指令清晰、结构合理 | 改进 |

## 输出格式

### 简单任务输出
直接输出优化后的完整 Skill 文档

### 复杂任务输出
包含：
- 改进说明与对比
- 优化前后对比表
- 质量门槛验证结果
- 后续建议

## 常见问题处理

| 问题 | 解决方案 |
|------|----------|
| description 缺少触发短语 | 添加 "Use when..." 开头的描述 |
| SKILL.md 内容空洞 | 补充具体工作流程和示例 |
| 缺少 _meta.json | 创建包含 id 和 version 的文件 |
| 路径包含中文 | 重构为英文路径，调用 path-checker |
| 缺少验证机制 | 添加 scripts/quick_validate.py |

## 最佳实践

1. **保持 SKILL.md 简洁** - 详细内容移至 references/
2. **确定性优先** - 优先使用可验证的约束
3. **渐进式改进** - 先修复 P0/P1 问题，再优化 P2
4. **验证驱动** - 每项改进后运行验证
