# Security Architecture Xml

## 总览

将安全架构、平台架构、组件架构相关的文字说明或方案文档，转换为两类输出：

1. 可直接导入 draw.io / diagrams.net 的 `mxGraphModel` XML。
2. 与图一致的一段中文“设计图描述”。

优先服务于以下场景：
- 安全服务总体架构图
- 安全平台逻辑架构图
- 安全组件/产品架构图
- 招投标方案中的总体架构、逻辑架构、产品架构配图

固定风格：**灰底、黑框、圆角、横向分层、分组容器 + 小矩形能力块**。

## 工作流

### 1. 读取输入

先判断输入来源：

- **纯文字架构描述**：直接提取层、能力、模块、接口、数据流、底座。
- **上传的 `.docx` 文件**：先读取文档内容，再抽取与架构有关的章节。

处理 `.docx` 时，优先关注这些标题或相近标题：
- 总体架构
- 总体架构设计
- 逻辑架构
- 产品架构
- 平台概述
- 设计定位
- 核心能力
- 主要功能
- 部署架构

忽略以下内容，除非它们明确影响模块划分：
- 大段营销表述
- 泛化的优势描述
- 纯性能指标
- 无法映射成图形元素的宣传语

如果一个文档里包含多套架构：
- 优先采用用户明确点名的那一套。
- 如果用户没点名，优先采用最完整、最中心、最像“总体/逻辑/产品架构”的那一章。

### 2. 提炼成图形语言

先把原文内容归一为以下图形元素：

- **层**：图中的横向大容器。
- **能力域/平台域**：层内的大分组框。
- **模块/功能点**：层内的小白色矩形。
- **联动/接口/协同**：底部“开放联动”层，或独立的小模块。
- **基础底座/部署底座**：最底层容器。

只保留能够支撑图结构的内容，不要把原文里的所有句子都塞进图里。

### 3. 确定图类型

优先匹配以下三类结构：

#### A. 总体安全服务架构图
适用于“总体架构设计”“安全服务总体架构”等内容。

默认分层顺序：
1. 应用场景 / 服务对象
2. 平台建设 / 统一管理
3. 核心能力层
4. 智能分析与运营支撑层
5. 数据与基础底座层

当文档中明确出现“统一管理平面”“联动机制”“策略编排”等内容时，可以单独加一个横向管理层。

#### B. 平台逻辑架构图
适用于“业务组综合安全平台”“逻辑架构规划”“平台逻辑架构”等内容。

默认分层顺序：
1. 应用场景
2. 展示交互层
3. 业务应用层
4. 分析计算层
5. 数据汇聚层
6. 设备接入层
7. 开放联动与平台底座

如果文档本身只给出五层或六层，则以原文为准，不强行补层。

#### C. 组件 / 产品架构图
适用于 WAF、NGFW、主机安全、审计平台等单一组件或产品说明。

默认分层顺序：
1. 部署/接入层
2. 核心引擎层
3. 策略执行/控制层
4. 管理控制层
5. 开放接口/联动层
6. 部署模式/底座补充层（仅在需要时）

### 4. 模块抽象规则

遵循以下抽象规则：

- 每层建议放 **3–6** 个主框。
- 每个主框建议放 **2–4** 个小模块。
- 同一层不要出现过多长句，优先使用短语。
- 模块名称尽量采用“名词 + 能力”或“动词 + 对象”的方式，例如：
  - 数据汇聚
  - 告警关联
  - 策略下发
  - 审计留痕
  - 智能体编排
  - 模型训练调优

如果原文信息不足，允许使用中性的结构化名称，但不能凭空虚构具体产品能力。

可安全使用的中性名称包括：
- 数据接入
- 数据清洗
- 归一化
- 分析计算
- 业务应用
- 展示交互
- 开放联动
- 平台底座
- 统一管理

### 5. XML 生成规则

输出的 XML 必须：

- 使用 `mxGraphModel` 根节点。
- 结构必须可直接导入 draw.io / diagrams.net。
- 使用唯一 `id`。
- 保持层级清晰，避免坐标重叠。
- `value` 中需要换行时使用 `&lt;br/&gt;`。
- 样式固定为本技能的单色风格，不要改成彩色技术风。

## 固定样式规范

严格遵循 `references/style-guide.md`。

核心规范如下：

- 外层背景：灰底，黑边。
- 标题：居中、加粗、较大字号。
- 各层：圆角大容器，浅灰背景，黑色边框。
- 层内分组：比层容器略深或略浅的灰底，黑边。
- 具体模块：白底黑边的小矩形。
- 整体版式：**横向分层、自上而下展开**。
- 除非用户明确要求展示关系箭头，否则以“层次布局”表达关系，不强依赖连线。

## 输出格式

默认输出两部分，必要时再补“分层说明”。

### 第一部分：XML代码

必须使用如下形式：

```xml
<mxGraphModel ...>
  ...
</mxGraphModel>
```

要求：
- 只输出完整 XML。
- 不输出伪代码。
- 不省略根节点。
- 不用 `...` 代替真实节点。

### 第二部分：设计图描述

输出一段与图完全对应的中文描述，通常 1 段即可。

描述要覆盖：
- 平台/系统定位
- 分层结构
- 每层的主要职责
- 关键联动关系或闭环关系
- 最终形成的整体价值

语言风格：
- 正式
- 方案化
- 适合直接写入投标书、设计说明或图下图注

### 可选第三部分：分层说明

仅在以下场景附带：
- 用户明确要求“先给我分层思路再出图”
- 文档包含多套候选架构，需要说明选型
- 图结构存在明显抽象取舍，需要给用户核对

## 设计图描述写法

采用“定位 + 分层 + 闭环”的写法。

推荐句式：

- “本图展示了……的整体逻辑架构。”
- “整体采用自上而下的分层设计，包括……层。”
- “其中，……层负责……；……层负责……；……层负责……”
- “平台通过……实现……，形成……的闭环体系。”

不要写成纯功能清单，也不要写成过长的宣传文案。

## 准确性约束

- 不要发明文档没有支持的具体模块。
- 不要把营销术语直接当作图层名称，除非其在原文中承担明确的架构角色。
- 如果原文存在多种可抽象方式，优先选择：
  - 层次更清晰的
  - 更适合横向分层展示的
  - 更接近用户当前图风格的
- 如果信息明显不足以稳定成图，先输出保守结构，不做花哨扩展。
