# Tooling Module

Three tooling modes attach external capabilities to an agent. Each agent has at most one `tooling:` block (a single object, not a list) — combine tools by listing entries within that one block.

## Three modes

### `function` — in-repo Python tools

```yaml
config:
  tooling:
    type: function
    functions:
      - file:All           # bulk import all functions from file.py
      - web:fetch_url      # specific entry from web.py
      - code_executor:All
```

The `module:All` shorthand is the dominant style in production workflows. It imports every function in that module file. Pickers sort `module:All` entries ahead of concrete entries.

### `mcp_remote` — HTTP MCP server

```yaml
config:
  tooling:
    type: mcp_remote
    server: https://my-mcp.example.com/sse
    headers:
      Authorization: "Bearer ${MCP_TOKEN}"
    timeout: 30
```

### `mcp_local` — stdio MCP process

```yaml
config:
  tooling:
    type: mcp_local
    command: uvx                       # the de-facto launcher convention
    args: [my-mcp-server, --flag]
    cwd: ${WORKSPACE}                  # session workspace; runtime-injected
    env:
      LOG_LEVEL: info
    inherit_env: true                  # inherit parent process env (default true)
    wait_for_log: "Server ready"       # readiness gate; engine waits for this string in stdout
    startup_timeout: 30                # seconds to wait for wait_for_log
```

`uvx <package>` is the de-facto launcher pattern (UV's package runner). The engine starts the process, waits for `wait_for_log`, and then bridges the agent to the MCP server's stdio.

## Function tooling: `_context` injection

Function-mode tools can declare a `_context` parameter to receive a runtime-injected object:

```python
def my_tool(query: str, _context: dict) -> str:
    workspace = _context["python_workspace_root"]
    store = _context["attachment_store"]
    graph_dir = _context["graph_directory"]
    # ...
```

The `_context` object provides:

- `attachment_store` — the session's attachment store; use `register_file()` to promote files to artifacts.
- `python_workspace_root` — same directory as the python node's working directory; same as `${WORKSPACE}`.
- `graph_directory` — the directory of the workflow YAML; useful for resolving relative paths.

## Built-in function modules

Common modules in the in-repo catalog (names may vary by deployment):

| Module | Functions |
|---|---|
| `file:All` | Read/write/list files in `code_workspace/` |
| `web:All` | HTTP fetch, search, page parsing |
| `code_executor:All` | Run Python/shell code in sandbox |
| `uv_related:All` | UV package management |
| `user:All` | Prompt the user mid-execution |
| `weather:All` | Weather lookups |
| `video:All` | Video processing |
| `utils:All` | General helpers |
| `deep_research:All` | Multi-step research workflows |

The exact catalog is generated at runtime from `functions/function_calling/` — use `--inspect-schema` against `FunctionToolEntryConfig` to see the live enum.

## Security notes

- Function tools run in-process. They have access to whatever the parent Python process has.
- `mcp_local` processes inherit the workflow's environment unless `inherit_env: false`. Audit `env:` carefully when secrets are involved.
- `mcp_remote` headers can carry secrets; use `${VAR}` references rather than inlining.
- The `code_executor` family runs untrusted code generated by agents — typical practice is to constrain it to `code_workspace/` and trust the sandbox boundary, but production deployments should verify.

## Common bugs

- `tooling:` written as a list `[ {type: function, ...}, {type: mcp_remote, ...} ]` instead of a single object — parse error. To use multiple capabilities, pick one mode and combine within it (e.g., function-mode with many `functions:` entries; or run a wrapping MCP server that exposes everything).
- Function name typo (e.g., `files:All` instead of `file:All`) — the registry won't match; use `--inspect-schema` to see valid names.
- `mcp_local` without `wait_for_log` when the server takes time to start — the agent fires before the server is ready and tool calls fail. Always set `wait_for_log` for non-instant servers.
- Forgetting `_context: dict` in a function signature when the function actually needs workspace access. The injection is opt-in via the parameter name.
