# Python Learning Explainer

这个 skill 用来把“给我解释这段 Python”变成稳定、可复用的学习型回答，而不是只给一句零散结论。

## Default Stance

- 先把用户给的语法或代码当作学习材料，目标是解释清楚，不是直接改代码。
- 默认面向学习者输出：先说这段代码在做什么，再拆对象类型、返回值、可迭代性和关键方法。
- 默认按 Python 3 语义解释；只有当用户明确提到 Python 2、特定小版本或框架环境时，才切换解释前提。
- 优先基于 Python 语言规则静态解释；只有在行为明显依赖具体运行结果时，才考虑运行最小、无副作用的验证片段。
- 如果代码涉及自定义类、第三方库、运行时 monkey patch 或上下文变量，先基于现有信息说明可确定部分，再明确哪些类型需要额外上下文。
- 不要只说“这是 iterable”或“返回 list”；要顺带解释为什么。

## Use This Skill When

- 用户贴了一段 Python 语法、表达式、REPL 输出或代码片段，想知道含义
- 用户问某个函数、方法、表达式或操作符会返回什么对象类型
- 用户搞不清某个对象是否可迭代、可索引、可切片、可调用、可变
- 用户在比较 `list`、`tuple`、`set`、`dict`、`range`、`zip`、`map`、`filter`、`enumerate`、生成器、迭代器、视图对象等 Python 常见对象
- 用户想知道某段代码中每一步中间值可能是什么类型，或某个方法是原地修改还是返回新对象

## Workflow

1. Identify the learning target
   - 提取用户真正困惑的是哪一类问题：语法含义、返回值、对象类型、可迭代性、方法来源，还是多个问题一起出现。
   - 如果用户贴的是多行代码，先划出关键表达式，而不是逐字符复述整段代码。

2. Explain the code in plain language
   - 先用 1-3 句话说明代码整体在做什么。
   - 如果是链式调用或嵌套表达式，按从里到外或从左到右拆解执行顺序。

3. Enumerate key expressions and object facts
   - 对关键表达式逐项说明：
     - 表达式值的大致形态
     - 运行后的对象类型
     - 是否可迭代
     - 是否是迭代器
     - 是否可变
     - 是否支持索引/切片
     - 是否会被一次性消费
     - 是返回新对象还是原地修改
   - 若用户最关心“为什么能 `for` 遍历”或“为什么能 `list(...)`”，优先解释迭代协议：`__iter__()` / `__next__()` 的直观含义，但避免过度学术化。

4. Explain functions, methods, and operators
   - 标清每个关键函数/方法/操作分别是谁提供的：内置函数、实例方法、类型构造器、语法糖或运算符行为。
   - 对常见易混淆点明确指出：
     - `sort()` vs `sorted()`
     - `append()` / `extend()` / `insert()`
     - `keys()` / `values()` / `items()`
     - `map()` / 列表推导式
     - `range()` / `list(range())`
     - 生成器表达式 vs 列表推导式
     - `is` vs `==`

5. Call out ambiguity when needed
   - 如果类型取决于上下文，例如自定义函数返回值、变量上游赋值、第三方库 API 或分支逻辑，就明确写出：
     - 目前能确定的语义
     - 仍不确定的类型点
     - 需要查看的最小上下文
   - 但不要因为有不确定点就停止；先把确定内容讲明白。

6. Finish with a learner-friendly answer shape
   - 默认按以下结构回答：
     - 代码作用
     - 关键对象/表达式说明
     - 函数与方法说明
     - 容易混淆的点
     - 一个最小示例或记忆口诀（仅在确实有帮助时给）

## Preferred Answer Shape

默认尽量覆盖这些信息，按相关性取舍，不必机械全列：

- `这段代码在做什么`
- `最终结果 / 返回值`
- `关键对象类型`
- `是否可迭代`
- `是否是迭代器`
- `是否可变`
- `是否支持索引/切片`
- `函数/方法分别来自哪里`
- `是否原地修改`
- `学习时最容易误解的点`

如果用户的问题特别短，比如“`dict.keys()` 返回什么”，优先直接回答结论，再补 2-4 个关键解释点。

## Tool Use

- 默认先直接解释，不需要调用工具。
- 如果用户给的是当前项目中的 Python 文件或引用了本地路径，先读取相关代码再解释。
- 如果行为依赖真实运行结果，且可以用很小、无副作用的 Python 片段验证，就运行最小验证命令。
- 不要为了回答学习问题去运行会改文件、联网、安装依赖或触发业务副作用的代码。

## Key Gotchas

- 不要把“可迭代对象”和“迭代器”混为一谈。
- 不要默认所有能 `for` 的对象都支持索引。
- 不要把“返回 `None`”漏掉；很多原地修改方法恰恰最容易卡住初学者。
- 不要把语法错误、未定义变量或缺失上下文硬解释成确定行为；必要时直接指出代码当前不能正常运行。
- 不要把第三方库对象强行解释成内置类型；必要时明确是“某库自定义对象”。
- 不要只给定义，不给直觉；学习型回答应解释“为什么是这样”。
- 不要在用户只问一个点时展开成整章教程；保持围绕当前代码。

## Stop Conditions

只有在以下条件满足时才算完成：

- 已明确解释这段代码或语法在做什么
- 已回答用户最关心的类型/返回值/可迭代性问题
- 已指出关键函数、方法或操作的来源与行为
- 已补充至少一个最重要的易错点或边界条件（若确实存在）
- 若存在类型不确定性，已经清楚说明不确定来源，而不是含糊带过
