# 坑位摘要（与图像处理/上云相关）

> 来源：一套经 95 份真实材料验证的归档工作流所积累的约 64 条实测坑位，此处摘取与**图像处理、上云调用**直接相关的部分。
> 已剥离全部档案数据（无姓名、无证件号、无住址）。

---

## 一、上云之前（顺序不能颠倒）

| # | 检查项 | 不做的后果 |
|---|---|---|
| 1 | **判断拍摄方向并摆正** | 增强工具会基于错误方向做透视矫正，**结果完全不可用**（白花一次计费） |
| 2 | **剥离 EXIF** | 见坑位 A（下方）——EXIF 的 Orientation **可能是错的** |
| 3 | **压缩到载荷限内**（长边 ≤800px、JPEG q85） | 返回 HTTP 413 |
| 4 | **大 base64 走 `@args.json`** | 命令行参数上限约 32KB，一张 1440×1920 的图 base64 约 160KB，**必然截断** |
| 5 | **先建好落盘目录** | 调用成功后存盘失败 → 只能重调，多花一次计费 |
| 6 | **含防伪底纹的件不要转 JPEG** | 有损压缩破坏细密网纹，削弱防伪可核验性 |

### 坑位 A：iPhone 拍摄件的 EXIF `Orientation` 可能是错误标记

**以存储像素为准，不得按 EXIF 旋正。** 同时也正因如此，上云前必须把 EXIF 剥掉——否则云端工具可能"好心"按错误标记旋转。
判定方向最快的锚点：**国徽在真实证件上位于左上角**；若出现在右上，说明证件被顺时针转了 90 度。

### 坑位 B：拍摄方向无 EXIF 可依

手机横拍证件时画面整体旋转 90 度，且 **EXIF 里根本没有 Orientation 标记**，任何基于 EXIF 的自动矫正都抓不到。
**稳妥做法：两向都生成、目视比对后再定，不要赌一次。**

## 二、判断"要不要上云"时的坑

### 坑位 C：「≥300 DPI 走本地」**只针对扫描件**

一份 3000×4000 的手机拍摄件按 A4 折算约 316 DPI，表面已越 300 DPI 线。若照搬 DPI 判据走本地，
**透视畸变与木桌背景会一并入档**。

> 判定顺序永远是：**先分「扫描件 / 拍摄件」，再谈分辨率**。
> 分辨率只决定"扫描件内部"的处理路径，不能替代"这张图要不要做几何校正"的判断。

### 坑位 D：横向页 ≠ 内容侧卧

"文件里有横向页"不等于"内容躺倒"。
有大量横向页**本身就是横向排版**（横向表格、横向票据、两张卡片并排）。
**必须逐页渲染目视确认，不可凭页面宽高比推断**。

### 坑位 E：源版本体检——同目录可能躺着一份更好的

用户递来的件未必是最优版本。只要**PDF 内嵌图分辨率远低于同目录的原生扫描图**，
就说明这个 PDF 是"降质搬运"的中间产物，原始扫描件另有其物。

**三条纪律**：① 先完成调用方指定的处理；② 发现更优/更全版本**只报告、不擅自替换**；
③ 体检要**连目录里的其他文件一起看**。

### 坑位 F：「是否已在库」的第一判据是**图像流 md5 指纹**

外观、页幅、字节数都不可靠；**像素相似度不可作判重判据**。
比较时应取 **XObject 的原始压缩流**去算 md5——
注意 `page.images[i].data` 那条路径会**经 Pillow 重新编码**后再返回，用它比对必然"不一致"，
会把无损件误判成有损，进而误导你去"修"根本没坏的东西。

## 三、增强结果的固有特性（必须在报告中如实标注）

### 坑位 G：云端增强**会改变图像纵横比**

实测两份文档：一份偏差 +1.8%（良好），另一份 **−8.4%**（偏大）。
来源无法从图像单方面判定（拍摄角度残余 / 纸张本身非标准 / 二者兼有）。

**处理原则**：
1. 一律按 **A4 短边 210mm** 放置，**绝不做拉伸变形去凑标准比例**（那是不可逆的信息破坏）；
2. 在报告中**如实标注**"打印尺寸不能保证严格 1:1"；
3. 落版时须按**主导边锚定、另一边等比推算**，**不得沿用增强前的 mm 尺寸**。

### 坑位 H：同一工具、同一批次，几何校正结果**逐件不同**

增强质量须**逐件量化标注**，**不可整批假定**。本包的 `verify.py` 就是做这件事的。

### 坑位 I：增强会统一漂白底衬

**印章饱和度略降**（可辨识度通常不受影响）。另注意五角星等处的**真实印油肌理**不要误判为算法伪影
（须与原图对照确认）。

### 坑位 J：扫描件的"低分辨率彩色层 ＋ 高分辨率二值叠加层"双层结构

部分扫描 PDF 是双层结构，**裁切重编码 / 单层提取都会丢层**。
→ 对这类件，**整页字节复制是唯一无损方案**。

### 坑位 K：扫描 PDF 的"OCR 三明治"（JBIG2 二值图 ＋ 隐形文字层）

外观是扫描件，其实带一层**不可用的乱码文字层**。
→ 探测时不要看到"有文字层"就当原生电子件；**要同时看文字层是否可读**。

## 四、载荷与请求

| 项 | 实测值 |
|---|---|
| 请求体上限 | 约 **2 MB**（超限 → HTTP 413） |
| 安全载荷 | **≤ 1.4 MB**（base64 膨胀 4/3） |
| 压缩起点 | 源件超过 1.4MB 或 base64 超过约 1.9MB |
| 压缩参数 | 长边 **≤800px**、JPEG **q85**（实测 3000×4000/2.9MB → 1200×1600/150–220KB） |
| 例外 | 含细密防伪网纹的 **PNG 不要转 JPEG**，源件未超限时直接原格式上传 |
| 命令行传参 | 上限约 **32 KB** → 一律用 `@args.json` |

## 五、其他值得记住的判据

- **拍摄件原样装箱**是允许的，但必须**标注保真等级、页幅与待定项**，并说明未增强。
- **一页多枚小件**的件数统计须用**纸张色差**掩膜；单用墨迹掩膜会把一张卡切成数块。
- **编号相同 ≠ 同一件**：双联/正副本可共用同一编号而内容不同。
- **浅底纹卡面 vs 纯白背景**：亮度阈值会失效 → 改用**色彩偏移剖面（B−R）**定缘 ＋ 国标尺寸反校。
- **元数据时点 ≠ 文书落款日**：扫描生成时间（如扫描仪写入的 2020 年）不等于文书的落款日期，两口径须**并列记录、不互代**。
- **锚定边恰等于页面边**会被"绝不缩放"硬拦（浮点误差）→ 锚定值**留 0.01–0.02mm 余量**。
