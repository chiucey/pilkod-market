# 同事交接助手

承接离职同事工作时的智能助手，帮助你从碎片化的文档、空荡的工位和不完整的交接中重建工作上下文。

## 核心工作流程

### 1. 信息收集与诊断

首先，全面收集离职者留下的所有材料：

**必收集项：**
- 交接文档（三页也好，三十页也罢）
- 项目代码和配置文件
- 邮件往来记录（关键项目相关）
- 通讯录和联系人列表
- 共享文档和云盘文件
- 即时通讯记录（如果可以获取）

**收集后，快速诊断交接质量：**

```
交接完整性评估维度：
├── 文档覆盖度：项目是否有文档？
├── 上下文完整性：为什么这么做有说明吗？
├── 联系人标注：找谁解决问题？
├── 状态透明度：哪些是坑，哪些是宝藏？
└── 维护可行性：接手后能独立运营吗？
```

### 2. 关键人物地图重建

交接断裂的核心往往是「人」的断裂。通过以下方式重建人际网络：

**优先级追问清单：**
- 直接上下游合作方是谁？
- 哪些人对项目有重大影响？
- 谁曾经提出过反对意见或质疑？
- 供应商/外包方联系方式？
- 审批链上的关键节点？

**输出：联系人地图**
```
[离职者] ←→ [核心协作圈] ←→ [影响圈] ←→ [外围联系人]
                 ↓
          你需要优先联系的人用 ★ 标记
```

### 3. 项目上下文重建

面对「三页文档想概括三年积累」，使用以下追问框架：

**黄金七问：**

1. **起源**：这个项目/系统为什么存在？解决什么问题？
2. **演进**：经历了哪些重大变更？为什么要变？
3. **现状**：现在运行状况如何？有哪些已知问题？
4. **关键点**：最脆弱的地方在哪里？什么会引发灾难？
5. **潜规则**：有哪些文档没写但必须知道的事？
6. **待办项**：有哪些未完成的承诺或欠下的债？
7. **退出路径**：如果完全搞砸了，怎么恢复到今天的状态？

### 4. 知识断层识别与填补

**常见断层类型：**

| 断层类型 | 表现 | 填补策略 |
|---------|------|---------|
| 隐性知识 | 「这个流程大家都知道」 | 找老员工口述历史 |
| 决策断层 | 不知道当初为什么选A方案 | 查邮件记录、会议纪要 |
| 关系断层 | 不知道该找谁 | 查项目文档的@记录 |
| 状态断层 | 不知道项目真实状态 | 亲自运行/测试验证 |
| 风险断层 | 不知道有哪些已知风险 | 查历史工单、Bug记录 |

### 5. 风险评估与优先级排序

**接手后，立即识别高风险项：**

**红色警戒（立即处理）：**
- 在进行中的关键业务流程
- 即将到期的合同/付款/承诺
- 无人知晓的密码/权限/证书
- 依赖该项目的其他方

**橙色预警（一周内处理）：**
- 历史遗留的技术债务
- 未解决的客户投诉
- 性能或稳定性隐患
- 人员依赖过高的流程

**黄色备忘（持续关注）：**
- 项目历史和决策背景
- 优化空间和待改进项
- 扩展计划和未来方向

### 6. 交接后的主动沟通策略

**新官上任三把火，但火要烧对地方：**

**第一步：广而告之**
- 向所有相关方发送「我接手了」的正式通知
- 说明你的背景和联系方式
- 表示愿意倾听和学习的态度

**第二步：关键人物一对一**
- 按影响力排序，逐一约聊
- 每次聊天准备三个问题：
  1. 你认为这个项目最大的风险是什么？
  2. 有什么是我接手后需要特别注意的？
  3. 我们之前合作中有什么可以改进的地方？

**第三步：文档补全计划**
- 边接手边补充文档
- 每解决一个问题，同步更新一份文档
- 三个月后，你的文档应该比前任的更完整

## 场景化指南

### 场景A：文档很少，全靠人肉

**信号：** 交接文档只有目录，实际内容全靠口口相传
**策略：**
1. 列出一份「谁知道什么」的清单
2. 按重要性约聊关键知情人
3. 每次谈话后立即写一份「今日学习」
4. 每周合并成一份知识文档

### 场景B：文档很多，但过时了

**信号：** 有很多文档，但日期都是两年前的
**策略：**
1. 标注每个文档的最后更新时间
2. 对比「文档说的」和「实际运行的」
3. 差异之处就是最需要更新的地方
4. 标注「待验证」和「已过时」

### 场景C：项目烂尾，责任不清

**信号：** 一堆半成品，不知道为什么没做完
**策略：**
1. 找出最后一个有效提交/修改的人
2. 了解项目停摆的真正原因（资金？优先级？技术障碍？）
3. 评估继续vs放弃的成本
4. 如果继续，制定分阶段复活计划

### 场景D：搭档转岗，默契归零

**信号：** 两个人的默契变成了一个人的摸索
**策略：**
1. 找回所有共同完成的项目记录
2. 分析哪些是「你们」的做法，哪些是「通用」的做法
3. 把「你们」的做法转化为「我」的标准操作流程
4. 建立自己的检查清单，避免重复依赖对方的隐性检查

## 心理建设

**允许自己不知道：** 前任三年积累的东西，不可能三天学会。给自己三到六个月的学习曲线。

**区分「不知道」和「应该知道」：** 有些事不知道是正常的，有些事不知道是会出问题的。优先搞清楚后者。

**把交接当作机会：** 接手别人的工作是一个重新审视和优化的机会。很多「一直想改但没改」的地方，现在可以改了。

**建立自己的系统：** 不要试图完全复制前任的方式，找到适合自己的工作风格，在此基础上承接工作。

## 输出模板

接手新工作后，建议产出以下文档：

### 1. 交接清单确认表
```
□ 已联系所有关键人物
□ 已了解项目起源和背景
□ 已识别所有高风险项
□ 已接管所有账号权限
□ 已验证关键系统可正常运行
□ 已建立自己的备份和恢复方案
```

### 2. 知识地图
```
项目名称：
关键人物： [姓名] - [角色] - [联系方式] - [重要性]
系统架构： [简图或描述]
依赖关系： 上游→本项目→下游
已知问题： [列表]
待了解项： [列表]
```

### 3. 前90天计划
```
第一周：熟悉现状，建立联系，识别风险
第一个月：接管运营，稳定运行，记录问题
第二个月：优化改进，补充文档，沉淀经验
第三个月：总结复盘，形成标准，准备交接
```

## 触发词速查

以下情况请立即使用本技能：
- 同事离职，需要接手工作
- 导师毕业，带走了经验和上下文
- 搭档转岗，合作默契归零
- 前任交接文档过于简略
- 项目文档无人维护
- 需要重建工作知识体系
