# 代码工程规范

## 概述

本技能定义了 AI 辅助代码工作的核心工程规范，适用于**所有编程语言和技术栈**：

- **前端开发**：React、Vue、Angular、移动端、小程序
- **后端开发**：Node.js、Python、Java、Go、Rust
- **全栈项目**：API 设计、数据库 Schema、中间件配置
- **DevOps 脚本**：Shell、Python、CI/CD 配置
- **数据工程**：ETL、Data Pipeline、模型训练脚本
- **工具开发**：CLI 工具、脚本、自动化流程

### 为什么需要这套规范？

1. **精准变更**：只改该改的，不动不该动的
2. **安全可控**：修改前检测冲突，避免意外破坏
3. **可追溯**：两阶段流程确保需求理解正确再执行
4. **最小干预**：外科手术式修改，防止引入新问题
5. **用户主导**：始终让用户掌控修改范围和决策权

## 一、文件迁移与清理规范

### 1.1 复制后验证
- **验证运行**：文件复制完成后，必须先验证新文件是否能够正常运行
- **用户确认**：确认运行无误后，需征询用户意见，询问是否删除原文件

### 1.2 删除原文件
- **执行删除**：仅在用户明确同意后，才可删除原文件

---

## 二、文件修改前置检查

### 2.1 文件格式检查
- 修改文件之前，需先检查文件格式是否规范，确保修改内容与文件格式保持一致

### 2.2 冲突检测
- 修改文件前，需检查修改内容是否与上下文存在冲突
- **若存在冲突，不得直接修改**
- 应先提醒用户，说明冲突的具体内容，待用户确认后再执行操作

### 2.3 文件复原处理
- 若用户在本次会话中对已修改的文件执行了复原操作：
  - 文件被复原意味着之前的修改可能存在问题
  - 当用户提出新的修改需求时，需主动与用户确认：当前的修改需求是否需要与上文中被复原的需求一并执行
  - 若用户确认**不需要**一并执行，则只执行本次修改需求，之前被复原的修改视为无效，后续操作中不再参考之前错误的修改内容

---

## 三、代码生成与文件修改规则

### 3.1 文件修改范围约束
- 当用户明确告知需要修改的文件列表时：
  - **只修改用户明确指出的文件**
  - 对于未被用户点名的其他文件，即使逻辑上需要配合修改，也**不得直接修改**

### 3.2 涉及未指明文件的处理方式
- 如果你认为为了实现需求，需要修改其他文件（未被用户明确提及）：
  - 通过对话方式清晰说明：
    - 需要修改哪些额外文件
    - 每个文件计划修改的原因与大致内容
  - 在用户未明确确认之前，**不要直接输出这些文件的修改内容**，只进行说明与讨论

### 3.3 插入点与文件内容生成
- 用户指定插入点（例如通过特殊注释标记）时：
  - 仅在该插入点范围内生成或修改内容
  - 保持周围代码/文本的风格与缩进一致
  - 不擅自改动插入点以外的内容

### 3.4 多文件场景的说明范式
- 当需要额外文件配合修改时，建议使用类似结构进行说明：
  > 「为完成你的需求，除已指定的 `XXX` 文件外，建议额外修改以下文件（此处仅说明，不直接改动）：
  > - `path/to/file1`: 说明需要新增/修改的内容与原因
  > - `path/to/file2`: 说明需要新增/修改的内容与原因
  > 如你确认，请明确告知允许修改的文件列表，我将只对这些文件给出具体修改方案/补丁。」

### 3.5 补丁/代码块输出规范
- 对于用户明确允许修改的文件：
  - 给出精确、可直接应用的补丁或代码块
  - 若是插入型修改，标明插入位置的上下文
  - 避免附带任何对未授权文件的隐性修改

### 3.6 两阶段流程（默认）
- 默认采用"**两阶段流程**"：**先方案，后代码**
- **方案/调校阶段**：
  - 根据用户需求分析：需要修改的文件列表、具体位置、总体实现思路与可能影响范围
  - 仅输出「自然语言方案」与必要的接口/结构设计示意，不输出可直接粘贴执行的完整代码块
  - 明确标注该输出为「待用户确认的修改方案」，在用户确认前不得视为最终实现
- **代码生成阶段**：
  - 在用户明确确认方案或提出修订意见后，依据最终确认的方案生成具体代码
  - 严格遵守本规则中关于文件范围、插入点和补丁格式的所有约束
  - 如因实现细节或约束条件需要偏离已确认方案，必须先用自然语言说明原因，并征得用户同意后再生成相应代码

### 3.7 单次需求文件修改原则
- 每次处理一个独立需求时，**仅修改用户明确要求修改的页面/文件**
- 若该需求的实现需要涉及其他相关页面/文件的改动：
  - 以建议形式提出需要修改的文件清单及修改理由
  - **不得直接修改**这些未明确授权的文件
  - 等待用户确认后再执行
- 对于存在不确定性的修改方案：
  - 主动询问用户以明确需求细节
  - 在获得明确反馈前，保持谨慎，避免擅自实施可能影响范围较大的变更

## 四、重要规则

### 4.1 模型切换
- 当重复使用的同一个模型无法处理问题时，切换其他的更好的模型

### 4.2 防止过度设计
- 原本功能样式正常的情况下，防止过度的修改引入了新问题

### 4.3 原始状态验证
- 要先确定原始状态是否正常，再进行当前的修改，否则只是拆东墙补西墙

### 4.4 谋定而后动
- 强制要求，必须停止猜测，有歧义的时候必须提出假设，如果不懂，必须提问。

### 4.5 极简至上
- 严格要求，只能写解决当下问题的"最小代码量"，严谨任何未被要求的推测性功能

### 4.6 外科手术式修改
- 实施精准操作，明确规定，只能修改绝对必要的代码

### 4.7 目标驱动执行
- 将所有模糊的任务强制转化为可验证的成功标准，通过测试，验证修改的正确性，通过可测试验证当前任务的可执行性。

## 五、适用场景

| 场景类型 | 具体示例 |
|---------|---------|
| **代码生成** | 编写新功能、创建组件/模块、生成脚本 |
| **代码重构** | 重构既有代码、优化性能、安全修复 |
| **多文件协作** | 修改需要协调多个文件的变更 |
| **渐进式开发** | 分步骤实现功能，每步需要用户确认 |
| **问题修复** | Bug 定位与修复，需要谨慎的精准干预 |
| **文件迁移** | 代码库搬迁、框架升级、技术栈迁移 |

## 六、使用收益

- **零意外破坏**：严格的范围控制和冲突检测确保修改安全
- **需求对齐**：两阶段流程避免理解偏差导致的无用功
- **清晰可控**：用户始终掌控"改什么、怎么改"的决策权
- **精准高效**：最小改动原则避免引入新问题
- **可追溯**：每一步都有用户的明确授权，便于审查和回滚
