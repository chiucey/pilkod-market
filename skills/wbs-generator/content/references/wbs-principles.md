# WBS设计原则与最佳实践

## 核心原则 (Core Principles)

### 1. 100%原则
WBS必须包含项目的所有工作，包括：
- 项目本身
- 项目管理活动
- 直接和间接工作
- 假设和约束相关的工作

子层次工作之和必须100%覆盖父层次的工作内容。

### 2. 功能导向原则
- 按可交付成果和功能进行分解
- 避免按组织结构、日历或人员分工分解
- 每个分支应代表相同类型的工作

### 3. 可管理性原则
工作包应该是：
- **时间可估算**: 4-80小时的标准工作包
- **成本可测量**: 可以独立核算成本
- **风险可评估**: 风险可以识别和管理
- **责任可明确**: 有唯一的责任人

### 4. 独立性原则
- 每个工作包应能独立完成验收
- 尽量减少工作包间的依赖
- 明确标识外部依赖

### 5. 层次合理性
| 层次 | 名称 | 说明 |
|------|------|------|
| L1 | 项目层 | 整个项目 |
| L2 | 阶段层 | 项目生命周期阶段 |
| L3 | 交付物层 | 主要可交付成果 |
| L4 | 工作包层 | 可管理的最小单位 |
| L5+ | 活动/任务层 | 日常工作任务 |

## WBS结构模式

### 模式一：按阶段分解
```
1 项目
├── 1.1 启动阶段
├── 1.2 规划阶段
├── 1.3 执行阶段
├── 1.4 监控阶段
└── 1.5 收尾阶段
```

### 模式二：按产品/交付物分解
```
1 项目
├── 1.1 产品A
│   ├── 1.1.1 子产品A1
│   └── 1.1.2 子产品A2
├── 1.2 产品B
└── 1.3 产品C
```

### 模式三：按地理/组织分解
```
1 项目
├── 1.1 区域A
├── 1.2 区域B
└── 1.3 区域C
```

### 模式四：混合模式
```
1 项目
├── 1.1 项目管理
├── 1.2 阶段一（按阶段）
│   ├── 1.2.1 产品A（按产品）
│   └── 1.2.2 产品B
└── 1.3 阶段二
```

## 命名规范

### 动词使用指南
| 阶段 | 推荐动词 |
|------|---------|
| 启动 | 制定、建立、识别、任命 |
| 规划 | 编制、规划、设计、定义 |
| 执行 | 实施、完成、开发、生产 |
| 监控 | 监督、控制、跟踪、评估 |
| 收尾 | 验收、移交、归档、总结 |

### 命名示例
- 正确：制定项目章程、编制进度计划
- 错误：项目管理、项目工作

## 常见错误及避免

### 错误1：按人员分工分解
```
错误：
├── 张三负责的工作
└── 李四负责的工作

正确：
├── 需求分析
├── 系统设计
└── 编码实现
```

### 错误2：分解过细或过粗
```
过粗：
1 项目
└── 1.1 完成项目

过细（建议合并）：
1.1.1.1.1.1 详细任务
└── 1.1.1.1.1.1.1 子任务1
```

### 错误3：包含非项目工作
```
错误：
1 项目
└── 1.1 日常运营工作

正确：仅包含项目范围内的工作
```

### 错误4：WBS与进度计划混淆
```
错误：
1 项目
├── 1.1 第一周工作
└── 1.2 第二周工作

正确：按交付物和功能分解
```

## 质量检查清单

- [ ] 顶层代表整个项目
- [ ] 每个分支代表父节点的100%工作
- [ ] 工作包可由单一责任人在单一地点完成
- [ ] WBS编码系统一致且唯一
- [ ] 工作包级别合理（4-80小时）
- [ ] 命名使用动词+名词
- [ ] 避免包含里程碑或日期
- [ ] 与项目范围说明书一致
- [ ] 便于成本和时间估算
