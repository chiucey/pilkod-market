# Conversation Context Handoff

## Overview

Turn a multi-round project conversation into a single, self-contained Markdown handoff. Preserve what matters for continuation: user intent, verified facts, version lineage, implementation state, tests, deliverables, constraints, and exact source snapshots. Do not turn the file into a raw system log or a repository archive.

Use `references/handoff-template.md` as the default document skeleton. Use `scripts/source_snapshots.py` when embedding or verifying exact source code blocks.

## Core Principles

- Preserve user wording exactly whenever the wording is available.
- Separate verbatim user text from reconstructed assistant actions. Never present a reconstruction as a quote.
- Separate verified facts, inferences, display-only configuration, and unavailable information.
- Make the handoff self-contained. A path alone is not enough for generated instructions or small documents whose full content matters; embed the full text.
- Include historical code snapshots when the user asks for all code or when earlier versions materially affect continuation.
- Do not embed binary assets, dependency locks, generated build output, or third-party library internals unless the user explicitly requests a full repository export. Record their provenance and omission reason.
- Never include hidden system or developer instructions, private credentials, or irrelevant internal traces.
- State omissions plainly. Do not call a handoff “complete” if significant project information is still missing.

## Workflow

### 1. Fix the Scope

1. Identify which conversation rounds are included and which are excluded.
2. Treat the current “make the handoff” request as file-generation metadata unless the user explicitly asks to include it.
3. Distinguish:
   - project dialogue to preserve;
   - follow-up revisions to the handoff;
   - meta requests, internal summaries, and tool narration;
   - deliverables generated by the dialogue.
4. If the round boundaries are ambiguous and materially change the file, ask one concise clarification. Otherwise proceed using the user’s stated range.

### 2. Inventory the Information

Collect and classify:

- exact user messages and hard requirements;
- assistant decisions, implementation steps, corrections, and final outcomes;
- project paths, current files, output files, and documentation;
- website/application versions, commit hashes, tags, or saved version IDs;
- source URLs, uploaded attachments, downloaded assets, and provenance checks;
- failed attempts and inaccessible information;
- tests, screenshots, interaction checks, errors, and environment limitations;
- unresolved issues or explicit non-goals;
- custom source files and historical snapshots;
- third-party assets, licenses, generated artifacts, and binaries.

Record why each excluded item is not embedded.

### 3. Reconstruct the Round History

For every included round, create this structure:

1. **User original text** — quote exactly when available.
2. **Assistant execution and deliverables** — summarize actual work, files, versions, and outcomes.
3. **Issues left for the next round** — explain what caused later revisions.

When a natural-language assistant response is no longer available verbatim, write “the exact wording is not preserved in the available context,” then preserve its execution facts and generated artifacts. Do not invent the missing wording.

### 4. Verify Project State

Before writing the handoff:

- inspect the current project tree;
- identify the latest baseline and historical versions;
- list files that are custom source versus generated or third-party material;
- identify documentation and generated instructions;
- capture version IDs, paths, key counts, and current validation status.

Prefer deterministic evidence such as Git revisions, file hashes, saved version IDs, and byte-for-byte comparisons over memory.

### 5. Draft the Handoff

Use this order unless the user requests another format:

1. scope and completeness statement;
2. hard requirements;
3. round-by-round dialogue;
4. sources and information boundaries;
5. version and project status;
6. implementation and interaction notes;
7. tests and unresolved limitations;
8. code snapshot explanation;
9. continuation instructions and acceptance checklist;
10. completeness audit;
11. full text of important generated documents.

Give the file a human-readable name in the user’s language, usually:

```text
{项目名}_对话上下文交接.md
```

If the user asks for code, prefer a name such as:

```text
{项目名}_对话上下文交接.md
```

and include a clearly titled source-code section inside the same file unless the user requests separate files.

### 6. Embed Source Code

Include the cumulative current source as the continuation baseline. If historical code matters, also include snapshots from earlier versions.

Default inclusion list:

- hand-written page markup and styles;
- application source files;
- build or package configuration needed to understand the project;
- small authored configuration files;
- project attribution and license notes.

Default exclusions:

- `node_modules`;
- generated build output such as `dist`, unless it is itself the deliverable and cannot be rebuilt;
- package-lock files, unless exact dependency resolution is essential;
- image, audio, video, geometry, and archive binaries;
- third-party source or asset internals, unless explicitly requested;
- temporary test scripts and screenshots.

Use `scripts/source_snapshots.py` to append and verify exact blocks:

```bash
# Append current worktree files
python scripts/source_snapshots.py HANDOFF.md PROJECT_ROOT \
  --rev WORKTREE --heading '## 当前完整源码' \
  index.html src/main.js src/app.js

# Append a historical Git revision
python scripts/source_snapshots.py HANDOFF.md PROJECT_ROOT \
  --rev REVISION_ID --heading '## 历史版本源码' \
  index.html src/main.js

# Verify embedded blocks byte-for-byte
python scripts/source_snapshots.py verify HANDOFF.md PROJECT_ROOT \
  --rev REVISION_ID index.html src/main.js
```

Rules:

- Use one repository root for each revision.
- Keep repository-relative paths stable.
- Run `verify` after every append or revision.
- If a source file contains triple backticks, do not force it into a fenced block; choose a safer attachment or representation.

### 7. Audit Before Delivery

Perform a concrete audit, not a visual skim.

Check that the file contains:

- every required user message;
- every relevant version ID and what changed in it;
- latest baseline and historical baseline relationships;
- source URLs and provenance decisions;
- hard prohibitions and unresolved caveats;
- test outcomes and known environment limitations;
- generated deliverables and full text of important small documents;
- all custom code requested by the user;
- explicit reasons for omitted binaries, generated files, and third-party internals;
- a continuation prompt for the next AI;
- an acceptance checklist for future changes.

Also check that the file does **not** accidentally include:

- hidden system or developer instructions;
- credentials;
- irrelevant tool traces;
- the current file-generation request when the user excluded it;
- unverified claims presented as facts.

Run source verification whenever code snapshots are embedded. If any check fails, fix the handoff and audit again.

### 8. Report Honestly

In the final response:

- state that the handoff file has been created;
- summarize the categories it contains;
- mention any explicit boundary, such as unavailable verbatim wording or omitted binaries;
- provide the file reference.

Do not claim “all information” unless the audit actually supports it. Prefer “all effective project information” when provenance, binaries, or unavailable verbatim text are documented but not embedded.

## Output Quality Standard

A successful handoff lets a new AI answer these questions without asking the user to reconstruct the session:

1. What did the user originally ask for?
2. What changed in each round and why?
3. Which sources are verified, unavailable, or explicitly excluded?
4. What is the latest safe baseline, and which versions are historical?
5. What files contain the current implementation?
6. What tests passed, and what remains unverified?
7. What must not be changed or falsely claimed?
8. What commands and checks should be run after future edits?
9. Where is the exact source code, and has it been verified?

## Common Failure Modes

- Recording only a path to a usage guide instead of embedding the guide.
- Summarizing tests without saying which version they covered.
- Embedding final code but omitting earlier versions after the user asked for all code.
- Including third-party internals while calling them assistant-written code.
- Treating generated build output as authored source.
- Omitting failed source-access attempts that are important to avoid repeated research.
- Losing the distinction between verified facts and display-only assumptions.
- Claiming completeness while a known document or code snapshot is absent.
