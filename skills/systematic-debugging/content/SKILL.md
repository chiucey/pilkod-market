# 系统化Bug排查方法论

## 核心原则

**先定义问题，再动手修复。** 遇到bug时，先回答：
- 现象是什么？
- 预期是什么？
- 问题边界在哪？
- 稳定复现还是偶发？
- 从什么时候开始？
- 影响范围多大？

---

## 8步排障主流程

### Step 1: 把问题"说清楚"

用标准格式描述bug：
```
在 [环境] 下，做 [操作]，出现 [异常]，预期 [结果]。
```

示例：
> iOS 17真机，登录后进入订单页，下拉刷新第一次正常，第二次页面白屏，预期应为正常展示列表。

### Step 2: 先复现，再修

判断复现类型：
- **100%复现** → 直接排查
- **概率复现** → 固定变量缩小范围
- **偶发无法复现** → 增加日志/trace，收集现场

固定变量的方法：
- 固定设备、系统版本、网络环境
- 固定账号、测试数据
- 固定操作步骤
- 尽量缩小变量

### Step 3: 先划边界，缩小范围

按层定位问题归属：

| 层级 | 可能问题 |
|------|----------|
| 前端展示层 | 布局约束冲突、数据绑定失败、渲染异常 |
| 业务逻辑层 | 状态机错乱、逻辑分支错误 |
| 网络层 | 请求超时、DNS问题、SSL错误 |
| 数据解析层 | JSON解析失败、字段类型变化 |
| 缓存层 | 脏数据、缓存穿透/雪崩 |
| 数据库层 | SQL异常、索引失效、连接池耗尽 |
| 服务端接口层 | 接口字段变更、返回值异常 |
| 第三方SDK | SDK冲突、版本兼容性 |
| 系统兼容性层 | 系统API差异、权限问题 |

**关键问题：它到底死在哪一层？**

### Step 4: 基于证据，而不是感觉

建立证据链：`现象 → 假设 → 验证 → 排除/确认`

常用证据来源：
- 日志（服务端/客户端）
- Crash堆栈
- 埋点/监控告警
- 网络抓包
- 线程堆栈
- 内存快照
- 数据库内容
- 请求参数/响应结果
- Git提交记录
- 最近上线变更

### Step 5: 一次只验证一个变量

每次只改一个点，观察结果。避免同时修改多个变量导致无法定位根因。

### Step 6: 优先检查最近变化

**昨天还好的，今天坏了，先查昨天改了什么。**

高优先级排查方向：
- 最近代码提交
- 最近配置变更
- 最近依赖升级
- 最近接口字段变化
- 最近灰度发布
- 最近数据结构调整

### Step 7: 先止血，再根治

| 阶段 | 措施 |
|------|------|
| 止血 | 回滚版本、关闭开关、降级功能、屏蔽异常数据、加兜底逻辑、限流/熔断 |
| 根治 | 修复根因、补监控、补日志、补测试、补文档、补防御性代码 |

### Step 8: 修完一定复盘

回答：
- 根因是什么？
- 为什么之前没发现？
- 为什么现有测试没兜住？
- 以后如何更早发现？
- 如何避免同类问题再次发生？

## 5种核心方法论

### 1. 二分法排查
适用：代码量大、调用链长、不确定问题在哪一段

做法：把问题链路一分为二，判断前半段是否正常，逐步缩小范围。

### 2. 最小复现法
适用：疑难crash、线程问题、布局问题、SDK冲突

做法：
- 去掉无关业务逻辑
- 去掉复杂UI
- 去掉多线程干扰
- 用最简单的数据复现

### 3. 时间线法
适用：线上事故、偶发问题、生产问题

按时间线整理所有事件，寻找因果关系。

### 4. 对比法
适用：定位"为什么这个有问题，那个没问题"

对比维度：
- 正常设备 vs 异常设备
- 正常账号 vs 异常账号
- 老版本 vs 新版本
- 有问题数据 vs 正常数据

### 5. 假设驱动法

不是漫无目的尝试，而是先提出假设再用证据验证。

常见假设：
- 是不是空指针导致？
- 是不是线程切换有问题？
- 是不是对象提前释放？
- 是不是服务端字段类型变了？

## 不同类型问题的应对策略

### Crash类问题
优先看：崩溃堆栈、崩溃线程、触发频率、机型/系统版本分布、最近发布版本

重点关注：空指针、野指针、数组越界、KVO/KVC、多线程访问、对象生命周期、主线程UI更新

### 性能问题
先分类型：启动慢、页面卡顿、滑动掉帧、内存暴涨、耗电异常、CPU飙高

排查要点：量化指标、找瓶颈点、采样分析、关注主线程、关注大对象/大量IO/频繁渲染/锁竞争

### 偶发问题
关键做法：
- 增加关键路径日志
- 增加唯一traceId
- 抽样还原现场
- 看是否和网络抖动、时序、并发有关
- 看是否和特殊账号/特殊数据有关

### 线上事故处理框架

| 阶段 | 任务 |
|------|------|
| 第一阶段：应急 | 判断影响范围、确定是否回滚/降级、找到负责人、同步相关方 |
| 第二阶段：定位 | 快速拿日志和监控、建立时间线、缩小变更范围、验证根因 |
| 第三阶段：恢复和预防 | 修复、验证、发布、复盘、补监控和机制 |

## 资深工程师的排障习惯

1. **先看日志质量** - 为什么这个问题排查这么难？是不是日志设计太差？
2. **保留现场** - 错误日志、请求响应、崩溃堆栈、用户操作路径、设备信息
3. **把问题分类** - 建立bug分类体系（空值类、越界类、生命周期类、线程安全类等）
4. **关注状态流转** - 很多诡异bug本质是状态机乱了

## 真正拉开差距的意识

1. **系统性思维** - 看整个调用链、状态链、数据链
2. **证据意识** - 少猜，多验证
3. **边界意识** - 先缩小范围，再深入细节
4. **风险意识** - 修bug要考虑会不会引入新问题
5. **复盘意识** - 一个bug修完，团队能力有没有提升
