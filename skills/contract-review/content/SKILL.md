# Contract Review

## Inputs to collect

调用前先确认三件事（用户没给就问，不要假设）：

- **合同文件**：PDF / DOCX / DOC（老 Word 二进制） / 纯文本 / 图片。处理方式见 `references/file-conversion.md`。
- **审查立场**：`甲方` / `乙方` / `中立`。立场决定风险权重和修改建议方向。
- **合同类型**（可选）：买卖、服务、租赁、劳动、股权、技术开发、保密协议、咨询、其他。影响条款权重与行业特殊风险点。

如果用户没给立场，**默认中立**，但要在报告"整体结论"里注明"若为甲方/乙方，关键风险会变成 XXX"，避免误导。

## Procedure

1. **读取合同正文**
   按 `references/file-conversion.md` 的格式分流处理（DOCX 用 docx skill 直接抽文字；DOC 先用 libreoffice 转 DOCX；PDF 用 `read` 带 `pages`；扫描件 PDF 用 pdf skill 的 OCR；图片用多模态识别；纯文本直接读）。
   原因：先有原文才能谈条款；不同格式处理路径不一样，硬猜会出错。原文片段定位必须保留到条款级，方便报告引用。
2. **抽取合同基本信息**
   合同名称、双方主体、签订日期、标的物 / 服务内容、合同总金额、履约期限、适用法律、争议解决机构、是否有附件。
   原因：基础事实卡片，后续风险定位和报告头部都要用。
3. **条款切分**
   按 `references/checklist-general.md` 的通用条款清单，把合同正文按"条款"粒度切分。同一段落涉及多条款的，逐条标记。
   原因：清单保证覆盖度，避免漏关键风险点；条款粒度切分让后续风险评级可定位到具体原文。
4. **按立场加权审查**
   不同立场对同一条款的风险敏感度不同（详见 `## Risk weights by side`）。每条按当前立场调整风险评分。
   原因：同样一条"违约金上限为合同总额 30%"，甲方嫌低乙方嫌高，不加权就会给出错误结论。
5. **逐条评级**
   每条按 `## Risk rating rubric` 评红 / 黄 / 绿，并给出一句话原因。涉及重大法律合规问题的（如违反法律强制性规定）即使条款表述漂亮也直接红。
6. **生成修改建议**
   - 红色条款：必须修改，给 1-2 个可直接复制的备选文本。
   - 黄色条款：建议修改，给优化方向 + 关键修改点。
   - 绿色条款：不修改，简要说明为什么接受。
   原因：审查报告光说"有问题"不够，要给可执行的修改方案。
7. **整体风险定级**
   根据红色条款数量和性质，给整个合同打一个"高 / 中 / 低"风险评级，并给一句话总结。
8. **输出报告**
   按 `## Output contract` 的格式输出 Markdown 报告 + 落盘到文件。

## Risk weights by side

通用权重表，按立场动态调整。具体条款含义见 `references/clause-glossary.md`。

| 条款类别 | 甲方重点（要严） | 乙方重点（要严） |
|---|---|---|
| 违约金 / 赔偿上限 | 上限要够高、责任面要宽 | 上限要压低、最好封顶到部分款项 |
| 解除权 | 触发条件要宽、可单方解除 | 限制对方单方解除、解除要给补偿 |
| 付款方式 | 早收钱、严验收、留少量尾款 | 分期收、宽松验收、尾款比例高 |
| 履约期限 | 对方期限要短、要严 | 自己期限要长、宽限期要够 |
| 知识产权 | 归甲方 / 共有、衍生作品也归 | 保留乙方背景 IP、衍生作品按贡献分 |
| 保密 | 保密期长、范围宽、单向保密 | 保密期短、范围窄、双向 + 已有信息豁免 |
| 不可抗力 | 列举要全、通知期要短、后果要重 | 列举要宽、通知期长、后果要松 |
| 争议管辖 | 本地法院、方便甲方执行 | 本地法院或仲裁、仲裁地中立 |
| 转让 / 分包 | 限制对方转让 / 分包 | 自己可自由转让 / 分包 |
| 验收 / 交付 | 严标准、宽己方异议期 | 宽标准、宽异议期、分阶段验收 |

## Risk rating rubric

每条风险按两个维度评估：

- **合规性**：是否违反法律强制性规定 / 行业监管要求
- **商业性**：对当前立场是否有利 / 可执行性

评级标准：

- 🔴 **红（高风险）**：必须修改才能签。典型场景：违反法律强制性规定、关键保护条款缺失、严重不对等条款、不可执行条款。
- 🟡 **黄（中风险）**：建议修改。签了能接受但留下隐患：表述模糊、可解释空间对己方不利、行业惯例不一致。
- 🟢 **绿（低风险）**：条款合理，符合法律要求和行业惯例，无需修改。

遇到以下情况直接红，不要权衡：
- 违反法律强制性规定（如违反劳动法上限、违反反垄断、违反消费者权益保护）
- 关键保护条款完全缺失（如无违约责任、无争议解决、无知识产权约定）
- 显失公平（违约金超过实际损失显著比例、解除权严重不对等）

## Output contract

输出一个 Markdown 报告，文件名：`contract-review-<合同简称或日期>.md`。

报告结构：

1. **合同基本信息**（表格）
   合同名称、双方主体、签订日期、标的物、金额、期限、适用法律、争议解决、立场

2. **风险概览**
   - 红色 / 黄色 / 绿色条款数量
   - 整体风险评级（高 / 中 / 低）
   - 一句话总结

3. **条款逐条分析**
   按 checklist 顺序，每条：
   - 条款标题
   - 风险等级（🔴/🟡/🟢）
   - 原文摘录（关键片段，1-3 句）
   - 风险说明（为什么是这个等级）
   - 修改建议（红色给完整替换稿，黄色给关键修改点）

4. **建议修改条款稿**（独立小节）
   把所有红色条款的修改建议稿集中到一起，方便用户一次性复制使用。

5. **缺失条款提示**（如有）
   checklist 里应该出现但合同中没有的条款，列出来，建议补充。

6. **整体结论**
   - 是否建议签署
   - 必须修改的条款清单
   - 建议修改的条款清单
   - 若用户立场不同于默认，提醒"切换立场后关键风险变化"

## Failure handling

- **PDF 读不出**（加密 / 损坏 / 扫描件无 OCR）：让用户提供 docx 或粘贴正文；如必须 OCR，先用 pdf skill 的 OCR 能力，不要硬猜。完整文件转换流程见 `references/file-conversion.md`。
- **DOC 转换失败**（老 Word 二进制）：先用 `libreoffice --headless --convert-to docx` 转；失败则降级 `pandoc <file.doc> -o contract.txt`，仍失败让用户提供新版 docx 或粘贴正文。
- **合同内容明显不完整**（缺签字页、缺附件、缺金额、缺日期）：在报告"基本信息"里明确标注，不阻塞审查，但把"完整性"本身标为黄色风险。
- **不确定法律条款含义**：标"⚠️ 建议咨询专业律师"，不要硬给结论。法律意见需要执业律师，不是模型替代得了的。
- **合同类型与立场冲突**（如用户说是甲方但条款明显偏甲方利益）：在报告里温和提醒"条款实际更倾向 X 方"，不要盲从。
- **合同语言为非中文**：保留原文引用，分析部分用中文；中英文条款释义差异提醒用户。
- **立场不明又必须立刻出报告**：默认中立 + 在结论里写明"立场未指定，按中立立场审查；切换为甲方/乙方后 X 条会变红"，不要让用户回来重问。

## Examples

**Input**:
> 帮我审查这份采购合同，我方是甲方。附件是 PDF。

**Output**:
- 读取 PDF → 抽取 8 项基本信息 → 切分 14 条关键条款
- 按甲方立场加权
- 评出 3 红 5 黄 6 绿
- 整体高风险
- 输出报告 `contract-review-采购合同-2026-09-21.md`，含 3 条完整修改稿
- 提醒"3 条必须修改后建议签署"

**Input**:
> 这是我们和渠道方的拉新合同（.doc 文件），乙方立场。

**Output**:
- .doc → libreoffice 转 .docx → docx skill 抽文字
- 抽取合同基本信息
- 按乙方立场加权 → 评出 5 红 6 黄 8 绿
- 整体高风险
- 输出报告，含 5 条完整修改稿 + 缺失条款提示

**Input**:
> 看一下这份服务协议，中立立场。

**Output**:
- 中立立场审查
- 6 黄 8 绿，无红
- 整体低风险
- 报告含"若为甲方/乙方后 X 条会变红/黄"的提示
