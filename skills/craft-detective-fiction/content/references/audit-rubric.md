## 1. 审计时机

在以下节点执行不同深度的审计：

| 节点 | 最小审计范围 |
|---|---|
| 案件圣经完成 | 真相、因果链、时间线、物理可行性 |
| 大纲批准前 | 公平线索、误导、章节信息顺序、人物弧 |
| 约 10%–20% 进度点 | 连续性、登记簿实际状态、节奏漂移 |
| 重大结构变更后 | 全部受影响事实与章节的回归检查 |
| 揭晓章节前 | 结论—证据链、替代解释、读者可见性 |
| 完稿 | 全文逻辑、体验、风格和清洁导出 |

篇幅短时合并节点，不机械增加检查次数。

## 2. 严重度

- **硬失败**：案件或叙事契约不成立；继续扩写会扩大返工。必须先修。
- **重大警告**：读者很可能感到不公平、牵强或失去兴趣。应在最近里程碑修。
- **一般警告**：影响清晰度、节奏或风格，但不破坏案件成立。
- **建议**：存在更优表达，不要求修改。

不要用总分掩盖硬失败。即使其他维度优秀，只要核心结论依赖新事实，公平性仍然不通过。

## 3. 案件成立性

逐项回答并引用项目文件中的具体位置：

- 一句话真相是否同时说明谁、为什么、何时何地、如何做和哪里失败？
- 犯罪因果链是否存在断点、倒因为果或纯巧合？
- 真凶是否同时具备动机、手段和机会？
- “为什么是现在”是否成立？
- 凶手为何采用该手法，而不是明显更安全的替代方案？
- 掩饰行为是否产生可以追踪的代价或痕迹？
- 调查开始后，凶手行为是否符合其知识范围和风险偏好？
- 结局是否依赖未铺垫的新角色、新技术、新规则或突然自白？

任一核心答案为否，标记硬失败。

## 4. 公平性

为终局的每项必要结论建立检查表：

| 结论 | 线索 ID | 首次对读者可见 | 推理步骤 | 替代解释 | 揭晓前足够？ |
|---|---|---|---|---|---|

检查：

- 读者是否真正看见观察事实，而非只看见侦探的结论？
- 专业知识是否在使用前被自然解释？
- 线索是否能支持结论，而不仅与结论“有关”？
- 核心身份是否至少由相互独立的事实交叉支持？
- 侦探是否掌握了读者没有机会掌握的关键事实？若作品明确采用信息不对等，是否建立了相应契约？
- 揭晓是否重新解释旧事实，而不是添加新事实？
- 叙述性诡计的相关句子在真相下是否仍成立？

“读者可能猜中”不是缺陷；“读者不可能根据前文证明”才是。

## 5. 时间与空间

将真实时间线与所有证词、记录、章节场景逐一比对：

- 同一人物是否在同一时间出现在不可能同时到达的位置？
- 移动、准备、清理、通信和反应时间是否足够？
- 门窗、锁具、灯光、天气、监控和物件持有状态是否连续？
- 死亡时间、伤势、药物、火灾、腐败或技术过程是否在合理范围？
- 证人陈述的精度是否超过其实际观察能力？
- 空间图与正文描述是否一致？

物理上不可能且世界规则未解释，标记硬失败；仅是精度不足时标记重大警告并要求研究验证。

## 6. 嫌疑人与人物

检查每名主要嫌疑人：

- 是否拥有被怀疑的具体事实，而不只是“行为古怪”？
- 隐瞒非凶案秘密的理由是否足以承担说谎风险？
- 最终排除是否基于可验证事实？
- 是否在故事中产生了人物或主题价值？
- 是否只是为了轮流制造悬念而突然可疑？

检查真凶与受害者：

- 真凶是否是完整人物，而不是反转装置？
- 动机是否解释选择，但不被文本简单等同为正当化？
- 受害者是否对因果链有主动作用、关系与历史？
- 真相揭开后，至少一段核心关系是否发生不可逆变化？

## 7. 叙事与连续性

### POV

- 当前 POV 能否知道、听见、看见或推断所写信息？
- 内心叙述是否为了隐藏真相而不自然回避必然想起的事实？
- 多视角切换是否增加新认知，而不只是重复场景？

### 连续性

- 人名、年龄、称谓、职业、伤势、服装和物件状态是否一致？
- 角色何时得知某事实？后文是否提前使用？
- 线索首次出现和登记簿记录是否一致？
- 大纲变更后是否残留旧版本事实？

### 章节功能

- 每章是否改变调查模型、风险、关系或决定之一？
- 删除该章后，主线是否完全不受影响？若是，合并或重写。
- 连续多个章节是否只增加问题而不验证任何假说？

章节进入 `canonical` 前还必须满足可判定门槛：`pov`、`continuity`、`ledger_synced`、`notes_synced` 均为 `pass`；`outline_deviation` 为 `none` 或 `accepted`；`user_approval` 为 `not_required` 或 `approved`；`ledger_actions` 已与登记簿实际位置和最终状态核销；`continuity_dependencies` 引用的章节均存在。任一条件不成立时保留 `draft`。

## 8. 揭晓与读者体验

检查揭晓：

- 是否先定义问题，再证明答案？
- 是否处理最强替代解释？
- 是否让证据、推理和人物反应交替，避免纯讲义？
- 真凶是否提出合理反驳，侦探是否能回答？
- 身份、手法、动机和掩饰是否形成闭环？
- 揭晓后的情感或社会后果是否与主题一致？

检查整体体验：

- 开篇建立的是精确好奇，而非无意义保密吗？
- 中段错误模型是否足够有说服力？
- 反转是否改变解释，而不仅提高事件规模？
- 读者是否有机会形成、验证和修正自己的假说？
- 结局是否兑现项目章程承诺的智力和情感体验？

## 9. 风格与出版清洁度

- POV、叙事距离和时态是否稳定？
- 句法、意象、对话和暴力尺度是否符合风格指南？
- 专业信息是否像人物和场景的一部分，而不是资料粘贴？
- 是否存在大段重复解释、作者替读者总结或过度提示线索？
- 清洁正文是否移除了 YAML、HTML 内部注释、线索 ID、TODO、模板占位符和完整谜底档案？
- 章节顺序、标题和格式是否适合最终交付？

## 10. 审计输出

按以下顺序报告：

1. **结论**：通过／有条件通过／不通过。
2. **硬失败**：逐条引用证据、说明为什么破坏案件、给最小修复路径。
3. **重大警告**：按影响与修复成本排序。
4. **一般警告与建议**。
5. **回归检查范围**：每项修改后必须重查哪些文件和章节。
6. **可继续写作条件**：明确什么修完即可继续，不要求无关润色。

使用 `assets/audit-report-template.md` 记录正式审计。结构脚本只能发现文件和登记问题；人工审计必须重建推理，而不能相信大纲自述“逻辑成立”。

正式报告必须记录报告版本、覆盖章节、章程版本、真相版本、大纲版本、登记簿版本和风格版本。报告只代表最近一次审计快照；任一已覆盖权威版本或章节变化后立即标为 `stale`，完成对应回归审计并更新覆盖范围后才能恢复为 `current`。
