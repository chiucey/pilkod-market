# 规范编程工作流技能

每次代码任务都遵循以下流程，提升代码质量和可维护性。

## 核心原则

1. **计划先行** — 先理解需求，再分解任务
2. **小步提交** — 每个任务颗粒度小，可追溯
3. **TDD 驱动** — 先写测试，用测试定义行为
4. **自审代码** — 写完自己先查一遍，再交付
5. **增量推进** — 每次只做一件事，做完再下一件

## 工作流程（5步）

### 第1步：理解与分解
- 明确需求：做什么？输入输出是什么？边界条件？
- 识别影响范围：会影响哪些现有代码？
- 分解为 1-5 个小任务（每个任务可单独完成和测试）

### 第2步：设计评审
- 决定技术方案：用什么数据结构/算法？为什么？
- 考虑错误处理、空值、边界情况
- 如有大改，先画简单的架构草图或写设计注释
- **拒绝** 没有设计就开写

### 第3步：TDD 循环（每个小任务）
对于每个小任务，遵循：
```
写一个失败测试 → 运行确认失败 → 写最少量代码让它通过 → 重构代码 → 确认测试通过
```
- 测试即文档：测试名要描述清楚测的是什么
- 不要测太多：只测核心行为，边界条件优先

### 第4步：自审与清理
写完代码后自己检查：
- [ ] 变量/函数命名清晰？
- [ ] 没有重复代码？
- [ ] 错误处理到位？
- [ ] 测试覆盖了核心路径？
- [ ] 代码格式一致（缩进、注释风格）？
- [ ] 没有临时调试代码残留？

### 第5步：提交记录
- 每完成一个小任务就记录（commit 或 log）
- commit 信息格式：`[功能] 简述：做了什么，为什么`
- 更新相关文档

## 快速检查清单

每次交付代码前过一遍：

| 检查项 | 通过 |
|--------|------|
| 测试覆盖核心功能 | ☐ |
| 运行测试全部通过 | ☐ |
| 没有 console.log/调试代码 | ☐ |
| 变量命名自解释 | ☐ |
| 错误情况有处理 | ☐ |
| 注释说明 Why，不说明 What | ☐ |

## 适用场景 vs 跳过规则

**完整走5步**：新功能、复杂重构、修复重要bug
**快速走3步**（简单任务如变量改名）：理解 → 改 → 检查
**跳过 TDD**：纯文案、配置修改、简单文件操作
