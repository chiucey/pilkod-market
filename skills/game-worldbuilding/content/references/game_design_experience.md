## 二、通用结构错误（两款游戏均犯过）

### ❌ 错误一：世界书 JSON 条目与世界观描述文档内容高度重复

**问题描述：**
机制类内容（背叛概率公式、信任度互动判定、拷问室效果、百分位判定规则等）同时出现在两份文件中：
- `worldbook.md`（世界观描述文档）：详细叙述
- `worldbook.json`（世界书条目）：再次详细描述

**后果：**
- 世界书 JSON 字符消耗量大，实际游戏只用到 ~1,165 字
- 同一内容在两处维护，同步成本高，易出错
- AI 调用世界书时产生逻辑混乱（两处表述不完全一致）

**根因：**
设计者未在设计前期明确"两份文件的分工边界"。

**✅ 正确做法（已验证）：**
- `worldbook.md`：**背景设定、NPC 身份、场景氛围、规则框架**（给人看/给 AI 做叙事参考）
- `worldbook.json`**精确数值、计算公式、触发条件、AI 专用执行说明**（AI 调用）
- `supplement.md`**设计师快速索引**（快速查数值用，不进游戏）

**→ 写入 skill：已更新"去重规则"章节（references/game_design_experience.md）**

### ❌ 错误二：游戏文件夹命名与文件命名混乱

**问题描述：**
```
/workspace/寒蝉末世/              ← 文件夹用中文
/workspace/寒潮末世_游戏状态.md   ← 根目录混用中文
/workspace/寒潮末世游戏设计稿_优化版.md
/workspace/game-dark-arena/       ← 世界书 md 文件 5 个版本
  worldbook.md
  worldbook_ai.md
  worldbook_clean.md
  worldbook_optimized.md
  worldbook_plain.md
```

**后果：**
- 多版本世界书内容不一致，AI 调用哪个产生歧义
- 维护成本极高，修改一处要同步改多个文件
- 中文文件夹在某些平台产生编码问题

**✅ 正确做法：**
- 文件夹：**英文或拼音**，如 `game-cold-apocalypse`、`game-dark-arena`
- 世界观描述文档：每游戏文件夹内统一命名为 `worldbook.md`（唯一入口）
- 中间版本文件不保留，直接覆盖
- JSON 输出文件统一命名：`[游戏代号]_worldbook.json`
- 游戏状态文件：`[游戏代号]_game_state.md`
- 设计存档：`[游戏代号]_design_archive.md`

**→ 写入 skill：已在 SKILL.md "文件管理规范" 中明确，执行良好**

## 三、游戏专项问题

### 寒蝉末世专属问题

#### ❌ 问题四：温度时间线在描述文档与任务简报中不一致

| 来源 | Day 1-10 | Day 11-20 | Day 21-30 | ... |
|------|---------|---------|---------|-----|
| 世界观描述（存档版） | 20→10°C | 10→0°C | 0→-10°C | ... |
| worldbook_task_briefing.md | 20→10°C | 10→0°C | 0→-10°C | ... |
| 寒潮末世游戏设计稿_优化版.md | **Day 1-25** | **Day 25-34** | **Day 35-44** | ... |

**后果：** 游戏进行中温度阶段划分出现矛盾，AI 难以准确推进剧情。

**✅ 修正方案：** 确认单一温度时间线基准，后续所有文档以此为准；建立 `balance_sheet.md` 作为数值总表。

#### ❌ 问题五：末日开始时间节点漂移

- `game_design_archive.md`：末日开始 Day 1
- `寒潮末世_游戏状态.md`：Day 0 = 末日爆发
- `寒潮末世游戏设计稿_优化版.md`：Day -13 开始囤货

**后果：** NPC 状态、物资消耗、剧情事件触发时间产生混乱。

**✅ 修正方案：** 建立 `game_timeline.md`，统一所有时间节点：
```
Day -13 to -1：末日前囤货期
Day 0：末日爆发
Day 1-100：生存期
Day 51：恢复3动作制（含夜间）
Day 98：终潮
```

#### ❌ 问题七：物资系统换算规则说明不足

**问题：** A/B/C/D 四类物资的"标准单位"换算规则在设计稿中存在但未同步进世界书 JSON，导致 AI 对物资增减的判定缺乏依据。

**✅ 修正方案：** 每类物资的单位换算表（已在优化版设计稿中整理）需同步生成 `supplement.md` 中的**设计师索引表**，确保数值可查、AI 行为可追溯。

### 暗黑狗斗专属问题

#### ❌ 问题八：世界书多版本未合并，AI 调用产生歧义

**问题描述：** 共生成 5 个 worldbook 版本，AI 实际调用的是 `worldbook_optimized.md`，但没有任何标记说明这是"正式版"。

**后果：** 设计者自己和 AI 都不确定哪个是最新/最完整版本。

**✅ 修正方案：**
- 世界书文件**只保留一个**：正式版直接覆盖 `worldbook.md`
- 中间版本存档至 `archive/` 子目录（而非散落根目录）
- 输出流程：草稿 → review → 覆盖 `worldbook.md`，不产生并列版本

---

#### ❌ 问题九：角色卡完成度参差不齐

| 角色 | 状态 |
|------|------|
| 沈婉清（团队经理） | ✓ 有姓名、职业、职能 |
| 林念水（格斗手A） | ✓ 完整姓名/背景/技能树 |
| 格斗手B-E | ✗ 仅有武术类型，无姓名/背景/性格 |

**后果：** 游戏叙事中格斗手 B-E 缺乏个性，AI 难以塑造差异化角色。

**✅ 修正方案：** 角色卡完成度标准：
- **核心角色**（前3名）：姓名 + 背景 + 性格 + 技能 + 人际
- **次要角色**：至少姓名 + 武术类型 + 性格关键词
- 设计流程中增加"角色卡完整度检查"，未达标不进入世界书生成阶段

---

#### ❌ 问题十：五行格斗系统过度复杂，首次设计试图一步到位

**系统设计：** 五行（水/火/土/木/金）+ 招式属性（相生相克）+ 技能树 + 解锁条件 + 基础威力 + 最终倍率

**问题：** 平衡性极难把控，初始数值需要大量测试；设计时间远超预期。

**✅ 修正方案：**
- **首次设计**：核心机制不超过 3 层规则
  - 寒蝉末世：物资 → 心情/信任度 → 背叛概率（3层 ✓）
  - 暗黑狗斗：武术类型 → 技能选择 → 五行（3层，过度了 ✗）
- **迭代策略**：先上线核心机制，验证后再叠加进阶层
- **简化推荐**：五行仅作叙事 flavor，不做数值克制；或克制表仅 3×3 而非 5×5

## 四、设计流程中的有效做法（保留）

### ✅ 做法一：supplement.md 的设计师索引功能

将所有数值型内容从 `worldbook.md` 抽离，集中于 `supplement.md`：
- 设计者：查数值 → 看 supplement
- AI：读世界书 JSON → 执行精确逻辑
- 各司其职，不冗余

### ✅ 做法二：三文档分工体系

```
worldbook.md         → 世界观背景（叙事层）
supplement.md        → 设计师索引（数值层）
game_state.md        → 运行时状态（动态层）
[游戏代号]_worldbook.json → Meimodu 导入（执行层）
```

### ✅ 做法三：游戏状态文件的"禁止透支"规则

寒蝉末世设计的四条动作计数规则（全局累计公示、透支暴露、透支结算、物资公示）有效防止了 AI 随意超发资源，是硬核生存游戏的必要约束。

### ✅ 做法四：NPC 心情崩溃阈值的双保险设计

心情数值 + 性格触发条件双重校验，避免 AI 仅凭数值做机械判断（如"心情 < 30 就崩溃"，而忽略性格因素）。

### ✅ 做法五：末日游戏的多阶段动作制

```
Day -13 to -1：3 动作/天（囤货期）
Day 1-50：    2 动作/天（生存高压期）
Day 51-100：  3 动作/天（夜间解锁，策略空间扩大）
```
动作制度的阶段性变化本身成为叙事节奏调节器。

## 五、对 skill 的具体改进建议

### 5.1 新增章节：设计验证检查表（Design Validation Checklist）

在现有"输出前自检清单"基础上，增加**设计完成后的专项验证**：

```
【数值一致性检查】
□ 同一 NPC 的心情/信任度数值在所有文档中一致
□ 温度/时间线在所有文档中一致
□ 物资换算规则同步至 supplement.md
□ 所有数值型内容确认来源（世界书 JSON or supplement.md，二选一不重复）

【世界书检查】
□ 世界书 JSON 无任何叙事内容与 worldbook.md 重复
□ 机制类条目仅存在于 JSON，背景描述仅存在于 md
□ 总字符数 ≤ 15,000
□ key 不超过 5 个，精准优先

【角色卡检查】
□ 核心角色：姓名 + 背景 + 性格关键词 + 初始数值 + 招募方式
□ 次要角色：至少姓名 + 类型 + 性格关键词
□ 无"待定"数值进入最终版世界书

【系统复杂度检查】
□ 核心机制层数：生存类 ≤ 4层，格斗类 ≤ 3层
□ 首次设计不尝试"完整系统"，优先核心闭环
□ 所有概率类规则有 fallback 描述（AI 无法精确计算时的叙事处理）
```

### 5.2 新增章节：常见错误速查表

```
【错误类型1：内容重复】
症状：世界书 JSON 某条目与 worldbook.md 内容高度重合
修复：从 JSON 中删除重复条目，保留数值计算部分

【错误类型2：数值漂移】
症状：NPC 心情/信任度在不同文档中数值不一致
修复：以 supplement.md 为准，修正其他文档

【错误类型3：多版本混乱】
症状：game/ 目录下有 3+ 个 worldbook 相关文件
修复：保留正式版，删除旧版本，建立 archive/ 子目录

【错误类型4：角色卡残缺】
症状：部分 NPC 角色卡缺少背景故事或性格关键词
修复：补全或明确标注"TBD—需用户确认"，未确认前不进入世界书

【错误类型5：机制过度复杂】
症状：系统设计超过 4 层嵌套规则
修复：拆分为"核心机制（v1）"+"进阶机制（v2）"，分阶段实现
```

### 5.3 修改"核心游戏系统设计规范"章节

**针对格斗类游戏额外增加：**

| 游戏类型 | 核心机制层数上限 | 数值复杂度上限 | 建议系统 |

## 【邪欲寄宿】设计复盘 · 2026-04-28

### 新增问题

#### ❌ 问题十一：时间推进机制自创，忽略 JSON 已有定义

**问题描述：**
设计初期，我在无 JSON 时自创了「每日行动槽 × 精力消耗」时间系统（三幕各设固定行动次数上限）。后用户指出有相关 JSON 文档（time-mechanism.json），读取后发现 JSON 明确规定为**三分制累计体系**：3次日常行动=推进1天，任务完成=推进1天，重要事件=推进3-5天。

**后果：**
- 原方案的时间系统与 JSON 定义完全不符
- AI 执行时若两套系统并存，将产生逻辑冲突
- 必须回炉重写第三部分（时间推进机制）

**根因：**
未在设计开始前完整检索该游戏的所有现有源文件（尤其是 JSON），先入为主地用逻辑推演代替了已有定义。

**✅ 修正方案（已执行）：**
- 设计启动时：**先检索** `/workspace/game-[代号]/` 目录下所有现有文件（.json / .md / .txt）
- JSON 文件优先级高于自创逻辑：JSON 是 AI 执行规范，文本是叙事参考
- 若发现已有 JSON 定义，**直接采用**，不在其上叠加自创体系
- 时间系统属于「精确执行逻辑」，必须以 JSON 为准

→ **写入 skill：设计启动流程第一步改为"源文件完整性检查"**

### 新增有效做法

#### ✅ 做法六：文档版本标注机制

**做法描述：**
在设计文档头部增加版本标注：
```
> 文档版本：v2.0（定稿·JSON修订版）
> 核心JSON来源：quest-timeline.json（任务序列）+ time-mechanism.json（时间推进）
> 文本来源：darkhost_1.0.0_condensed.md + 邪欲寄宿_final.md + worldbook-v3.md
```

**适用场景：**
- 存在多次修订的设计文档
- 有多个数据源的设计文档
- 需要 AI 判断「哪个版本最新」的场景

**效果：**

## 八、事件驱动角色数据系统（人格驱动解释引擎）

> 来源：邪欲寄宿·事件影响角色数据机制，2026-04-29
> 状态：**已验证可执行版**

---

### 8.1 系统定位

本系统用于：**事件发生后，通过可量化的计算链，驱动 NPC 属性变化并触发对应行为决策**。
适用于：GOT（欲望寄宿）、邪欲寄宿等以角色关系为核心驱动力的游戏。

---

### 8.2 输入层（每轮必须读取）

**事件向量 E（6维度）：**
| 维度 | 范围 | 含义 |
|------|------|------|
| P | -1 ~ 1 | 亲密（正向情感强度） |
| T | 0 ~ 1 | 威胁感 |
| B | 0 ~ 1 | 利益（身体/物质刺激） |
| C | 0 ~ 1 | 控制感 |
| I | 0 ~ 1 | 强度（事件烈度） |
| D | -1 ~ 1 | 意图（支配/服从方向） |

**NPC人格（6维度）：**
| 维度 | 范围 | 含义 |
|------|------|------|
| O | 0 ~ 1 | 开放性 |
| S | 0 ~ 1 | 抑制性 |
| K | -1 ~ 1 | 性癖匹配度（正值=正向匹配，负值=反向匹配） |
| M | 0 ~ 1 | 道德感 |
| R | 0 ~ 1 | 敏感性 |
| V | 0 ~ 1 | 控制欲 |

**关系初始值（4维度）：**
| 维度 | 范围 | 含义 |
|------|------|------|
| F | -100 ~ 100 | 好感 |
| D | 0 ~ 100 | 欲望 |
| T | 0 ~ 100 | 信任 |
| I | 0 ~ 100 | 依赖 |

---

### 8.3 计算链（强制顺序）

```
E（原始）→ E'（人格修正）→ E''（关系修正）→ Δ（强度修正）→ 属性 → 行为
```

**第一步：人格修正 E → E'**

```
P' = P × (1 + 0.5O - 0.5M)
T' = T × (1 + 0.6S + 0.4V)
B' = B × (1 + 0.3O)
C' = C × (1 + 0.5V - 0.3O)
I' = I × (1 + 0.5R)
D' = D × (1 + K)
```

**性癖匹配处理：**
- 若事件符合 NPC 性癖（K 与事件方向匹配）：
  - `P' += 0.5 × K × I`
  - 欲望额外 `+0.5 × K × I`

**第二步：关系修正 E' → E''（归一化后）**

```
F_n = F/100,  D_n = D/100,  T_n = T/100,  I_n = I/100

P'' = P' × (1 + 0.5F_n)
T'' = T' × (1 - 0.4T_n)
B'' = B' × (1 + 0.3F_n)
C'' = C' × (1 - 0.3F_n)
I'' = I' × (1 + 0.3I_n)
```

**第三步：强度修正（最终变化量）**

```
Δ = E'' × I_n × K_scene
```

**场景系数 K_scene：**
| 场景类型 | 系数 |
|---------|------|
| 日常 | 0.5 |
| 普通 | 1.0 |
| 剧情 | 1.5 |
| 强冲击 | 2.0 |

---

### 8.4 属性映射（计算后直接应用）

| 属性 | 公式 | 说明 |
|------|------|------|
| 好感度 | `P'' + B'' - T'' - C''` | 正向刺激减去负面刺激 |
| 欲望度 | `P'' + B'' + I''` | 情感 + 身体 + 亲密三者叠加 |
| 忠诚度 | `P'' - T'' - C''` | 正向减去威胁和控制 |
| 恐惧度 | `T'' + C'' - P''` | 威胁和控制减去正向 |
| 纯度 | `P'' - B'' - C''` | 正向减去身体和羞耻 |

所有结果限制在合理范围内（如 -100~100）。

---

### 8.5 行为评分系统

**关系使用规则（强制）：**
1. 关系(F, D, T, I) **仅用于** E'→E'' 修正步骤
2. **禁止**使用"当前属性值"替代关系原始值
3. 属性计算结果**不得反向参与**本轮计算
4. 若关系需要更新，必须**延迟到下一轮**生效

**行为评分公式（使用关系原始值，不是属性计算结果）：**
```
接近 = 0.6×好感 + 0.4×欲望 - 0.5×恐惧
互动 = 0.7×好感 + 0.3×信任
暧昧 = 0.8×欲望 + 0.2×好感
服从 = 0.6×恐惧 + 0.4×忠诚
回避 = 0.8×恐惧 - 0.3×好感
试探 = 0.5×控制欲 + 0.3×不确定性
```

**决策流程：**
1. 计算所有行为评分（保留小数）
2. 选择最高值作为本轮行为
3. 若最高值与次高值**差值 < 0.1** → 随机选择（避免机械感）

---

### 8.6 关系慢更新机制

关系值不在事件发生时直接修改，而是**每轮结束后更新**：

```
F_new = F_old + 0.1 × Δ好感
D_new = D_old + 0.1 × Δ欲望
T_new = T_old + 0.1 × Δ信任
```

更新后的关系值在**下一轮**事件处理时生效（本轮仍用旧值）。

---

### 8.7 执行约束（强制，不可违反）

```
【强制约束】
□ 每个 NPC 必须独立计算（禁止批量/平均处理）
□ 计算链必须完整经历：E → E' → E'' → Δ → 属性 → 行为
□ 禁止跳步骤（如：跳过 E' 直接用 E 计算属性）
□ 禁止主观判断替代计算结果
□ 同一事件不同 NPC 必须产生不同结果（至少 E' 阶段就产生差异）
□ 行为决策必须基于评分公式，不允许"感觉应该……"
□ Δ计算结果需记录到游戏状态文件（供下一轮慢更新使用）
```

### 8.8 伪代码参考（实现用）

```python
def process_event(npc, event_E):
    # E → E'：人格修正
    ep = {
        'P': event_E['P'] * (1 + 0.5*npc.O - 0.5*npc.M),
        'T': event_E['T'] * (1 + 0.6*npc.S + 0.4*npc.V),
        'B': event_E['B'] * (1 + 0.3*npc.O),
        'C': event_E['C'] * (1 + 0.5*npc.V - 0.3*npc.O),
        'I': event_E['I'] * (1 + 0.5*npc.R),
        'D': event_E['D'] * (1 + npc.K),
    }
    # 性癖匹配处理
    if match_kink(npc, event_E):
        ep['P'] += 0.5 * npc.K * event_E['I']
        extra_desire = 0.5 * npc.K * event_E['I']

    # E' → E''：关系修正（使用原始关系值，非属性）
    fn = npc.F/100; dn = npc.D/100; tn = npc.T/100; IN = npc.I/100
    epp = {
        'P': ep['P'] * (1 + 0.5*fn),
        'T': ep['T'] * (1 - 0.4*tn),
        'B': ep['B'] * (1 + 0.3*fn),
        'C': ep['C'] * (1 - 0.3*fn),
        'I': ep['I'] * (1 + 0.3*IN),
    }

    # Δ计算
    delta = {
        k: epp[k] * IN * scene_coeff
        for k in epp
    }

    # 属性映射
    attributes = {
        '好感': epp['P'] + epp['B'] - epp['T'] - epp['C'],
        '欲望': epp['P'] + epp['B'] + epp['I'],
        '忠诚': epp['P'] - epp['T'] - epp['C'],
        '恐惧': epp['T'] + epp['C'] - epp['P'],
        '纯度': epp['P'] - epp['B'] - epp['C'],
    }

    # 行为评分（使用关系原始值，非属性值）
    scores = {
        '接近': 0.6*npc.F + 0.4*npc.D - 0.5*(epp['T']+epp['C']-epp['P']),
        '互动': 0.7*npc.F + 0.3*npc.T,
        '暧昧': 0.8*npc.D + 0.2*npc.F,
        '服从': 0.6*(epp['T']+epp['C']-epp['P']) + 0.4*(epp['P']-epp['T']-epp['C']),
        '回避': 0.8*(epp['T']+epp['C']-epp['P']) - 0.3*npc.F,
        '试探': 0.5*npc.V + 0.3*uncertainty(npc),
    }

    behavior = max(scores, key=scores.get)
    return attributes, behavior, delta
```

| 隐瞒 | `0.5×V + 0.3×T（关系原始值）` | 隐藏关键信息 |
| 操控 | `0.8×V + 0.4×Strategic（谋略维度）` | 主动操控局势 |

**⚠️ 关键禁止规则：**

- 关系层与属性层**禁止混用**

### 9.5 行为强度公式

```
强度 = I × (主导属性 / 100) × (1 + R - S)
```

**变量定义：**
| 变量 | 含义 | 来源 |
|------|------|------|
| `I` | 事件烈度（0~1） | 来自事件向量E中的I维度 |
| `主导属性` | 行为评分中权重最高的属性值 | 例：回避行为→恐惧；反抗→V |
| `R` | NPC敏感度（0~1） | 第八章人格定义 |
| `S` | NPC抑制系数（0~1） | 第八章人格定义 |

**示例：** 表妹刘晓雨（O=0.55, S=0.75, R=0.90, V=0.10）执行回避行为，恐惧=68，主导属性=恐惧
```
强度 = 0.7 × (68/100) × (1 + 0.90 - 0.75)
     = 0.7 × 0.68 × 1.15
     = 0.547（≈54.7%）
```
→ 回避行为以约55%的强度执行（不是100%，符合高敏感NPC情绪波动特征）

### 9.6 行为选择规则

```
1. 计算所有行为评分（A类7个 + B类8个 = 15个）
2. 目标驱动修正（×1.5倍率）
3. 环境修正（叠加）
4. 选择评分最高者
5. 若最高值与次高值差值 < 0.1 → 随机选择其一
6. 若评分均为负或零 → NPC选择最低风险行为（逃离/回避）
```

### 9.11 设计示例：NPC决策行为计算（表妹刘晓雨 × 邪教仪式事件）

**场景：** Day 8，玩家前往废弃厂房参加召集令。表妹在窗口目睹玩家离开。

**输入：**
- 属性层（第八章计算结果）：好感=-1.197, 欲望=0.798, 恐惧=1.339（已映射为追踪轨：68/72/45/50/24）
- 关系层：F=70, D=50, T=50, I=20
- 人格：O=0.55, S=0.75, K=0.20, M=0.85, R=0.90, V=0.10, Strategic=0.15
- 环境：危险（目睹邪教）+ 敌对场景
- 目标：生存（恐惧修正×1.5适用）

**行为评分计算（以回避行为E为例）：**
```
回避 = 0.8×恐惧 + 0.3×V
     = 0.8×68 + 0.3×0.10×100  ← V为0-1，转换时×100
     = 54.4 + 3 = 57.4

环境修正（危险+敌对场景）：+0.3（回避）
目标修正（生存）：×1.5

最终评分 = 57.4 × 1.5 + 0.3 = 86.4
```

**其他候选行为：**
```
反抗 = 0.7×10 + 0.4×68 - 0.5×50 = 7 + 27.2 - 25 = 9.2
结盟 = 0.6×0 + 0.4×70 + 0.3×50 = 0 + 28 + 15 = 43（无利益驱动）
逃离 = 0.9×68 - 0.4×10 = 61.2 - 4 = 57.2
```

**决策：** 回避（86.4）vs 逃离（57.2）→ 回避胜出

**行为输出→剧情：** 回避 → 表妹选择与玩家保持距离 → 好感度降至65 → Q006任务中表妹作为祭品候选人的可用性下降 → 玩家需在Q006前修复关系或寻找替代祭品

| **L1** | 属性层（Agent State） | 个体状态：情绪/属性/能力 | 好感/欲望/恐惧/理智/精力 |
| **L2** | 关系层（Relational Graph） | Agent之间关系网络 | F/D/T/I（好感/欲望/信任/依赖） |
| **L3** | 势力层（Faction System） | 群体组织运行结构 | 资源/稳定性/情报/影响力/战略目标 |
| **L4** | 世界层（World Runtime） | 宏观规则与事件生成 | 灾难/战争/信息传播/崩溃/秩序变化 |

### 11.3 L3势力层（Faction System）

#### 与NPC阵营的关系（不同层级并存）

```
阵营（Narrative Tag）= L3势力的"外显标签投影"
L3 = 阵营的"真实运行系统"

映射规则：
Faction_Tag = f(L3战略目标 + 价值观权重)
```

| NPC阵营标签 | 对应L3势力系统 |
|------------|--------------|
| 正义守护者 | 正义阵营运行层：资源/稳定性/情报/影响力/目标 |
| 机会主义者 | 机会主义势力运行层：利益最大化逻辑 |
| 邪神信徒 | 邪教势力运行层：资源/稳定性/影响力/献祭目标 |
| 中立 | 无势力运行层支撑（或独立势力） |

**L3核心变量（每个势力必须定义）：**
| 变量 | 范围 | 说明 |
|------|------|------|
| 资源（Resource） | 0~100 | 势力物质基础，影响扩张能力 |
| 稳定性（Stability） | 0~100 | 内部凝聚力，影响存续 |
| 影响力（Influence） | 0~100 | 对其他势力/个体的控制力 |
| 情报能力（Intelligence） | 0~100 | 信息获取与传播能力 |
| 战略目标（Goal） | 枚举/向量 | 势力终极目标 |
| 核心资源 | 枚举 | 势力运转的关键资源 |
| 脆弱点 | 枚举 | 影响稳定性的关键因素 |

#### L3行为模块类型

| 模块 | 影响 | 说明 |
|------|------|------|
| 势力扩张 | L3资源/影响力↑ | 招募/掠夺/外交 |
| 势力渗透 | L2关系/L3稳定性↓ | 策反/情报/破坏 |
| 势力战争 | L3资源/稳定性↓ | 消耗资源，降低稳定性 |
| 势力崩塌 | L3→L4 | 稳定性=0时势力瓦解 |
| 势力重组 | L3结构变化 | 合并/分裂/领导更替 |

### 11.4 L4世界层（World Runtime Layer）

#### 与叙事层的关系（两套系统并存）

```
叙事层（Narrative Layer）= 表现结构（UI）
L4 = 运行引擎（Backend）
```

| 叙事层（表现） | L4（运行） |
|--------------|-----------|
| 表层现实/阴影层/深渊层 | 宏观事件生成 |
| 地理空间结构 | 冲突/灾难/秩序变化 |
| 描述"世界长什么样" | 生成"世界如何变化" |

**禁止：**
- 不允许用L4替代叙事结构（叙事层独立存在）
- 不允许叙事层参与数值计算
- 不允许跨层直接写死依赖

#### L4核心变量

| 变量 | 说明 |
|------|------|
| 世界稳定性（S） | 全局秩序/混乱程度，影响L4事件优先级 |
| 危险等级 | 宏观危险程度，影响所有NPC行为 |
| 信息传播度 |谣言/情报在系统中的扩散程度 |
| 资源分布 | 全局资源分配状态 |
| 事件日历 | 已触发世界事件的队列 |

#### L4事件模块类型

| 模块 | 影响 | 触发条件 |
|------|------|---------|
| 灾难事件 | L4危险↑/L3稳定性↓ | S<阈值 / 随机概率 |
| 冲突扩散 | L3战争 / L2敌对↑ | 势力战争爆发 |
| 信息传播 | L2关系变化 / L4危险 | 谣言/情报触发 |
| 秩序崩溃 | L4→L3重置 | S=0 |
| 秩序建立 | L4→L3稳定 | 特定条件满足 |

### 11.5 数据流规则（强制）

```
L1→L2→L3→L4（向上影响：个体事件→世界变化）
L4→L3→L2→L1（向下反馈：世界事件→个体影响）
```

**禁止规则：**
- 禁止跳层修改数据（如：L1直接修改L3）
- 禁止单模块跨三层直接写入
- 禁止绕过模块系统直接写死逻辑

**跨层数据流示例（合法路径）：**
```
L4事件（战争爆发）→ L3稳定性↓ → L2NPC恐惧↑ → L1行为变化（回避/逃离）
```

### 11.6 模块系统规范（核心设计）

#### 模块结构（每个模块必须定义以下五项）

```markdown
【模块名】：模块名称

【所属层级】：L1/L2/L3/L4

【输入依赖】：从哪些层读取数据（如：L1好感, L2信任, L3资源）

【计算逻辑】：作用于哪些变量（具体公式或描述）

【输出影响】：修改哪些层的数据（如：L1恐惧↑, L3稳定性↓）

【更新频率】：每轮/条件触发/事件触发

【优先级】：与同级模块冲突时的处理方式
```

#### 标准模块类型（预定义五类）

| 模块类型 | 所属层级 | 影响范围 | 示例 |

| **关系演化模块** | L2 | 关系层内部 | 好感增长、信任崩塌 |
| **势力行为模块** | L3 | 势力层内部 | 扩张、渗透、战争 |
| **世界事件模块** | L4 | 世界层内部 | 灾难、冲突、信息传播 |
| **信息传播模块** | L2/L3/L4 | 跨层影响 | 谣言扩散、情报获取 |

### 11.8 冲突解决机制

**层级优先级（从高到低）：**
```
世界层（L4）> 势力层（L3）> 行为层（L1→行为）> 属性层（L1）> 关系层（L2）
```

**同层冲突处理：**
- 使用权重加权平均
- 若差值 < 0.1 → 随机选择

**跨层冲突处理：**
- 高层级模块优先
- 低层级模块数据被覆盖但不丢失（记录原始值）

### 11.9 NPC执行标准流程（统一）

每个NPC每轮必须执行：
```
1. 读取L1/L2/L3/L4当前状态
2. 应用所有相关模块（按优先级排序）
3. 计算行为评分（L1属性 + L2关系 + L3势力 + L4环境）
4. 输出行为
5. 更新所有受影响层（L1→L2→L3→L4）
6. 写入下一轮状态
```

### 11.10 世界更新标准流程（每轮必须执行）

```
1. 收集所有Agent行为
2. 更新势力状态（L3：资源/稳定性/影响力变化）
3. 生成世界事件（L4：灾难/冲突/信息传播）
4. 反向影响关系与属性（L4→L3→L2→L1）
5. 更新世界稳定性S
6. 进入下一循环
```

### 11.11 L4与主线任务的动态优先级机制

**优先级切换规则：**
```
Priority = f(世界稳定性 S)

S ≥ 高阈值（>70）→ Q任务优先（L4作为环境扰动）
中阈值（30≤S≤70）→ L4与Q并行运行
S < 低阈值（<30）→ L4接管剧情（危机模式）
```

**危机模式触发条件：**
- 世界稳定性 S < 30
- 大规模事件发生（L4灾难）
- 势力战争爆发（L3冲突）

**L4事件可重写任务的规则：**
| 操作 | 条件 | 影响成本 |
|------|------|---------|
| 中断任务 | S < 30 | 高 |
| 改写任务条件 | S < 50 | 中 |
| 替换任务路径 | S < 30 | 高 |
| 添加支线任务 | 无限制 | 低 |

**⚠️ 限制：** L4事件重写主线后，必须在游戏状态文件中记录"任务变更日志"。
