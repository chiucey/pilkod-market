# Editorial pipeline

## Source order

Prefer official announcements, filings, release notes, research, developer posts, and first-party video; then reputable specialist reporting; then credible local-language industry media. Use community sources only for community reaction and label them.

Use live web research for every current briefing. Track publication date and event date separately. Link to direct sources rather than search results.

## Candidate record and selection

Record stable ID, issue date, content type, topic, region, language, source, title, factual summary, why it matters, URL, timestamps, image/thumbnail, confidence, duplicate group, editorial status, and approved localizations.

Verify link support, merge duplicate reports, balance importance and usefulness, separate fact from inference, and reject promotional filler, stale recycling, unsupported rumors, and unrelated imagery.

## Approval and recurring runs

For manual review, show candidate number, title, type, source/region, date, why it matters, and link. Preserve rejection reasons.

Each recurring run must determine the correct local issue date, search configured sources, verify/deduplicate/localize, create an approval queue or publish under an approved automatic policy, update archive/search data, validate output, and report partial failure instead of shipping broken content.

Store schedule timezone explicitly. Per-subscriber local delivery requires subscriber IANA timezones and duplicate protection; a single server cron is insufficient.
