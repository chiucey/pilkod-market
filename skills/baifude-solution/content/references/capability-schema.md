# 能力条目 Schema

每条能力是一个独立的 markdown 文件，存放在 `references/capabilities/` 目录下。skill 运行时按需读取这些文件做匹配。

## 命名规范

- **目录**：`references/capabilities/`
- **文件名**：kebab-case，如 `flexible-benefits.md`、`holiday-gift.md`、`employee-points.md`
- **能力 ID**：前缀 `BFD-` + 三位数字（如 `BFD-001`），按添加顺序递增，不可重复
- **统一用中文撰写能力名称和描述**（除非该能力本身就是英文术语）

## 模板

复制以下内容到 `references/capabilities/<kebab-name>.md`，按字段填空：

```markdown
# <能力中文名>

- **能力 ID**：BFD-XXX
- **所属模块**：<员工激励 / 福利发放 / 健康关怀 / 数据看板 / 节日福利 / 积分商城 / 弹性福利 / 长期激励 / 员工关怀 / ...>
- **适用场景**：
  - <典型场景 1，如"新员工入职礼包">
  - <典型场景 2，如"中秋/春节节日福利发放">
  - <典型场景 3，如"员工激励积分兑现">
- **核心功能**：
  1. <一句话功能 1>
  2. <一句话功能 2>
  3. <一句话功能 3>
- **客户价值**：
  - 业务价值：<如"提升员工福利感知度"、"降低 HR 福利发放人力">
  - 数字化价值：<如"福利发放数据可追溯"、"自动对账">
- **对接要求**：
  - 单点登录：<支持飞书/钉钉/企微/自建 SSO/无需>
  - 数据接口：<需要哪些客户侧数据，如员工花名册、组织架构>
  - 实施周期：<从开通到上线典型周期，如"1-2 周">
- **典型客户场景**（1-2 个真实脱敏案例）：
  - <场景 1：客户背景 + 用了什么能力 + 解决了什么问题>
  - <场景 2：...>
- **注意事项 / 限制**：
  - <合规要求，如"个保法要求 PII 数据本地化">
  - <能力边界，如"暂不支持海外员工币种结算">
  - <常见误用，如"不建议用于高频小额发放，建议单笔 ≥ XX 元">
- **关联能力**：
  - 强关联：<通常会一起推荐的能力 ID>
  - 替代关系：<可被哪些能力替代>
```

## 怎么新增一条能力

1. **复制模板**到 `references/capabilities/<kebab-name>.md`
2. **填写所有字段**（除"关联能力"可后补，其他都建议一次填齐）
3. **分配能力 ID**：打开 `_index.md`，看现有最大 ID 编号 +1
4. **更新索引**：在 `_index.md` 的"已收录能力"表格里追加一行
5. **不需要重启**，skill 下次触发时自动可用

## 怎么写一个"好的"能力条目

- ✅ **场景具体**："500 人制造业企业，中秋节日福利发放" 比 "福利发放" 好
- ✅ **客户价值量化**：能写数字就写数字，写不出就写定性
- ✅ **限制诚实**：把不适用的场景写清楚，避免销售过度承诺
- ❌ **不要写营销话术**："业界领先"、"行业第一" 之类不要写
- ❌ **不要写未上线功能**：草稿中待上线的能力标记为"⏳ 规划中"，不要混入已交付能力

## 字段填写小贴士

- **适用场景** 这一栏最重要，直接决定售前匹配效果。至少写 3 个具体场景。
- **对接要求** 缺失会导致技术类问题回答不到位。
- **典型客户场景** 不需要写很多，1-2 个脱敏的就行，但必须有具体数字（如"覆盖 3000 员工，提升福利使用率 40%"）。
