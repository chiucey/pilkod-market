# IT基础设施需求调研报告撰写

基于委托方提供的能力需求清单，对目标市场进行全面调研，产出结构化资源清单和覆盖矩阵。

**核心原则：验证优先，宁缺毋滥，诚实标注。**

---

## Phase 0：需求理解与 Checklist 化

### 0.1 输入信息收集

| 信息项 | 说明 | 获取方式 |
|--------|------|----------|
| 委托方背景 | 项目介绍、核心功能、运行平台 | 用户提供或需求文档 |
| 能力需求清单 | 按优先级(P0/P1/P2)组织的能力需求 | 需求文档 |
| 调研市场范围 | 各梯队市场及调研深度 | 需求文档 |
| 交付物要求 | 报告格式、包含章节 | 需求文档 |

### 0.2 需求 Checklist 提取（必做）

收到需求文档后，第一步是逐条扫描文档中所有"调研重点""特别关注""重点调研"关键句，提取为一份 checklist。

**输出格式：**

```markdown
## 调研 Checklist

### 需求1：[名称]
- [ ] [调研重点1，原文摘录]
- [ ] [调研重点2，原文摘录]

### 需求2：[名称]
- [ ] [调研重点1]
...
```

此 checklist 贯穿全流程：
- Phase 1 搜索时，每条搜索必须关联到至少一个 checklist 项
- Phase 2 写入时，每个 checklist 项必须有对应资源或显式"未找到"
- Phase 4 自检时，逐条核对 checklist 覆盖情况

### 0.3 触发前确认

- [ ] 是否已提取需求 checklist
- [ ] 是否明确了调研市场优先级
- [ ] 是否确认了交付物格式要求
- [ ] 是否理解了每项能力的具体定义和调研重点
- [ ] 是否知晓了不在调研范围内的内容（适配评估、接入实现、成本对比、委托方内部逻辑）

---

## Phase 1：搜索与验证（先查后写）

### 1.1 分段执行，按优先级推进

**不要一次性搜索所有需求。按 P0 → P1 → P2 分段执行。**

每段流程：
1. 搜索该优先级下的所有需求
2. 对搜索到的资源逐个验证关键信息
3. 生成该段的资源清单和覆盖矩阵
4. 执行段内一致性检查（Phase 3）
5. 确认无误后，再进入下一优先级

### 1.2 搜索记录要求

每条搜索记录必须关联目标需求编号：

| 搜索日期 | 搜索渠道 | 关键词 | 目标需求 | 结果数量 |
|----------|----------|--------|----------|----------|
| YYYY-MM-DD | GitHub | search MCP server | 需求1 | 15 |

### 1.3 验证规则（强制执行）

**每个资源写入报告前，必须验证以下字段：**

| 字段 | 验证方式 | 不可验证时的处理 |
|------|----------|------------------|
| 仓库地址 | 访问 URL 确认页面存在 | 标注 ⚠️ 待验证 |
| Stars 数 | 从 GitHub 页面提取 | 写"未确认"，不得估算 |
| 接入命令 | 从 README 或官方文档复制 | 标注"需确认" |
| 活跃度 | 查最近 commit 日期或更新记录 | 写"未确认" |
| 语言栈 | 确认是 TypeScript/Python/Go 等 | 标注"未确认" |

**绝对禁止：**
- 从记忆中"回忆"Stars 数、仓库地址、安装命令
- 对无法验证的信息填写看似合理的估计值
- 将一个工具的接入方式套用到另一个工具上

### 1.4 验证状态三级标注

每个资源条目必须带验证状态标签：

| 标签 | 含义 | 使用条件 |
|------|------|----------|
| ✅ 已验证 | 关键信息已从源页面确认 | 仓库可访问、Stars/接入命令已核实 |
| ⚠️ 待验证 | 信息来源不确定或仓库无法访问 | 二手信息、页面不可达 |
| ❌ 不可用 | 确认已失效或不存在 | 404、项目已归档 |

**规则：⚠️ 待验证的资源不得在覆盖矩阵中标注"完全覆盖"。**

## Phase 2：文档生成

### 2.1 报告结构

报告必须包含以下章节（参见 `references/report-template.md`）：

1. **背景**（项目简介、调研目的、当前运行环境）
2. **能力需求清单**（P0/P1/P2 表格）
3. **调研过程记录**（调研市场范围、搜索记录、信息验证记录）
4. **资源清单**（按需求编号组织，每个需求含空白说明）
5. **能力覆盖矩阵**
6. **空白区域**（完全空白 + 部分覆盖）
7. **调研结论与建议**
8. **附录**（资源汇总表、修改记录）

### 2.2 资源条目标准格式

```markdown
#### 资源N：[资源名称]

- **类型**: MCP / Skill / Agent框架 / 第三方服务（标注语言栈：TypeScript / Python / Go 等）
- **能力描述**：一句话说明它能做什么
- **接口规范**：
  - 调用方式、tools 列表、输入输出格式
- **接入方式**：
  - **TypeScript版（npx/npm）**: `npx @xxx/xxx`（如适用）
  - **Python版（uvx/pip）**: `uvx xxx`（如适用）
  - 其他方式（Docker 等）
- **是否开源**: 是/否
  - 仓库地址：[完整 URL]
  - Stars: [具体数字]
- **活跃度**：最近更新时间、commits 数、维护状态
- **验证状态**: ✅ 已验证 / ⚠️ 待验证 / ❌ 不可用
- **备注**：限制、已知问题、风险提示
```

### 2.3 特殊标注规则

**语言栈标注**：对于 modelcontextprotocol/servers 等同时有 TypeScript 和 Python 实现的仓库，必须分别列出两种接入方式，不得混用 npx 和 uvx。

**低活跃度风险提示**：Stars < 50 或 commits < 10 的资源，必须在备注中标注"活跃度较低，生产环境慎用"。

**未验证资源处理**：仓库无法访问的资源应降级到"待验证资源"附录，不列入正式资源清单主体。如必须列入正文，需在类型行标注 ⚠️ 并在备注中说明。

### 2.4 每个需求必须包含"空白说明"

在每个需求的资源列表末尾，增加一个"空白说明"小节，显式回应需求文档中的调研重点：

```markdown
#### 空白说明

**需求X特别说明**：
- ✅ [已找到的能力]：[资源名称]（已验证）
- ⚠️ [部分找到的能力]：[资源名称]（待验证）
- ❌ [未找到的能力]：经调研未找到可用资源，原因：[说明]
```

### 2.5 覆盖矩阵填写规则

| 标注 | 含义 | 使用条件 |
|------|------|----------|
| 完全覆盖 | 能 100% 满足该能力需求 | 仅限 ✅ 已验证资源 |
| 部分覆盖 | 能满足部分需求 | ✅ 或 ⚠️ 资源均可 |
| 部分覆盖（需XX） | 有条件限制 | 需标注具体限制条件 |
| ⚠️ 待验证 | 资源本身未验证 | 仅限 ⚠️ 资源 |
| — | 不覆盖该能力 | |

## Phase 3：一致性自检（生成后必做）

**每段（P0/P1/P2）生成后、以及全文完成后，必须执行以下 checklist：**

### 3.1 交叉一致性检查

```
□ 每个资源在正文、覆盖矩阵、空白说明中的验证状态标注一致
□ 覆盖矩阵中没有标注"完全覆盖"的 ⚠️ 资源
□ 验证记录表覆盖了资源清单中的所有条目
□ 空白说明中引用的资源状态与正文一致
□ 覆盖矩阵中的覆盖度描述与空白区域章节不矛盾
```

### 3.2 格式规范检查

```
□ 章节编号连贯无跳跃（特别是子编号如 4.8.x 而非 4.4.x）
□ 所有仓库地址为完整 URL（https://github.com/...）
□ ⚠️/✅/❌ 标记语义全文档统一
□ 同一资源的 Stars 数在正文、验证表、附录中一致
□ 接入命令与标注的语言栈匹配（npx 对应 TypeScript，uvx 对应 Python）
```

### 3.3 需求覆盖检查

```
□ Phase 0 提取的调研 checklist 每项都有对应资源或显式"未找到"
□ 调研市场范围表中声称调研的每个市场，在资源清单中有实际产出或诚实说明"未找到相关资源"
□ 搜索记录中的每个目标需求在资源清单中有对应章节
```

## Phase 4：交付

### 4.1 交付物

- 主文件：Markdown 格式调研报告
- 附带修改记录（如有多版本迭代）

### 4.2 分工边界

| 调研方负责 | 委托方负责 |
|------------|------------|
| 找到有什么资源 | 评估适不适合 |
| 记录能力描述和接口规范 | 做适配测试 |
| 验证资源的可用性和活跃度 | 写基建测试报告 |
| 诚实标注空白区域和未验证项 | 决定是否接入 |

**原则**：告诉委托方货架上有什么，委托方自己决定买不买。不为了报告好看而填入无关或未验证的资源。

## 调研资源类型参考

| 资源类型 | 调研深度 | 记录字段 |
|----------|----------|----------|
| MCP 服务 | 重点：完整 7 字段 + 验证状态 | 完整记录 |
| Skill | 了解：名称、能力范围、依赖条件 | 概要记录 |
| Agent 框架 | 了解：能力集成方式 | 概要记录 |
| 插件/工具市场 | 浏览筛选与需求相关的资源 | 关联记录 |

## 搜索关键词策略参考

```
通用：MCP Server 列表、AI Agent 工具生态、awesome-mcp-servers
专项（按需求适配）：
  - 搜索类：search MCP server, web search API, news search, academic search
  - 存储类：file storage MCP, KV store, document database, Git sync
  - 并行类：task orchestration, parallel execution framework
  - 网页获取：web scraping MCP, Jina reader, Firecrawl
  - 定时类：cron job scheduler, scheduled task MCP

```

## 不在调研范围内的

1. **适配性评估**：适不适合由委托方自行测试
2. **接入实现**：怎么接入、代码怎么写不在范围
3. **成本对比**：定价对比不在范围（可顺便记录）
4. **委托方内部逻辑**：不需要理解委托方的业务细节
