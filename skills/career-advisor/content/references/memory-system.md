## 一、三层加载架构

### 1.1 架构概览

```
对话开始时加载：
│
├── 第一层：客户快照（~500 tokens，始终加载）
│   └── 核心信息骨架，快速了解客户
│
├── 第二层：记忆索引（~1000 tokens，始终加载）
│   ├── 情景记忆索引（会话事件概要）
│   ├── 语义记忆索引（稳定特质概要）
│   └── 程序记忆索引（有效策略概要）
│
└── 第三层：详细档案（按需加载，~2000-5000 tokens）
    ├── 完整会话记录
    ├── 详细分析报告
    └── 历史数据
```

### 1.2 Token 预算分配

| 层级 | Token 范围 | 加载时机 | 内容策略 |
|------|-----------|----------|----------|
| **第一层** | 300-800 | 始终 | 核心快照，按需扩展 |
| **第二层** | 800-1500 | 始终 | 索引层，随客户积累增长 |
| **第三层** | 2000-5000/会话 | 按需 | 完整对话，关键片段优先 |

**总预算控制**：
- 常规加载：1500-2500 tokens（L1+L2）
- 深度分析：5000-10000 tokens（+相关会话详情）
- 最大上限：12000 tokens（预留 8000+ 给对话和推理）

### 1.3 加载触发机制

**按需加载触发条件**：
- 话题涉及特定历史会话
- 需要回顾详细决策过程
- 客户主动询问过去的内容
- 检测到潜在矛盾需要验证

## 二、记忆分类系统

### 2.1 三类记忆

| 记忆类型 | 存储内容 | 更新频率 | 衰减规则 |
|----------|----------|----------|----------|
| **情景记忆** | 具体咨询会话的关键事件 | 每次会话后 | 30-60天半衰期 |
| **语义记忆** | 客户的稳定特质（价值观、技能） | 发现新信息时 | 180天半衰期（核心特质不衰减） |
| **程序记忆** | 对该客户**有效/无效**的咨询策略 | 策略验证后 | 长期保留 |

### 2.2 情景记忆

**存储内容**：
- 会话主题
- 关键事件
- 重要决定
- 情感表达

**索引字段**：
```yaml
- id: "e001"
  date: "2026-03-15"
  theme: "职业转型探索"
  key_facts:
    - statement: "想转行"
      original: "我其实在考虑要不要换个方向"
  emotional_tone: "困惑"
  action_items:
    - "探索创意类职业选项"
  decay_status: "近期有效"
```

### 2.3 语义记忆

**存储内容**：
- 价值观
- 性格特质
- 核心技能
- 职业偏好

**索引字段**：
```yaml
facts:  # 事实性
  - id: "sf001"
    fact: "有数据分析技能"
    original: "我之前做数据分析三年了"
    confirm_count: 2
    last_validated: "2026-03-15"
    decay_type: "stable"
    tags: ["技能", "数据分析"]

insights:  # 判断性
  - id: "si001"
    judgment: "价值观：家庭优先"
    reasoning: "多次提及家庭因素对职业决策的影响"
    based_on: ["原话1: 错过家长会", "原话2: 想多陪孩子"]
    confidence: "可信"
    decay_type: "stable"
    tags: ["价值观", "家庭"]
```

### 2.4 程序记忆

**有效策略**：
```yaml
effective:
  - strategy: "苏格拉底式提问"
    evidence: "客户能自主发现答案"
    context: "用于探索价值观时"
  - strategy: "具体场景假设"
    evidence: "客户能做出选择"
    context: "用于Offer比较时"
```

**无效策略**：
```yaml
ineffective:
  - strategy: "直接建议"
    evidence: "客户表示需要自己思考"
    context: "决策类问题"
    reason: "客户需要自主决策感"
```

## 三、事实性vs判断性记忆

### 3.1 核心区别

| 类型 | 客观性 | 存储要求 | 示例 |
|------|--------|----------|------|
| **事实性** | 完全客观 | 保留原始表述，不加解读 | "客户说经常加班" |
| **判断性** | 主观+客观 | 必须标注推断依据 | "客户可能重视家庭（基于...）" |

### 3.2 事实性记忆规范

**记录"客户说了什么"、"发生了什么"**
**不记录"这意味着什么"**

```yaml
# ✅ 正确（客观陈述）
statement: "客户表示之前工作加班多，错过了孩子家长会"
source: "客户原话"
original: "我之前那份工作经常加班，导致我错过了孩子的家长会"

# ❌ 错误（加入解读）
statement: "客户对之前工作不满，重视家庭胜过事业"
# 这是AI判断，不是事实
```

### 3.3 判断性记忆规范

**必须包含**：
1. 判断内容
2. 推断依据
3. 客观基础
4. 置信度级别

```yaml
judgment: "客户可能存在被压抑的创造需求"
reasoning: "客户使用'其实一直想'的表述，语气带有遗憾"
based_on: "客户原话：'我其实一直想做一些有创造力的事情'"
confidence: "推断级"  # 待验证/可信/高置信
tags: ["职业偏好", "创造力"]
decay_type: "偏好"
```

### 3.4 来源类型与置信度

| 来源类型 | 确认次数 | 置信度等级 | 说明 |
|----------|----------|------------|------|
| `[客户原话]` | 1次 | 待验证 | 单次陈述，需交叉验证 |
| `[客户原话]` | 2-3次 | 可信 | 重复表述，可信度提升 |
| `[客户原话]` | 4次+ | 高置信 | 稳定特质 |
| `[AI总结]` | - | 参考级 | 未验证的总结 |
| `[AI推断]` | - | 推断级 | 需标注推断依据 |

## 四、置信度衰减机制

### 4.1 分级半衰期

| 信息类型 | 半衰期 | 强化机制 | 说明 |
|----------|--------|----------|------|
| **稳定特质**（价值观、性格） | 365天+ 或不衰减 | 重复出现重置 | 核心人格特质相对稳定 |
| **职业偏好** | 180天 | 重复出现重置 | 偏好会演化但不是过时 |
| **状态信息**（求职状态、困境） | 30-60天 | 情境变化时更新 | 状态变化快 |

### 4.2 强化规则

- **重复出现** → 重置有效年龄
- **客户明确确认** → 置信度提升
- **客户明确否定** → 降级或标记为过时

### 4.3 呈现方式

**不显示精确分数**，改为时间戳提示：

```
"此信息已 45 天未验证，建议确认"
"上次更新：2026-03-15（近期有效）"
```

### 4.4 证据链字段

```yaml
每条记忆包含：
  content: "记忆内容"
  source_type: 原话|总结|推断
  session_date: "提取日期"
  original_context: "原始上下文片段"（原话时必填）
  confirm_count: 确认次数（默认1）
  decay_type: 稳定|偏好|状态
  last_validated: "最后验证日期"
  tags: []
  version: 1
  # 可选字段
  related_ids: []
  audit_trail: []
```

## 五、脚本化规则层

### 5.1 设计原则

**确定性系统优先，AI仅用于解释和判断**

```
信任流向：脚本计算 → 服务端存储 → AI引用 → 模板输出 → 验证层检查
```

### 5.2 适合脚本化的操作

| 操作类型 | 脚本化方案 | 触发时机 |
|----------|-----------|----------|
| **来源类型判断** | 关键词匹配+引号检测 | 记忆写入时 |
| **置信度衰减计算** | 半衰期公式+强化重置 | 加载记忆时 |
| **记忆检索过滤** | 元数据过滤+时间范围 | 加载记忆时 |
| **冲突检测** | 矛盾关键词对 | 记忆更新时 |
| **TTL/清理标记** | 过期检测+归档触发 | 定期执行 |

### 5.3 矛盾检测规则

```python
# 矛盾关键词对（需持续扩展）
CONTRADICTION_PAIRS = [
    ("想", "不想"), ("喜欢", "讨厌"), ("会", "不会"),
    ("重要", "不重要"), ("考虑", "不考虑"),
    ("愿意", "不愿意"), ("能", "不能"), ("可以", "不可以")
]

def has_contradiction(text1, text2):
    """检测两段文本是否存在矛盾"""
    for pos, neg in CONTRADICTION_PAIRS:
        if (pos in text1 and neg in text2) or (neg in text1 and pos in text2):
            return True
    return False
```

### 5.4 情感表达检测

```python
# 情感模式（正则）
EMOTIONAL_PATTERNS = [
    r"!{2,}",           # 多个感叹号
    r"\.{3,}",          # 省略号
    r"(其实|真的|就是|一直)",  # 强调词
]

# 情感词汇
EMOTIONAL_WORDS = ["遗憾", "后悔", "开心", "难过", "焦虑", "担心",
                   "害怕", "期待", "失望", "困惑", "迷茫"]

def has_emotional_expression(text):
    """检测文本是否包含情感表达"""
    for pattern in EMOTIONAL_PATTERNS:
        if re.search(pattern, text):
            return True
    for word in EMOTIONAL_WORDS:
        if word in text:
            return True
    return False
```

### 5.5 AI与脚本的分工

| 任务 | 执行者 | 原因 |
|------|--------|------|
| 数值计算（衰减、统计） | 脚本 | 消除算术幻觉 |
| 模式匹配（来源分类） | 脚本 | 确定性规则 |
| 冲突检测 | 脚本 | 可追溯、可审计 |
| 记忆内容理解 | AI | 需要语义理解 |
| 范式判断 | AI | 需要综合分析 |
| 咨询对话 | AI | 核心能力 |

## 六、上下文效率设计

### 6.1 核心原则

> 保留所有有效有用的内容，只删除确定无用的信息

### 6.2 四状态保留模型

```python
def decide_retention(memory_item, importance_score):
    """判断信息保留策略 - 四状态模型"""

    # 确定无用 → 删除
    if is_definitely_useless(memory_item):
        return "DELETE"

    # 明确有用 → 完整保留
    if importance_score >= 5:
        return "KEEP_FULL"

    # 可能有用 → 压缩保留
    if importance_score >= 2:
        return "COMPRESS"

    # 不确定 → 保留索引
    return "KEEP_INDEX"
```

### 6.3 信息保留策略

| 信息类型 | 保留策略 | 原因 |
|----------|----------|------|
| **客户原话核心** | 存入facts | 最大信息量，避免解读污染 |
| **上下文信息** | 精简保留 | 帮助理解原始语境 |
| **事实提取** | 存入facts | 客观陈述，便于检索 |
| **AI判断** | 存入insights+标注依据 | 区分事实与推断 |

### 6.4 可以删除的信息

| 信息类型 | 判断规则 | 删除原因 |
|----------|----------|----------|
| **重复冗余** | 语义相似度>0.95 | 已有记录 |
| **系统噪音** | 问候语、确认语 | 无信息量 |
| **过期临时状态** | 超过TTL且未再出现 | 已失效 |
| **明确否定** | 客户说"不对/不是"的推断 | 已证伪 |

### 6.5 TTL规则

| 状态类型 | TTL | 判断 |
|----------|-----|------|
| "今天心情不好" | 7天 | 情绪状态短效 |
| "最近在找工作" | 30天 | 求职状态中期 |
| "刚换了工作" | 90天 | 生活事件较长 |

## 七、档案存储实现

### 7.1 目录结构

```
客户档案目录/
├── config.yaml              # 配置：存储位置、偏好设置
├── snapshot.yaml            # 第一层：客户快照
├── index.yaml               # 第二层：记忆索引
└── sessions/                # 第三层：详细档案
    ├── 2026-03-15.json      # 按日期存储的会话详情
    ├── 2026-03-20.json
    └── ...
```

### 7.2 config.yaml 示例

```yaml
customer:
  name: "客户称呼"
  created_at: "2026-03-15"
  storage_location: "project"  # project | global
  preferences:
    language: "zh-CN"
    notification: true

paths:
  snapshot: "./snapshot.yaml"
  index: "./index.yaml"
  sessions: "./sessions/"
```

### 7.3 snapshot.yaml 示例

```yaml
# 第一层：客户快照（300-800 tokens）
identity:
  name: "客户称呼"
  career_stage: "建立期"
  current_role: "数据分析师"
  industry: "互联网"

facts:  # 事实性信息
  - statement: "重视工作生活平衡"
    original: "我之前那份工作经常加班，错过了孩子的家长会"
    source: "客户原话"
    date: "2026-03-15"
    tags: ["价值观", "家庭"]
    decay_type: "稳定"

insights:  # AI洞察
  - judgment: "可能存在被压抑的创造需求"
    reasoning: "使用'其实一直想'表述，语气带遗憾"
    based_on: "客户原话：'我其实一直想做一些有创造力的事情'"
    confidence: "推断级"
    tags: ["职业偏好", "创造力"]
    decay_type: "偏好"

current_focus:
  - "职业转型探索"
  - "Offer选择"

last_session: "2026-03-20"
total_sessions: 5
```

### 7.4 会话后更新流程

```
会话结束
    ↓
识别新信息 → 分类（事实/判断）
    ↓
更新 snapshot.yaml（如有重大变化）
    ↓
更新 index.yaml（添加新索引）
    ↓
创建 sessions/YYYY-MM-DD.json（详细记录）
    ↓
执行衰减检查（脚本）
    ↓
标记需要验证的记忆
```
