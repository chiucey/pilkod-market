# 零件标签信息提取

把一张标签照片变成一个可交付的 JSON 文件。核心约束：**先逐字转写，再归类映射**；看不清就留空并写进 `parse_note`，不要猜。

## Inputs to collect

- **图片**：附件或工作区路径。没有图片就别动手，先要图。
- **字段模板**：用户给了 JSON 模板 → key 严格照抄，一个字都不改（见 Step 5）。
- **输出位置**：默认工作区 `output/<图片名>.json`；用户指定目录就用他的。
- **批量**：多张图 → 每张一个文件；要不要额外汇总，等用户说。

## Procedure

1. **打开图片**。用 `read` 工具读（jpg/png/webp 直接可视化）。照片里标签只占一小块时，先圈出标签区域再逐块读，别对着整张图猜。
   **每张图最多读 2 次**（原图 + 一次裁剪/放大/增强）。两次都读不出来就按不可读处理，直接走 Failure handling 出文件继续下一张。理由：批量场景下一张废图能拖住整个批次——反复调试图不会让糊掉的字变清楚，只会把时间耗光、后面几十张排不上。增强产生的临时文件放 `.scratch/`，别污染 `output/`。

2. **逐字转写**。先不管字段名，按图上排版从上到下、从左到右把每行字符原样写出来（含标点、连字符、空格）。
   原因：一边转写一边往模板字段里塞值，模型会不自觉地往"预期答案"上靠，把看不清的字补成看起来合理的值——这是 OCR 最常见的错误来源。

3. **按规则归一化**。用 `references/field-mapping.md` 的字符混淆表处理转写结果：
   - 只在上下文能确定时替换（`-A-Z0-9-` 编码里的 `(` 只能是 `0`；人名/自由文本里的 `0` 不要动）
   - **归一化本身不写进 `parse_note`**（破折号统一、删字距空格、`0` 与 `O` 的字形比对——这些是规范执行，不是质量信息）。只有替换本身可能有争议、值真被改错了，才在 Step 6 点名
   - 日期保持图上原样（`20240404` 不要自作聪明改成 `2024-04-04`），除非用户要求归一化
   - **版式先验**：同类标签的**位置**是固定的（品号/件号在左上、日期/批次在右上之类），位置可以用来确定"这个位置是什么字段"。
     **位置只定身份，不定值**——品号和件号的写法没有固定规则，别拿上一张的值或某个正则去套这一张。连续处理多张同类标签时，前面几张读准的是**位置字典**（哪个位置放什么），不是**值模板**。

4. **定 label_type**。零件标签**只有一种版式，恒为 `零件标签`**，照抄即可，不用判断、不用解释。
   换成别类标签时按版式 + 内容判断，取值见 `references/field-mapping.md` 第四节。判定优先级：
   - **纸上不只有零件信息 → 不是零件标签**。判据是"只有"，不是"含有"：除了品号 / 件号 / 生产日期 / 批次号，还印着车辆信息、故障描述、单据编号之类**别的类别信息** → 停手，按那些信息归类（印着"维修单号"就是维修标签，交 `repair-label-to-json` 技能）。
   - 用户在对话里说过"这类标签固定是 X" → 直接用他的，`parse_note` 不用提。
   - **模板 JSON 里那个 `label_type` 字面值是示例，不是真值**。示例模板的字段值经常只是随手写的样板——和实际版式冲突时**以版式为准**，并按 Step 6 表格最后一行写一句结论。
     原因：`label_type` 是下游做路由和分流的键，猜错的代价远大于多写一句备注；反过来为迁就模板写错类型，整批数据都会分流到错的地方。字段名可以照抄模板，类型不行。

5. **填值：先猜，再留空**。零件标签按 `references/layout-零件标签.md` 的版位表走，那份表已经钉死了四个字段的位置和顺序，不用再推断字段身份。
   - 用户给了模板：模板里每个 key 都要出现。
   - **有先验就填**：字迹有缺损，但位置 + 上下文能定下来（同一版位上该位置放什么、同一张标签上其他字符的形态），按最可能的读法填上，并在 `parse_note` 把这个字段点名进去（Step 6）。
   - **没先验才留空**：该位置压根没有可辨认的字迹 → 空字符串 `""`，在 `parse_note` 点名这个字段并带一句留空原因。
   - **"格式看起来不对"不是留空的理由，也不是改写的理由。** 品号和件号的写法没有固定规则，别拿正则去"纠正"它们——详见 `references/field-mapping.md` 第三节。同理也**不要**从别的字段倒推这个字段（拿批次号反推日期之类），那是编数据不是识别。
   - 用户没给模板：零件标签直接用版位表的四个 key，顺序照版位表。其它标签才需要靠值形状反推，见 `references/field-mapping.md`。

6. **写 parse_note**。只回答一个问题：**哪个字段（或哪个判断）不能直接用**。
   照下面挑一句，别自己扩写：

   | 情况 | 写法 |
   |---|---|
   | 有字段存疑（推出来的、拿不准的） | `生产日期、批次序号存疑，建议人工核对` |
   | 有字段留空 | `生产日期、批次序号留空（字迹被遮挡）` |
   | 两者都有 | `生产日期留空（字迹被遮挡）；批次序号存疑，建议人工核对` |
   | `label_type` 判断没底 | `按 A 判为 B，可能应归为 C` |
   | 一切正常 | `无明显异常` |

   **点名字段，不解释过程。** 不写"第 4 位被污渍覆盖按日期格式推为 5"，写"生产日期存疑"就够——复核的人会自己去翻那一位是谁。写得越细，下游和抽检的人越容易只读备注不看图。

   **不写**：归一化记账（长破折号统一成 `-`、删字距空格、`0` 与 `O` 的字形论证）、字段是怎么按版位映射出来的、模板与实物的对照说明。这些是过程和惯例，不是质量信息，写进来只会稀释真正的不确定。

   **没有例外**：不追加"替换说明"分句，也不追加条码 / 厂内标记分句。上表五种写法就是全部——有争议的替换本身就是"该字段存疑"，点名字段已经说完了；条码和版位外的标记不进字段、也不进备注。

   硬性纪律：**不要照抄用户模板里的 parse_note**——模板里那句是示例，实际观察到什么就写什么。全段**1-2 句封顶**。不要留空串——下游程序靠它判断能不能跳过人工核对。

7. **落盘**。写 `output/<图片名>.json`：UTF-8、`ensure_ascii=false`、2 空格缩进，key 顺序 `label_type` → `fields` → `parse_note`。**单个对象，不要套数组**。

8. **校验**。跑 `python3 .skills/part-label-to-json/scripts/validate_json.py output/<图片名>.json`。有 ERROR 就改到没有为止；有 WARN 就确认是不是真问题，是就写进 `parse_note`。

9. **交付**。用 `<deliver-assets>` 把 json 文件给用户，回复里用一两句话讲清：识别到什么、有没有需要人工核对的地方。不要把完整 JSON 再贴一遍——文件已经给了。

## 批量

- 每张图各走一遍完整流程，命名带序号防重名：`001_<图片名>.json`。
- **一张都不能少**：读不出来的也出文件（全空 + 备注）。批量是为了后面人工抽检，漏一张等于丢一条产品的追溯记录。跑完报一句"共 N 张，其中 M 张建议人工核对"。
- 批量场景**默认就写** `_manifest.json`，不用等用户开口：`[{"image": "...", "json": "...", "label_type": "...", "needs_review": true}, ...]`，`needs_review` = `parse_note` 里记了任何不确定。全 false 说明这批可以跳过抽检。

## Output contract

文件：工作区 `output/<图片名>.json`

```json
{
  "label_type": "零件标签",
  "fields": {
    "零件品号": "20-C002-00-7E",
    "零件件号": "4121010-DY01-AA",
    "生产日期": "20240404",
    "批次序号": "L00118"
  },
  "parse_note": "零件件号存疑，建议人工核对"
}
```

硬约束：
- 三个顶层 key 都在且顺序如上
- `fields` 是对象，值一律为字符串（缺失用 `""`），不出现 `null` / 数字 / 数组
- `parse_note` 是非空字符串，**1-2 句封顶，只点名字段不解释过程**
- 文件名与图片同名，扩展名换 `.json`

## Failure handling

- **`read` 打不开图片**（HEIC/TIFF/超大图）：先转格式再试（ImageMagick / `sips`，或让用户重传 JPG）；仍不行就加载 `mcode-tools-master` skill 走多模态识别。
- **标签区域完全不可读**：照样出文件，全部字段留空，`parse_note` 写"全部字段留空（标签区域不可读）"，manifest 里标 `needs_review: true`。事后告诉用户哪些图需要补拍。理由：批量是为人工抽检服务的，缺一个文件下游就少一条记录，猜不出不等于不用交。
- **部分字段可读**：其余照常填，别因为一处模糊就放弃整张标签。
- **某个字符拿不准**：选最可能的读法，并把该字段点名进 `parse_note`；实在没把握就用空字符串 + 一句原因。
- **图上有二维码/条码**：不尝试解码，也**不写进 `parse_note`**——不写进字段、不写进备注，一个字都不留。原因：条码由主机厂侧系统消费，本技能只负责标签上印刷的字符，不碰条码这条链路。
- **用户模板与图上实物对不上**：以图为准，模板缺的字段留 `""`，差异只写一句结论（例：`模板缺生产日期，该字段留空`），不要把整个模板对照抄进备注。
