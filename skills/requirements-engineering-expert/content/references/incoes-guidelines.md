# INCOSE系统工程需求指南核心要点

## 概述

INCOSE（国际系统工程委员会）发布的《需求编写指南》为需求工程实践提供了最佳实践框架。本文档提炼核心要点供快速参考。

## 需求基础原则

### 七项基本原则

1. **必要性原则（Necessity）**
   - 每条需求必须是系统必需的
   - 移除后系统无法满足干系人需求
   - 避免镀金（gold-plating）

2. **完整性原则（Completeness）**
   - 需求集合应完全覆盖干系人期望
   - 包含正常操作和异常处理
   - 考虑边界条件和极端情况

3. **一致性原则（Consistency）**
   - 需求之间无逻辑冲突
   - 术语使用统一
   - 与上层文档保持一致

4. **可验证性原则（Verifiability）**
   - 存在有限的低成本验证方法
   - 可通过测试、分析、演示或检查验证
   - 验证标准明确

5. **可修改性原则（Modifiability）**
   - 结构化组织便于变更
   - 无冗余和重复
   - 变更影响可控

6. **可追溯性原则（Traceability）**
   - 向上追溯到需求来源
   - 向下追溯到设计/实现/测试
   - 双向追踪链路完整

7. **正确性原则（Correctness）**
   - 语法正确
   - 语义准确
   - 技术可行

## 需求编写规则

### 形式化模板

```
REQ-[类别]-[编号]
描述：[具体的需求陈述]
来源：[需求来源]
理由：[为什么需要此需求]
验证方法：[如何验证]
依赖关系：[相关需求]
```

### 句式规则

**规则1：使用主动语态**
- ✅ "系统应验证用户密码"
- ❌ "用户密码应被系统验证"

**规则2：使用确定性动词**
- ✅ "系统应发送确认邮件"
- ❌ "系统可以发送确认邮件"

**规则3：避免量化模糊词**
- ✅ "响应时间应≤2秒"
- ❌ "响应时间应快速"

**规则4：单一性原则**
- ✅ "系统应记录用户登录时间戳"
- ❌ "系统应记录用户登录时间戳和IP地址，并保存到日志"

**规则5：使用现在时态**
- ✅ "系统支持1000并发用户"
- ❌ "系统将支持1000并发用户"

### 常用动词库

| 类别 | 推荐动词 | 说明 |
|-----|---------|-----|
| 功能 | shall, will, must | 定义系统行为 |
| 约束 | shall, must | 定义限制条件 |
| 可选 | may, can | 表示可选功能 |
| 禁用 | should, ought to | 过于模糊 |

### 量化要求矩阵

| 指标类型 | 必须包含 | 格式示例 |
|---------|---------|---------|
| 数值范围 | 是 | 10 ≤ X ≤ 100 |
| 最大值 | 是 | ≤ 100单位 |
| 最小值 | 是 | ≥ 10单位 |
| 精确值 | 是 | = 50单位 |
| 百分比 | 是 | 99.5% |
| 时间 | 是 | ≤ 5秒 |

## 需求缺陷分类

### A类缺陷（严重）

| 缺陷 | 特征 | 影响 |
|-----|------|-----|
| 模糊性 | 含模糊词汇 | 无法正确实现 |
| 歧义性 | 多重解释 | 需求冲突 |
| 不可测试 | 无验证方法 | 无法确认满足 |
| 矛盾性 | 与其他需求冲突 | 系统失效 |

### B类缺陷（中等）

| 缺陷 | 特征 | 影响 |
|-----|------|-----|
| 不完整 | 缺少必要条件 | 实现遗漏 |
| 不可实现 | 技术/资源限制 | 返工 |
| 不一致 | 术语/层级不统一 | 理解偏差 |

### C类缺陷（轻微）

| 缺陷 | 特征 | 影响 |
|-----|------|-----|
| 冗余 | 重复描述 | 维护困难 |
| 可读性 | 结构/格式问题 | 理解效率 |
| 可修改性 | 变更风险高 | 维护成本 |

## 需求分层模型

```
Level 0: 业务需求
    ↓
Level 1: 用户需求
    ↓
Level 2: 功能需求
    ↓
Level 3: 设计约束
```

### 各层需求特征

**Level 0 - 业务需求**
- 来源：组织目标
- 关注：为什么需要系统
- 特点：高层、战略、抽象

**Level 1 - 用户需求**
- 来源：用户调研、场景分析
- 关注：用户目标和期望
- 特点：面向任务、描述性

**Level 2 - 功能需求**
- 来源：用户需求分解
- 关注：系统行为
- 特点：规范化、可测试

**Level 3 - 设计约束**
- 来源：技术决策、标准
- 关注：实现限制
- 特点：非功能特性

## 质量评估量表

### 评分标准

| 分值 | 等级 | 缺陷数 | 说明 |
|-----|------|-------|-----|
| 90-100 | A | 0个A级 | 优秀可直接使用 |
| 70-89 | B | 1-2个B级 | 良好需小幅修改 |
| 50-69 | C | 1-2个A级或3+个B级 | 及格需重大修改 |
| <50 | D | 3+个A级 | 较差需重写 |

### 检查清单使用

使用以下检查清单逐条评估：

```
【每条需求必须通过以下检查】

□ 1. 必要性检查 - 是否为系统必需？
□ 2. 完整性检查 - 是否描述完整？
□ 3. 明确性检查 - 是否无歧义？
□ 4. 可验证检查 - 是否可测试？
□ 5. 可追踪检查 - 是否有标识？
□ 6. 一致性检查 - 是否无冲突？
□ 7. 可实现检查 - 是否可实现？
□ 8. 无冗余检查 - 是否不重复？
□ 9. 格式正确检查 - 句式/术语？
□ 10. 分类正确检查 - 类型正确？
```

## 常见问题修复指南

### 问题1：模糊量化词

**问题需求：**
"系统应具有足够的存储空间"

**修复步骤：**
1. 识别模糊词："足够的"
2. 确定量化指标：存储容量
3. 定义具体值：基于数据分析
4. 设定合理范围

**修复结果：**
"系统应提供不小于500GB的可用存储空间，用于存储用户上传的文件数据"

### 问题2：不可测试需求

**问题需求：**
"系统应是用户友好的"

**修复步骤：**
1. 识别抽象概念："用户友好"
2. 分解为具体特性：
   - 易学性
   - 效率
   - 可记忆性
   - 错误率
   - 满意度
3. 为每个特性定义量化指标

**修复结果：**
"新用户完成标准任务的学习时间应≤15分钟；
熟练用户完成相同任务的平均时间应≤30秒；
用户操作错误率应≤1%"

### 问题3：复合需求

**问题需求：**
"系统应验证用户身份，记录登录时间，并发送欢迎邮件"

**修复步骤：**
1. 识别独立行为
2. 拆分为单独需求
3. 保持可追踪性

**修复结果：**
- REQ-FUN-001: "系统应验证用户输入的用户名和密码"
- REQ-FUN-002: "系统应在用户成功登录后记录登录时间戳"
- REQ-FUN-003: "系统应在用户首次登录时发送欢迎邮件"

### 问题4：缺少边界条件

**问题需求：**
"系统应处理用户输入"

**修复步骤：**
1. 识别缺失场景
2. 补充边界条件
3. 定义异常处理

**修复结果：**
"系统应处理用户输入的以下情况：
a) 正常字符输入
b) 空输入
c) 超出长度限制的输入
d) 特殊字符输入
e) 恶意输入（SQL注入、XSS）
f) 网络中断后的重连输入"
