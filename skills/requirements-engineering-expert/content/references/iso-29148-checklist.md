# ISO/IEC/IEEE 29148 需求工程标准检查清单

## 标准概述

ISO/IEC/IEEE 29148:2018 《系统和软件工程 - 生命周期过程 - 需求工程》为需求工程过程提供了全面的指导框架。

## 需求工程过程框架

```
需求开发 ←→ 需求管理
    ↑
需求启发 ←→ 需求分析 ←→ 需求规格 ←→ 需求验证
```

## 需求质量检查清单（基于29148）

### 1. 需求定义原则

| 编号 | 检查项 | 检查标准 |
|-----|-------|---------|
| RD-01 | 必要性 | 需求应直接支持干系人的合法需求 |
| RD-02 | 充分性 | 需求集合应充分满足干系人需求 |
| RD-03 | 可行性 | 需求应在技术和资源约束下可实现 |
| RD-04 | 可验证性 | 需求应可通过有限成本和方法验证 |
| RD-05 | 适应性 | 需求应能适应未来变更 |

### 2. 需求特性检查

#### 2.1 完整性检查

- [ ] 所有系统边界已定义
- [ ] 所有接口需求已明确
- [ ] 所有约束条件已记录
- [ ] 所有假设条件已文档化
- [ ] 异常和边界情况已考虑

#### 2.2 正确性检查

- [ ] 需求与业务目标一致
- [ ] 需求之间无逻辑冲突
- [ ] 需求满足法规和标准
- [ ] 数据定义准确一致

#### 2.3 明确性检查

- [ ] 使用确定性的语言
- [ ] 无模糊词汇（如"适当的"）
- [ ] 无歧义性描述
- [ ] 只有一个可解释的含义

#### 2.4 可追踪性检查

- [ ] 每条需求有唯一标识
- [ ] 需求来源已记录
- [ ] 可追踪到设计实现
- [ ] 可追踪到测试用例
- [ ] 可追踪到用户故事

### 3. 需求编写规范

#### 3.1 句式要求

**推荐句式：**
```
<Subject> shall <action verb> <object> <condition/constraint>
系统应<动作><对象><条件>
```

**禁止句式：**
- ❌ 陈述句："系统具有用户管理功能"
- ❌ 祈使句："实现用户登录功能"
- ❌ 模糊句："系统应该有良好的安全性"

#### 3.2 动词使用规范

| 推荐动词 | 禁用动词 |
|---------|---------|
| shall | should (弱化) |
| must | may (模糊) |
| will | might (不确定) |
| is required to | ought to |
| will be limited to | approximately |
| will support | suitably |
| will provide | appropriately |
| will deliver | adequately |

#### 3.3 量化指标要求

| 类别 | 必须量化 | 示例 |
|-----|---------|-----|
| 性能 | 是 | 响应时间 ≤ 3秒 |
| 容量 | 是 | 支持1000并发用户 |
| 可用性 | 是 | 99.9% uptime |
| 精度 | 是 | 精度 ≤ 0.01% |
| 时间 | 是 | 处理时间 < 5分钟 |

### 4. 需求分类检查

#### 4.1 功能需求

- [ ] 描述系统行为
- [ ] 定义输入/处理/输出
- [ ] 明确触发条件
- [ ] 描述错误处理

#### 4.2 非功能需求

**性能需求：**
- [ ] 响应时间
- [ ] 吞吐量
- [ ] 资源利用率

**可靠性需求：**
- [ ] 可用性
- [ ] 平均故障间隔（MTBF）
- [ ] 平均恢复时间（MTTR）

**安全性需求：**
- [ ] 认证要求
- [ ] 授权要求
- [ ] 审计要求
- [ ] 加密要求

**可维护性需求：**
- [ ] 模块化要求
- [ ] 可测试性要求
- [ ] 可扩展性要求

### 5. 需求验证检查

| 验证方法 | 适用场景 | 检查要点 |
|---------|---------|---------|
| 评审 | 所有需求 | 语法、结构、完整性 |
| 原型演示 | 界面需求 | 可理解性、可用性 |
| 模拟 | 动态行为 | 性能、并发 |
| 测试 | 可测试需求 | 可验证性 |

### 6. 常见缺陷类型对照表

| 缺陷类型 | 典型示例 | 识别关键词 |
|---------|---------|----------|
| 模糊性 | "适当的安全措施" | 适当、合理、足够 |
| 歧义性 | "高优先级用户" | 高、多、复杂 |
| 不可测试 | "用户友好" | 用户友好、易用 |
| 不完整 | "支持多语言" | 未定义语言列表 |
| 矛盾性 | 与其他需求冲突 | 需全局检查 |
| 不可实现 | 技术限制 | 需技术评估 |

### 7. 需求文档结构检查

基于29148的需求规格文档应包含：

1. **引言**
   - [ ] 目的
   - [ ] 范围
   - [ ] 定义和缩略语
   - [ ] 参考资料

2. **总体描述**
   - [ ] 产品透视
   - [ ] 产品功能
   - [ ] 用户特征
   - [ ] 约束
   - [ ] 假设和依赖

3. **详细需求**
   - [ ] 功能需求
   - [ ] 性能需求
   - [ ] 接口需求
   - [ ] 操作需求
   - [ ] 包装需求
   - [ ] 迁移需求

4. **附录**
   - [ ] 需求索引
   - [ ] 可追踪矩阵
