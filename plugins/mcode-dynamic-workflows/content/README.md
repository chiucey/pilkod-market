# 动态工作流

版本 0.8.2。通过英文 `dynamic-workflow` Skill 生成动态工作流，使用本地 MCP 服务调度 MCode Agent，在 Workflow Studio 面板查看阶段、依赖、节点状态、日志和结果。

## 开始使用

安装并启用插件，在新会话中输入：

> 使用 dynamic-workflow，先运行一个演示工作流，并打开可视化面板。

演示模式不调用模型。真实任务示例：

> 使用 dynamic-workflow，从安全、正确性和可维护性三个角度审查当前项目，汇总有证据的结论，并打开可视化面板。

网页支持跟随系统语言、中文和 English；手动语言选择会保存在浏览器中。用户输入与历史模型输出保留原文。

## 运行要求

- 本地 Desktop 分发；包含 1 个 Skill、1 个 stdio MCP 服务、11 个工具，不包含 App 或 Hook。
- MCP 启动环境需提供兼容 Node.js（22.19+ 的 22.x，或 24–26）。包内已包含 JavaScript 依赖和 QuickJS WASM，无需在插件目录运行 npm install。
- 真实执行需要可用的 MCode CLI，以及用户自己的登录和模型配置。Skill 会先检测 CLI，缺失时通过官方安装器协助安装；登录授权仍由用户完成。参见 [CLI 快速入门](https://matrix-pre.xaminim.com/docs/cli/quick-start)。已有可用 CLI 不会自动升级。
- CLI 自带的私有 Node 不保证 MCP 宿主可以从 PATH 找到 Node。启动失败时先检查宿主的 Node 环境。

## 工作区与本地数据

默认 MCP 入口为项目路由，不再把插件安装目录视为任务项目。除 `workflow_validate` 外，每次工具调用均须提供当前任务的绝对 `workspace`；Skill 从会话项目或用户指定位置获取，未知时先询问，无需修改安装文件。

每个规范项目路径在 `~/.mcode-dynamic-workflows/projects/<规范路径 SHA-256>/` 下拥有独立服务、历史、模板、并发预算和固定面板地址。重新连接或使用符号链接别名会复用同项目服务；不同项目不能互用运行 ID。旧数据不会自动迁移，并发上限按项目服务生效，不是跨项目总上限。

显式 `--workspace` 或 `settings.workspace` 配置保留原固定项目模式及数据目录。独立启动服务须明确指定项目；审核和执行前核对返回的 workspace。

市场包不包含本地路径、运行记录或登录凭证。面板使用可收藏的本机地址，无需 token。

## 预算与恢复

默认每个 Agent 最多 120 个模型步骤、30 分钟超时，整个工作流最多 120 分钟；创建和恢复时可以调整预算。失败节点展示具体原因。暂停会停止继续调度；取消和恢复通过面板或 MCP 工具进行。

恢复复用已成功步骤，失败步骤从头执行，不是恢复原 CLI 会话。重试前确认外部副作用。真实 Agent 使用 MCode smart 权限，不代表继承主会话的完整上下文，也不是只读操作系统沙箱。工作流脚本在 QuickJS 中执行，不直接访问 Node、文件系统或网络。

## 先审核，再执行

`workflow_start` 创建持久化的「待审核」草稿，不执行脚本或 Agent。Skill 自动使用 MCode 宿主的 Browser Use Skill 与 `mcp_browser` 在内置浏览器打开当前运行；浏览器能力缺失或停用时明确说明，保留草稿并给出手动链接。自动打开不代表自动批准执行。

可在拓扑图中选择计划节点查看源码，点击「修改工作流」编辑脚本、完整 JSON 输入和预算。保存后递增 revision 并重新生成拓扑；用户点击「开始执行」后才调度 Agent。服务拒绝旧版本与重复启动，MCP 不提供审核工具。已经开始的运行不能改写脚本。

拓扑是静态结构分析，不是模拟模型执行，也不是实际节点的完整预测：循环和回调显示为动态任务组，条件分支可能不执行，推断连线表示数据关系；别名等无法解析的结构需阅读完整脚本。

## 共享并发与队列说明

全局默认 **8 个 Agent**，在顶部并发设置中可调整为 **1–32**，并保存在服务数据目录。新工作流默认 **4 个 Agent**，可调整为 **1–16**；最多同时执行 3 个工作流。多个符合条件的工作流轮流取得空闲名额，调低全局上限不会中断在途 Agent。步数、超时、总调用预算独立生效。

队列详情显示当前容量限制和占用名额的工作流。排队不等于停死，可能是其他工作流占满共享容量。0.4.0 同时修复健康或排队节点的空错误对象导致面板停止刷新的问题。

## 固定地址与独立服务

MCP 会话连接独立后台服务，关闭聊天或断开 stdio 不会停止面板或已审核工作流。首次端口写入数据目录的 `address.json`（`endpoint.json` 记录当前进程），重启后复用；端口被占用时明确报错，不自动换地址。也可通过 MCP args 中的 `--port <端口>` 显式配置。数据与服务日志 `service.log` 保存在配置的数据目录，不在插件缓存里。

面板无需 token；API 只绑定 127.0.0.1，检查 Host、Origin、Fetch Metadata 与自定义请求头，并拒绝跨站 CORS 请求。同一系统用户下的本地程序仍可访问。

需要停止服务时先暂停或取消活动任务，再在插件目录运行 `node ./dist/main.mjs --stop-service`，附上与启动时一致的 `--settings` 或 `--workspace` / `--data-dir` 参数。有活动任务时命令拒绝停止。地址和历史保留；未安装系统开机自启动或完成通知。关机后重新连接插件即可启动服务，异常终止仍需确认旧 Agent 已停止才恢复。

更新不会替换仍活跃的旧服务。旧版服务仍使用原生命周期与 token 链接；用户停止旧服务并重新连接新版插件后，才启用独立服务与无 token 地址。

## 0.5.0：从审核到交付

- 逐项流水线：每项审查结束即可开始该项复核，最后统一汇总。仍受公平调度和并发预算约束。
- 任务说明：审核前显示并可编辑目标、输入说明、预期产物，修改后更新审核版本。
- 实时进展：`ctx.log(message, {stepId, phase})` 记录具体节点进展，面板展示最近一条；每次执行最多 200 条，每条 4,000 字符。
- 可交付报告：结构化结果可阅读，结束或暂停后可下载 HTML／Markdown，保留失败与覆盖缺口，并标识演示结果。导出内容来自已保存结果，不会额外调用模型。
- 本地模板：最多 50 个，包含脚本、当前输入、说明和预算，不含结果或批准状态。复用会打开编辑表单，保存后仍需审核，不自动执行。

`workflow_start` / `workflow_update` 可传 `metadata: {objective, inputDescription, deliverables}`。前两项各最多 1,500 字符，产物最多 12 项、每项 300 字符。新版英文 Skill 包含自包含节点提示、逐项流水线、进展记录、报告和模板使用指导。设计参考 [deer-workflow](https://github.com/deerwork-ai/deer-workflow)，基于本插件现有 QuickJS、SQLite 和调度器独立实现。

## 0.6.0：完整执行画布与精简审核

开始执行后保留计划节点，在同一画布区分尚未开始、排队、执行中、成功、失败、依赖受阻和未执行。可静态确定的字面量或输入数组提前展开；依赖上游结果的节点保留动态分组，运行时逐步展开，不虚构数量。默认示例在执行前后均显示 7 个节点，展示占位不会增加实际调用。

审核页聚焦目标、拓扑和编辑／开始按钮；输入、产物、预算、静态分析说明与次要操作折叠。桌面画布自动适应可用宽高，窄屏保留缩放和滚动。历史运行兼容旧拓扑，节点调用位置只用于展示关联，不改变原脚本、请求 hash、批准或调度语义。

## 0.6.1：依赖兼容与可定位错误

`dependsOn` 支持单个节点 ID 字符串或数组，推荐 `dependsOn: ["scope"]`。保存、验证、审核和恢复前检查静态可确定的格式错误；运行时继续要求每个上游已成功，未成功的依赖会报告节点、依赖 ID 和状态。沙箱保留结构化错误，不再重复转义 JSON。

旧版因单个依赖字符串失败的记录会显示兼容说明和恢复建议；刷新不改变状态、不自动重跑。显式恢复时复用参数未变的成功节点。

## 0.7.0：节点阅读与报告排版

点击节点进入宽幅阅读面板，可切换前后节点、结果／输入／日志、阅读／原文，并复制原文。执行参数折叠，依赖节点可以直接跳转；后台刷新保留阅读位置，支持键盘和窄屏。

结果按 Markdown 或 JSON 结构展示。HTML 报告以结论、覆盖情况、节点证据和原始汇总附录组织，节点输出可以折叠，支持离线阅读与打印；Markdown 保留标题、列表、表格、代码块和段落。面板预览直接使用同一份 HTML 导出内容。渲染不会改写存储的原始结果，不加载输出中的远程图片或执行 HTML／脚本。

## 0.7.2：项目目录绑定

MCP 工具发现不再从插件目录启动工作流服务。工具调用显式绑定项目，拒绝缺失、相对、不存在或插件内部路径；并发调用按规范路径路由，运行记录和固定端口按项目隔离。

## 0.7.3：结构化输出契约

下游要读取字段的节点必须声明 schema。运行时先校验原生结果，兼容完整 JSON 文本及单个完整 JSON 代码块，解析后仍严格校验；不从任意正文中抽取对象、不选择多个块、不强制转换类型或猜测缺失值。节点详情保留原始输出及具体校验错误，校验失败不记为可复用的成功节点；带保护的脚本报告覆盖缺口。未声明 schema 的叙述性结果保持原样。Skill 补充最终回复格式、嵌套字段保护、未知决策值及显式保留任务 ID 等约束。

## 根据错误修复脚本

运行停止后，点击「修改并修复」，查看错误、编辑完整脚本和输入、填写修复说明，并勾选确认仍有效的成功节点。也可在 MCode 对话中要求根据错误修复，Skill 会通过 `workflow_results(includeDefinition: true)` 读取原脚本和诊断，再用 `workflow_repair` 创建新的待审核版本并打开面板。原运行完整保留，必须审核后点击开始执行。

默认不复用；所选节点仅在实际参数、输入、工作区、执行方式、登记文件哈希及依赖均匹配时复用。上游重跑会使下游重跑；未到达的分支不会预先标为成功。节点详情保留结果来源，不重复计入调用和 Token。脚本从头重放，checkpoint 重新计算。

声明完整的数据与控制依赖 `dependsOn`；未登记文件、外部数据和副作用无法自动检测，复用前需确认有效。成功但内容错误的结果不要勾选。只调预算或重试暂时错误仍使用「恢复」；本功能不续接失败 Agent 会话，也不会自动批准执行。

升级后若提示 `WORKFLOW_SERVICE_UPGRADE_REQUIRED`，说明常驻后台仍是旧版。先暂停或取消活动运行，再经用户确认使用新版包的 `--stop-service`（相同 `--workspace` 和 `--data-dir`）停止项目服务，重新连接 MCP 即加载新版本；保留端口和历史，退出聊天不会自动重启后台。

## 0.8.2：Windows 兼容性修复

- 解析官方安装器的 `mcode.cmd`（含 `current` / `releases` 版本化布局和旧版 `runtime` 布局）及 npm 启动器，直接用安装器固定的 `node.exe` 运行 CLI，不再经由 PowerShell。此前在默认执行策略下节点无法启动，带 `schema` 的节点参数中的双引号也会被 Windows PowerShell 5.1 去掉。
- PATH 查找不再命中 npm 生成的无扩展名 POSIX 脚本 `mcode`。
- 暂停、取消和超时用 `taskkill /T` 停止整棵 Agent 进程树；遗留子进程占用输出管道时节点也能结束，不再停在“停止中”。
- `setup-mcode.mjs --install` 以 `-ExecutionPolicy Bypass` 运行官方安装器，并以带 BOM 的 UTF-8 写入临时脚本；经符号链接、junction 或不同盘符大小写调用时不再静默无输出。
- `workspace` 接受 Git Bash 形式的 `/c/Users/...` 路径；`address.json`／`endpoint.json` 替换遇到短暂占用时重试；后台服务启动等待延长到 30 秒，失败时附带 `service.log` 末尾内容。
