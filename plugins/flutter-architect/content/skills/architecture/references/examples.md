# 示例与自测

## 一、示例：腐化项目的治理回答

**用户问**：我们的 Flutter 项目越来越乱，页面里全是网络请求和状态逻辑，怎么办？

**参考回答要点**：

1. 结论：这是职责边界缺失导致的架构腐化。采用 Feature-First + 轻量 Clean Architecture，先治理高频变更模块，不做一次性全量重构。
2. 假设：项目进入维护期；页面逻辑复杂；团队要持续迭代；没有时间停线重写。
3. 方案：新功能强制分层；老功能按"高价值、高复杂度、高变更频率"排序。
4. 步骤：
   - 第一阶段建立规范：禁止 Widget 内直接请求网络；禁止 Page 写复杂业务逻辑；统一错误与加载态。
   - 第二阶段抽象公共层：ApiClient、Result/Failure、Logger、Router。
   - 第三阶段试点重构登录页或首页，产出模板与测试。
   - 第四阶段推广：每迭代 10%~20% 技术债治理，新页面必须遵循新架构。
5. 验收：页面不直接依赖 Dio；业务逻辑可单测；仓储可 mock；错误提示统一；关键流程有覆盖。
6. 风险：一次性重构风险高；团队不适应分层；无测试保护时重构易回归。

## 二、示例：状态管理选型

**问题**：10 人团队维护中型应用，Riverpod 还是 Bloc？

**回答要点**：

1. 先问四个变量：团队既有经验、状态复杂度（是否有复杂异步/状态机）、测试与规范要求、存量代码规模。
2. 对比维度要具体：学习成本、样板代码量、异步与依赖注入能力、可测试性、生态与维护、迁移成本。
3. 给混合策略：新模块统一用其一，存量按改动频率迁移，避免一次性推翻。
4. 落地：选 1~2 个模块试点 4 周，产出规范与评审清单，用缺陷率、返工率、上手时间评估。
5. 反面回答："Riverpod 更现代"——没有结合团队与阶段，属于不合格。

## 三、示例：Flutter 大版本升级

**问题**：项目停在 3.29，要升到当前版本。

**回答要点**：

1. 影响面清单：渲染引擎（Impeller 覆盖范围）、iOS 依赖管理（SwiftPM 默认）、Web 渲染器（仅 CanvasKit/Skwasm）、Android targetSdk/AGP、Xcode 最低版本、废弃 API。
2. 分步：升 SDK → 修 analyzer 与 deprecated → 三方包逐个升级或替换 → 原生工程适配 → 渲染与布局回归 → 灰度发布。
3. 回归重点：字体行高、图片解码、权限、剪贴板、深链、启动耗时、包体积。
4. 验收：崩溃率与卡顿率不升、关键链路测试全绿、体积增量在阈值内。
5. 回滚：保留旧分支与灰度开关，演练一次回滚。
6. 风险：一次跨多个大版本、只测 debug 模式、CI 缓存导致误判。
## 四、自测题（判断建议质量）

1. 10 人团队维护中型应用，选 Riverpod 还是 Bloc？——必须回答团队熟悉度、状态复杂度、测试需求、规范强度、代码量、学习成本，不能只说"更好"。
2. 什么时候不该用 Clean Architecture？——小项目、生命周期短、团队不熟、规则简单、验证期。
3. 购物车状态放哪？——区分列表缓存、购物车业务状态、结算流程状态、持久化、服务端一致性、登录态关联。
4. 如何避免全局状态滥用？——分类、作用域最小化、注入、单向数据流、来源唯一、可追踪。
5. 长列表卡顿怎么系统排查？——DevTools、Build/Layout/Paint、builder、图片尺寸、RepaintBoundary、item 复杂度、异步数据、缓存、分页、const、嵌套。
6. 启动慢如何优化？——原生阶段、engine 初始化、main、插件、首屏请求、首帧、延迟加载、骨架屏、启动埋点。
7. 如何设计多环境？——flavor/dart-define、入口、env 配置、DI、feature flag、API host、日志级别、构建命令、CI 变量。
8. 如何做模块拆分？——feature 边界、core、shared、design system、依赖方向、workspace、版本管理、编译隔离。

## 五、最小代码示例原则

- 只给理解方案所需的最小片段，不贴完整项目代码。
- 示例必须可编译、命名清晰、包含错误处理。
- 接口优先：先展示抽象接口，再给一个实现示意。
- 示例中不出现真实密钥、内网地址、用户数据。
