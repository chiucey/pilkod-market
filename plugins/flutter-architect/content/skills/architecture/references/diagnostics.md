# 线上诊断与异常归因

本文件负责"如何定位"，不负责"具体怎么改代码"；定位结论明确后，修复走工程流程。

## 一、捕获接入

必须在 runApp 前完成，且不要把上报逻辑写成会再次抛错的分支：

- `FlutterError.onError`：框架内同步异常（build/layout/paint、手势回调）。
- `PlatformDispatcher.onError`：未捕获的异步异常（Future、Zone 之外）。
- `ErrorWidget.builder`：release 下替换默认红屏，展示兜底页并上报，避免白屏。
- 原生侧崩溃 SDK（Crashlytics/Sentry/自研）初始化要早于 Dart 入口。
- 关键路径补 breadcrumbs：页面进入、接口调用、开关状态、重试次数。
- 上报字段至少包含：版本、构建号、平台与系统版本、设备型号、渠道、网络类型、账号哈希、页面路径。

## 二、白屏/黑屏定位树

按顺序排除：

1. 首帧是否渲染？build 抛异常会落成 ErrorWidget，release 下若未兜底就是白屏。
2. 引擎或资源初始化是否失败？（原生侧日志、字体/图片资源缺失、平台视图崩溃）
3. 路由目标是否存在？守卫是否死循环或错误重定向？
4. 数据为空时是否只有 loading 没有空态？接口失败是否静默？
5. 权限被拒、网络不可用、登录态失效是否有可见反馈？
6. 是否只在某个灰度版本/渠道/机型出现？（先做范围对照）

常用手段：真机 release 包复现、看最后一条日志、看 ErrorWidget 是否触发、对比灰度与全量版本、抓首帧前后时间线。

## 三、崩溃归因

- 保留符号：Dart 侧 `--obfuscate --split-debug-info` 产物、iOS dSYM、Android mapping，全部上传到崩溃平台。
- 本地还原：`flutter symbolize -i stack.txt -d symbols/`。
- 维度聚合：版本、构建号、平台、机型、系统、渠道、账号类型；按堆栈指纹分组去重。
- 结合用户路径：崩溃前的页面序列、接口失败、开关状态，判断是数据驱动还是并发驱动。
- 指标口径：crash-free users / sessions、启动崩溃率、ANR 率（Android）、卡死与看门狗（iOS）。

## 四、偶现问题

- 先补可观测性：日志、埋点、关键分支计数，让"偶现"变成"可统计"。
- 建条件矩阵：设备、系统版本、网络、账号状态、时序（登录前后、冷热启动、前后台切换）。
- 二分：版本（哪个构建开始）、灰度（哪些用户）、配置（哪个开关）、数据（哪类输入）。
- 现场快照：内存曲线、线程栈、订阅与定时器数量。
- 无法立即定位时先兜底：降级、超时、重试、功能开关关闭。

## 五、线上事故流程

1. 止血优先：开关关闭、灰度暂停、版本回滚，先控制影响面。
2. 关联最近变更：客户端发版、服务端接口、配置下发、三方 SDK。
3. 定位：按上文分阶段缩小范围，必要时补日志版本。
4. 修复与验证：修复版本走灰度，观察同指标是否回落。
5. 复盘：补监控缺口、补测试、补降级方案，产出可跟踪的改进项。

## 六、与架构的关系

反复出问题的地方通常不是"某个 bug"，而是架构缺口：

- 没有统一异常模型 → 错误在各页面各自处理。
- 没有空/错/加载态规范 → 失败时白屏。
- 没有开关与灰度 → 只能靠发版止损。
- 没有符号表上传 → 崩溃不可归因。

这些问题应进入技术债清单，而不是逐次打补丁。

## 七、自检

- 线上崩溃能定位到具体版本、页面与代码行吗？
- 白屏时用户看到什么？有兜底页和重试吗？
- 从发现到止血需要多久？谁有权关开关？
- 最近一次事故的根因，是否已转成测试或监控？
