# 迁移与升级

## 一、通用原则

- 增量而非重写：每一步都能独立上线、独立回滚。
- 先建测试与监控，再动结构；没有回归防护的迁移等于赌博。
- 一次只迁一个维度（状态管理 / 路由 / 模块化 / 版本），不要混合。
- 每步给出验收口径：功能等价、性能不退化、崩溃率不升、包体积不涨。

## 二、Flutter 大版本升级

顺序（不要跳步）：

1. 读目标版本的 release notes、breaking changes 与 migration guide，列出影响面。
2. `flutter pub outdated` 检查三方包兼容；锁定无维护的包并评估替代。
3. 逐步升级：先升 SDK；可自动迁移的项先跑 `dart fix --apply`（含官方规则，如 `--code=migrate_design_widgets`），再处理剩余的 analyzer 报错与废弃 API，并按 breaking change 索引逐条勾销。
4. 原生侧同步：Gradle/AGP、Kotlin/JDK、targetSdk、Xcode 与 iOS 最低版本。
5. 渲染与平台变化：Impeller 是否默认、SwiftPM 是否接管 iOS 依赖、Material/Cupertino 是否拆包（3.47+ 可迁到 material_ui / cupertino_ui）、Web 渲染器变化。
6. 回归重点：字体与行高、图片解码、剪贴板、权限、深链、启动耗时、包体积。
7. 灰度发布，观察崩溃与卡顿指标后再全量。

常见坑：跨多个大版本一次升、三方包被迫大改、CI 缓存导致误判、只在 debug 模式验证。

## 三、状态管理迁移

以「Provider/GetX/setState → Riverpod 或 Bloc」为例：

1. 按 feature 排序：先迁改动频率最高、测试覆盖最好的模块。
2. 双轨期：新代码用新方案，旧代码保持；在边界处做适配，不要求一次替换全部。
3. 先抽状态模型（sealed/不可变），再换容器；否则只是把混乱换个位置。
4. 迁移完成判据：旧容器不再被 import、测试覆盖关键流程、无跨页面共享泄漏。

GetX 迁出注意：隐式全局依赖要显式注入，路由跳转要收口到 Router，控制器生命周期要显式释放。

## 四、路由迁移（Navigator 1.0 → go_router 等）

1. 先建立路由清单：路径、参数、返回值、是否需要登录、是否可深链。
2. 保留旧入口一段时间：深链与外部跳转按新路径映射，旧路径重定向。
3. 参数迁移：URL 参数与服务端下发字段做兼容层，避免一次性改后端。
4. 回归清单：冷启动深链、push 替换、返回结果、Tab 内嵌套栈、状态恢复。
5. 收口后删除散落跳转，禁止业务代码直接调 Navigator。

## 五、模块化迁移（单包 → workspace）

1. 先抽 core（网络/存储/错误/日志），再抽 design system，最后拆 feature。
2. 依赖方向用 CI 检查固定，不允许新反向依赖。
3. 每拆一个包都要能独立 `flutter analyze` / `flutter test`。
4. CI 分片与缓存，避免拆包后构建时间翻倍。
5. 版本策略：内部包统一由 workspace 解析，对外发布才需要版本与 changelog。

## 六、数据与配置迁移

- 数据库 schema 变更必须写迁移脚本并保留回滚路径，禁止 drop 重建。
- 本地缓存格式变更要带版本号，旧格式做读兼容或一次性转换。
- 配置（环境、开关）迁移要保证默认值安全：读不到就用保守值。

## 七、迁移验收与回滚

- 功能：核心链路回归用例全绿，埋点口径不变。
- 性能：首帧、列表滚动、内存、包体积与迁移前对比。
- 稳定性：崩溃率、错误率、卡顿率不升；灰度期间可一键降级。
- 组织：迁移文档与决策记录（ADR）落地，后来者能看懂为什么这么做。
- 回滚演练：至少验证一次回滚路径真的可用。
