## 二、状态决策 8 问

1. 只被一个 Widget 使用？ → 局部 StatefulWidget / ValueNotifier。
2. 只被一个页面使用？ → 页面级 Controller / Bloc / Provider。
3. 需要跨页面共享？ → 模块级，谨慎全局。
4. 来自服务器？ → Repository + 缓存 + 查询状态，不进全局 UI 状态。
5. 需要持久化？ → LocalDataSource / SecureStorage。
6. 影响多个模块？ → 明确事件来源与订阅关系。
7. 复杂异步（重试/并发/取消/分页）？ → 状态机 / AsyncNotifier。
8. 需要严格测试？ → 抽 UseCase / Controller，注入依赖。

## 三、性能决策 8 问

1. 问题发生在哪个阶段？（启动 / 首屏 / 滚动 / 动画 / 切换 / 后台恢复）
2. 是否有量化指标？（帧率、首帧、加载时长、内存峰值、CPU、包体积）
3. 能否用 DevTools 在 profile 模式复现？
4. 是否 rebuild 过多？（状态作用域、selector、Widget 拆分、const）
5. 是否布局过重？（嵌套、约束、builder、itemExtent）
6. 是否图片问题？（尺寸、解码、缓存、占位、复用）
7. 是否主线程阻塞？（同步 IO、大 JSON、计算、isolate）
8. 是否插件初始化过多？（启动全量初始化、不必要通道调用、过早预加载）

## 四、依赖准入门槛

满足才允许引入：

- 近 12 个月有发布，issue 有响应。
- 许可证在白名单内且 SPDX 明确。
- 纯 Dart 优先；含原生代码的必须评估平台覆盖与维护者。
- 通过接口隔离，不直接依赖其类型，替换成本可接受。
- 有明确的降级或移除方案。

## 五、反模式细则

| 反模式 | 症状 | 修法 |
|---|---|---|
| UI 层写业务逻辑 | onPressed 里发请求、写库、埋点、跳转混在一起 | 拆到 Controller/Bloc + UseCase + Repository |
| 全局状态泛滥 | 什么都进全局 Provider/Bloc，页面互相影响 | 状态分类，作用域最小化 |
| 过度 Clean Architecture | 一个 CRUD 页面 8 个文件 | 按复杂度分层，简单场景合并 |
| 依赖堆砌 | 每遇问题加一个包 | 准入评估 + 接口隔离 |
| 路由散落 | Navigator.push 到处写 | 集中 Router + 路由常量 + 守卫 |
| 错误处理不一致 | 有的 SnackBar、有的静默、有的崩 | 统一异常模型、错误码、提示与上报 |
| 无监控上线 | 无崩溃、无成功率、无开关 | 先接监控与开关再发版 |
| 生成物污染仓库 | 生成代码入库还手改 | 不入库 + CI 校验 + PR 排除 |

## 六、方案/代码评审检查表

**架构**
- 职责边界是否清晰，是否存在跨层调用？
- 依赖方向是否向内，Domain 是否被框架污染？
- 是否引入了不必要的抽象层？

**可维护性**
- 命名与目录是否符合项目既有约定？
- 是否存在巨型 Widget / 巨型文件 / 超长方法？
- 配置与常量是否集中？

**正确性**
- 空状态、错误状态、加载状态是否处理？
- 异步竞态、取消、重复提交是否处理？
- 资源（Controller、订阅、Timer）是否释放？

**性能**
- 列表是否 builder，是否有不必要的 rebuild？
- 是否有主线程阻塞或大图解码？
- 是否引入了额外依赖或包体积增长？

**可测试性**
- 是否可注入依赖、可模拟时间与网络？
- 关键分支是否有测试？

**安全**
- 是否打印或上报敏感数据？
- 是否把密钥写进代码或配置？
- 网络请求是否走统一鉴权与错误处理？

## 七、技术债治理验收标准（示例）

- 页面不直接依赖网络库；业务逻辑可单测。
- 仓储可替换为 mock；错误提示统一。
- 关键流程有测试覆盖；崩溃与关键性能有监控。
- 新代码必须遵循新架构，旧代码按迭代逐步迁移。
