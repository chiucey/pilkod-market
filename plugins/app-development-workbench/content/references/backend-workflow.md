# App 后端实施与运行

## 读取现状

定位 app/server 入口、依赖与 lockfile、路由注册、配置加载、模型/迁移和服务生命周期。记录当前可运行版本及未提交改动；只读配置变量名，不输出 .env 或凭据。已有 Node/Python/其他栈可沿用，按项目工具执行。

接口契约至少包含用户身份、字段类型/必填、归属、错误语义、分页与并发版本。状态码只是协议结果，业务完成还要核对实际返回与存储。认证令牌解析、资源归属和业务资格分开验证。

## 实现一条完整任务

route/controller 将协议转换为领域输入，service 校验业务并安排次序，provider 封装外部网络，repository/model 提供持久化。层次因现有架构调整，避免为“整洁”机械加层。

文件流明确临时文件、对象存储 key、业务记录引用的生命周期：校验输入 → 上传 → 处理 → 提交记录 → 清理旧资源。每个失败点说明谁回滚；已提交成功后的清理异常单独追踪。删除失败只能记录待处理，不能声称已经删除。

模型服务以任务定义集中管理模型键、提示词版本、输入输出 schema 与归一化，统一传输层处理超时、结构化解析和追踪。业务正确性由领域校验补充；模型输出不是可信指令或已验事实。

## 有意义的测试

测试最可能破坏用户数据的边界：跨用户访问、重复请求、旧版本提交、取消后迟到、外部依赖失败、DB 失败与清理同时失败、重启后读回。使用隔离库与可识别测试对象，不在生产数据做不可逆试验。

普通测试使用 provider 替身时明确标记；真实服务另跑受控 E2E，记录 requestId 与实际外部响应。收费/真实数据操作沿用户已授权范围。测试结束清理只处理明确属于本次的资源，失败记录保留。

## 启动与部署

先用项目端口检查方式确认监听者的 PID、命令和工作目录，再决定复用或终止残留。不用 killall node/python。优雅退出并保留数据，避免重复实例。

health 证明进程响应，readiness 检查必要依赖可用。运行配置需与被测配置一致；模型和存储环境不同必须标记。部署记录目标环境、commit、配置键、迁移、健康检查与回滚命令。数据库破坏性迁移、域名切换和生产部署需对应明确授权。

验收从原生 UI 发起一条请求，用同一记录验证 API 与数据持久化；API 直传仅能验证该层。交付可执行启动/停止/测试步骤，保留用户可体验实例。
