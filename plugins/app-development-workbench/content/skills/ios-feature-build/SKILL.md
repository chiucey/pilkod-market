# 构建 SwiftUI 功能


先读 [SwiftUI 实施](../../references/swiftui-implementation.md)、[项目规则](../../references/project-rules.md) 与当前接口/原型契约。发现工程、scheme、配置、最低 OS、依赖版本与真实启动入口，不沿用无关项目的固定值。

## 构建顺序
1. 保持现有架构约定，找到接近的页面和服务实现。新工程先完成 App 入口、根依赖、导航与一个有价值的页面闭环。
2. 确定本地值状态、跨页共享状态与外部服务的归属，再选择 SwiftUI 包装器。不要为所有页面自动造 ViewModel，也不要为了使用某种模式推翻合理既有架构。
3. 优先完善 DesignSystem 和可复用基础元件，再组合业务页。颜色、字体、圆角、阴影和交互状态集中管理；页面不复制修饰符链。
4. 使用稳定路由和选中对象驱动详情/弹层，避免互斥多个布尔值；请求在生命周期或服务层执行，不能从 body 发起网络副作用。
5. 按契约实现加载、空态、错误、取消、重试、重复提交与持久化。处理异步竞态，防止旧请求覆盖新选择，取消不自动呈现为业务失败。
6. 先构建可编译的骨架，再接异步数据和复杂状态。失败时从首个根因修复，不叠加新改动绕过错误。

## 从代码到体验
调用 ios-simulator-debug 完成构建、安装和启动，复用当前适合的模拟器。只要求模拟器时不安装到真机。局部迭代运行 1–2 个能覆盖本次风险的检查；功能收口跑相关完整回归，不能用镜像实现的无意义断言冒充测试。

按确认原型逐页核对布局、可点击区域、键盘和长内容。功能检查至少包含一次操作后的数据读回；使用 Mock 时明确模式，真实登录、支付、相机和外部服务另验。

## 交付
保留正常应用运行，给出从哪里点、输入什么、看到什么的 E2E 路径，以及构建/运行环境、变化和已知缺口。用户体验验收与自动检查分开；提交、合并、发布沿本轮已有授权执行，不把测试通过自动升级为生产发布授权。
