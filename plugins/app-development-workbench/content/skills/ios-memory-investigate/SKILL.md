# 调查 iOS 内存与引用泄漏


阅读 [内存证据](../../references/memory.md)，通过 ios-simulator-debug 固定 App 与模拟器版本。明确哪个对象应在何时释放，而不是只看总内存曲线。

## 采样顺序
1. 固定输入数据，启动 App，执行一次进入/操作/退出，再等待应完成的异步任务。
2. 从当前进程信息确认目标 PID 和可执行文件，不凭旧日志或同名进程猜 PID。
3. 使用 Xcode Memory Graph 或 Apple leaks 采集当前进程，保存原始 memgraph 到本次独立目录；不得写进插件安装目录。
4. 分组查看泄漏类型，定位最早的 app-owned 对象，追查强引用链及其字段/闭包/Task/定时器。
5. 解释预期生命周期与实际持有者，再修复强环、未取消任务或缓存回收策略。
6. 重复相同流程、次数和等待时间，重新采样，核对目标类型/引用链是否消失及是否引入功能回归。

## 判断边界
内存总量下降、memgraph 文件更小或延迟初始化都不能单独证明泄漏修复。找不到外部 root 的对象也可能是不可达的自持有环，要继续看组内引用。

区分正常缓存、可回收峰值、系统对象和应用泄漏。不要为消灭统计数字删除必要持久化或改变业务。无法采集时交付源码上的生命周期推断和具体待采信息，不编造前后数量。

交付 PID 来源、构建/场景、memgraph、目标引用链、修改与同条件复采结果。保留用户指定的研究证据，清理仅限明确属于本次且获授权的临时资源。
