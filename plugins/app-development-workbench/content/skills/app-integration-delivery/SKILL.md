# 跨端联调与交付验收


读取 [交付契约](../../references/delivery-contract.md) 和本轮授权范围，确认原型版本、App 构建、后端提交/配置、设备与数据模式。不要从旧报告的“完成”推断当前环境。

## 一条链路逐层确认
1. 以用户实际入口开始，执行约定动作：登录/选择输入 → 请求 → 处理 → 保存 → 查看结果 → 返回历史。
2. 用客户端记录 ID、请求 ID 与服务端日志关联同一次操作，不把 API 直传和 UI 上传的两个结果拼成同一证据。
3. 原型与原生用相同页面、视口和数据状态对照；字段无真实值时显示缺失，不能填原型示例分数。
4. 数据验证覆盖 API 读回、列表/详情一致和允许范围的重启恢复。对象引用一致与原文件字节一致分别验证；签名 URL 变化不一定意味着换文件。
5. 对关键失败、重试、取消、账号切换和重复动作检查资源/界面一致性。修复后只复测受影响范围，再在功能收口运行必要完整回归。

## 证据账本
每条写触发步骤、预期、实际、环境、版本、模式、产物、结果。区分 static、browser、simulator、device、live-service、user-acceptance、publication；这些维度不能互相代替。

保留失败和未测项，不累加重复运行冒充独立用例。某次重跑成功不代表已解释间歇故障。用户未明确认可就保持验收待定。

## 发布准备与授权
准备正确版本、配置、签名、隐私/权限说明及回滚。App archive、安装、上传、提交审核、审核通过与可下载各自核实。后端部署另核对在线版本和读回。测试市场与正式市场分别记录。

已有授权覆盖的提交/部署持续完成；范围缺失时先完成可审阅包与检查再问具体发布动作。不能因本地测试通过自动合并或上生产；也不要重复询问用户已明确授权的动作。

交付正常运行的体验入口、可重复步骤、源码/包/MR、实际通过证据和当前阻塞。最终说明必须足以让用户独立复核，不需要翻查过程消息。
