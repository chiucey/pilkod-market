# 调查 iOS 卡顿与响应耗时


读取 [性能采样](../../references/performance.md)。先明确操作、起止点、App 构建、设备/模拟器、OS、Debug/Release 和数据量；不使用随意操作一段时间的混合采样。

## 先定位可疑链路
沿触发到渲染检查观察范围、稳定身份、body 内计算、同步图片解码、布局反复测量、动画范围和主线程 I/O。源码发现只能写为可疑原因；用户已提供 trace 时优先使用并核对版本。

## 采集一次可解释证据
1. 构建并安装实际被测版本，复现固定场景。
2. 选择可用 Instruments/xctrace，或按参考使用 ETTrace。若采用 ETTrace，临时链接与 runner 匹配的 Simulator framework，确认启动日志和 app-owned dSYM UUID。
3. 保存原始采样和处理后数据，标明采样窗口、线程与符号完整性。ETTrace 只分析已核实格式的 processed output_<thread>.json，不误读同名 viewer/raw JSON。
4. 解释最重的应用调用栈及其业务路径，区分 inclusive 与 self 成本、样本比重与绝对时长。缺符号的关键应用栈不能作为完成诊断。
5. 做最小修复，重跑相同起止步骤和条件。设备/构建/数据不同则分别列出，不能直接声称提升百分比。

## 修复原则与收尾
缩小不必要的观察传播，稳定列表身份，将昂贵计算和图片处理移到适当生命周期/后台，先测再决定缓存与 equatable。不要用降低数据量或隐藏功能伪装性能修复。

恢复临时注入和采样配置，保留证据到独立运行目录。报告测量值、重复次数、波动、剩余问题和未验证设备；模拟器 CPU 成本不能直接等同实体设备能耗。
