# 邮箱接入助手

默认解决真实的浏览器操作任务，而不止输出教程：确认目标账号 → 进入官方设置 → 启用所需服务 → 生成授权码 → 填入用户指定的连接表单 → 核实连接结果。用户只询问获取方式时才停留在资料查询。写作或安装这个 skill 本身不授权操作任何邮箱。

## 确定范围和服务商

- “在哪获取”“整理所有教程”只查询信息；“帮这个邮箱获取授权码 / 接入工作台”可协助操作指定账号。复用会话中已有授权，不重复确认已明确的范围。范围仍不明确时先完成官方资料查询，再澄清是否需要操作账号。
- 优先读取目标产品当前的服务商注册表和可用工具。没有项目上下文时用 [服务商快照](references/providers.json)。快照包含 18 套配置，不能视为永远不变的产品能力或所有账号都支持接入的保证。
- 可用 `python3 scripts/lookup_provider.py --domain qq.com` 精确匹配域名；自定义域名在用户确认托管商后使用 `--provider feishu`，清单用 `--list`。命令路径相对本 skill 目录。脚本只查公开资料，不连接邮箱、不接收密码。
- 已识别的域名不再要求手选服务商。拼写疑似错误先提示用户核对，不静默改地址；未知域名不等于地址错误。自定义企业域名根据用户选择或官方组织配置识别，MX 最多作为线索。
- 区分个人版、企业版、地区与数据中心，以及套餐和管理员权限。识别出服务商不代表目标工作台支持其认证方式；对当前不支持的 OAuth / Bridge 流程如实说明，不索取用不上的授权码。

`official_steps_verified` / `verified` 表示文档支持步骤，不表示已在用户账号实测。`partial` 会给出具体缺口；`seed_only` 才是只有待核验链接。所有条目带 `checkedAt` 和 `sourceUrls`。

1. 已核实且可见 UI 一致时，直接沿内置步骤操作，无需每次从搜索引擎重查教程。不要把 Gmail/iCloud 的账号安全入口误当成邮箱设置，也不要在飞书网页端寻找桌面端的生成按钮。
2. `partial`、入口缺失、页面改版或账号条件不符时，先按 `missingEntryHelp` 排查，再打开具体官方来源；确需搜索时限定官方域名。不要把搜索摘要或服务器参数页当成已核实的授权码生成教程。
3. 用服务商的实际凭据名称；不统一假定是同一种开关、固定长度或有效期。无法核实的新条件如实标明，不补造菜单。
4. 已有授权码不可再次查看、仅能重置时，按 `credentialLifecycle` 和 `stopConditions` 处理；不能把“新增独立密码”与“重置旧码”当作同一动作。

只需说明时，直接交付“打开邮箱”入口、最短操作路径、具体官方教程和必要前提。已有授权码的用户可直接使用，不要求重新生成。不要把长篇协议解释塞进添加表单。

批量维护产品引导时，逐个当前 providerId 输出：`providerId, credentialLabel, mailEntryUrl, officialGuideUrl, steps, prerequisites, missingEntryHelp, verificationStatus, checkedAt, sourceUrls`。未知字段留空并说明原因。只有核验过的链接能标为官方图文教程；同品牌版本仅在官方说明确实共同适用时复用。产物不包含邮箱完整地址、授权码或会话信息。

## 用 computer use / browser use 完成操作

如果请求来自工作台“自动获取授权码”按钮，优先遵守其明确范围：获取并回填即可，由用户点击“验证并连接”。保留请求携带的 operationId 与现有表单，不调用 open_account_settings 创建新操作。回填前再次核对页面邮箱地址和服务商，用户取消或修改了目标就停止，不覆盖新输入。可使用 returnPage 定位原页面，不能打开一个新表单冒充原表单，也不把追加请求成功当作 agent 已启动。

读取 [浏览器协助与连接交接](references/browser-assistance.md)，使用当前可用的 computer use / browser use 工具执行。实际操作是主流程：

1. 定位目标工作台的添加或重连表单，保留其标签、账号和未保存内容；仅获取授权码而未指定接入产品时，最终留在服务商的授权码界面即可，不自行接入其他产品。
2. 沿用户已有登录会话打开条目指定的官方邮箱、账号安全页或桌面客户端，核对目标账号后进入设置。按钮请求中的 mailboxUrl 是邮箱入口，不保证就是生成入口；优先遵循知识库中的 credentialSurface 和实际 UI。观察控件，不从旧教程猜坐标。
3. 查看客户端服务状态和账号条件。已有可用授权码则直接使用；需要新码时先确认提供独立新增，只有重置入口则说明影响并交接，不自动作废其他客户端的凭据。未开启服务时仅处理本次需要的设置，保留其他设置。
4. 遵守当前工具对权限变化或凭据生成的确认/交接要求，按页面填写目标应用备注并继续生成；遇到身份验证时说明当前所需动作并交接用户，完成后从原页继续。
5. 用户已授权获取并接入时，通过官方页面复制新授权码，并用当前工具支持的输入方式填入此前确认的目标表单。具体传递方式见参考文档；只在目标表单验证输入，不把授权码展示在最终回复里。
6. 执行用户已授权的连接操作，读取同一笔操作的后端状态。只有目标产品返回成功才报告已连接；若用户仅要求获取，报告授权码已在服务商页面生成即可。

登录、短信、扫码、验证码或设备确认留给用户完成，再从同一页面继续。不要要求用户把授权码、密码或验证码发到聊天里。

实际能力不足（没有浏览器工具、无法操作目标表单、组织禁止服务等）才降级为用户接手，并说明卡在哪一步。生成页面与输入操作可能被工具记录；不能承诺普通 computer use / browser use 具备不经模型或不留工具记录的秘密传递能力。若用户要求这种隔离，先核对工具是否支持，不支持则将生成和填入交给用户。

## 完成与失败

- 沿用目标产品公开的账号设置操作及 operationId，读取状态确认结果。打开教程、打开表单或拿到授权码都不等于已连接。
- 最多做一次有依据的普通连接重试；凭据生成结果不明时先查看同一账号的授权码管理页，不重复生成。会话结束不声称会自动继续等待。
- 区分服务商认证失败、管理员限制、网络超时、客户端页面会话失效。后两者不是重新生成授权码的依据。
- 连接校验优先使用目标产品现有连接测试；SMTP 认证成功不等于实际发信成功。接入请求不包含发送测试邮件或修改邮件状态。
- 最终说明实际到达的位置：已核实教程、已打开设置、等待用户验证、等待安全填入，或后端确认已连接。附具体官方来源，不显示凭据。
