# H3 序列帧图生成

把 H3 的视频生成能力转成序列帧资产（sprite sheet）。**两个分支，先确认用途**：

- **游戏精灵图**（主分支）：品红平底定妆 → 每动作一段短视频 → 姿势极值帧 →
  键控抠像 → 打包 atlas，面向游戏引擎；
- **原风格序列帧**：主体保持原样不做风格改造，直接让原图动起来 → 按运动
  变化抽帧 → 拼帧图，面向动态表情包、动态壁纸、商品展示、网页动画和动作参考。

常见结果按以下预设进入规格卡，预设只提供推荐值，用户要求优先：

- 游戏精灵图：通常透明背景，按 `idle`/`walk`/`attack` 等动作拆分，角色 pivot
  默认 bottom-center；
- 动态表情包：通常透明背景或保留原背景，一个表情/手势一个动作；循环表情必须
  回到起始表情，一次性表情明确回到静止态还是保持末帧；
- 动态壁纸：通常保留原背景，以环境微动为主并做正向无缝循环；不得把镜头往返或
  倒播伪装成循环；
- 商品展示与网页动画：对象 pivot 默认 center，旋转展示覆盖完整 360° 且方向
  单一，交互或拆解动画必须声明结束时保持、返回还是消失。

用户意图不明确时（如传了张照片说"做成序列帧/让它动起来"），先用 `ask_user`
确认走哪个分支，**不要默认用户想要游戏风格改造**。

任何要交给游戏、网页或动画工具继续使用的任务，开始前必须读取
[标准生产与交付合同](references/production-standard.md)。该合同定义任意输入路由、
动作边界、cell/pivot/纹理上限、双层质检和最终目录；本文件没有重复展开的地方以
该合同为准。

## 硬性事实

- 模型名有且只有一个合法值：`MiniMax-H3`，任何提交、转述、日志中都只用
  这个名字（本流程依赖的 FL2VA 首尾帧对齐与官方多模态提示词格式为其独有，
  不可降级到其他模型）。
- **H3 是生成模型硬门禁，不只是 Prompt 格式。** 凡是需要新生成视频的步骤，
  最终提交参数和任务回执都必须明确指向 `MiniMax-H3`。禁止使用 H2.5，禁止让
  video-creater、连接器或底层接口采用默认模型，也禁止在 H3 不可用时自动降级。
  若当前工具不能显式选择并确认 `MiniMax-H3`，停止提交并告知用户“当前环境
  无法确认 H3 视频生成”，不得先用其他模型试做。
- 已有 MP4/MOV/WebM/GIF 的抽帧、抠像和打包不属于“生成视频”，因此无需重新
  调用 H3；只有从图片或文字创造新运动时才进入上述 H3 硬门禁。
- 键色自适应：默认品红 `#FF00FF`；主体含品红/粉色系时改用绿 `#00FF00`，
  仍冲突则蓝 `#0000FF`——看图选与主体配色距离最远的一个，并告知用户。
  定妆、视频、背景替换全程用同一键色。抠像脚本从边框自动估计键色，
  换色无需任何参数。主体撞键色不是硬伤，换键色即可，不要让用户改角色配色。
  自适应只容忍**小幅**漂移；生成中背景漂成另一种颜色（如品红→黄，可能
  恰好撞上角色发色）＝背景崩坏，脚本会自动检测（report.json 的
  `key_drift`）并只从干净段采样，见 Step 5/6 的处理规则。
- 首帧/尾帧/首尾帧参考模式不传 `ratio`，画面比例跟随参考图。
- 后处理依赖运行环境的 `python3 + Pillow + numpy + ffmpeg`（缺库时
  `pip install pillow numpy`）。
- 图片/视频生成均消耗积分：任何生成动作前需用户明确确认。
- 多张 img2img 提交策略（内部静默执行，**不向用户提及**）：先按 batch
  提交，失败则自动回退为逐张独立提交（可并行）重试；任何情况下不得
  降级为纯文生图——丢掉参考图等于丢掉角色一致性。

## 调用纪律（历史事故教训，必须遵守）

- **参考图 URL 只能用上传工具实际返回的地址**（如 `upload_temp_url` 的
  返回值），严禁手工构造、拼接或凭记忆猜测 URL——曾有一次全部失败的事故
  根因就是编造了一个不存在的 HTTPS 地址。
- **重试前先判因**。服务端「temporary failure, please retry」提示只适用
  于零星失败：**整批同时失败、或更换请求后仍是同一错误 = 请求本身有问题**
  （URL 不可达、参数非法），此时停止重试，转为自查参数并用单张最小请求
  复现定位。
- **同一请求连续失败 2 次即停**，把真实错误信息报告给用户再决定下一步，
  不做长时间静默重试循环。

## 交互约定

- **先完整体检，再一次性提问**。不要把用途、背景、风格、方向、cell、pivot、
  动作类型和消耗拆成一连串问答。除定妆候选挑选外，所有未决项必须汇总到一张
  规格卡里，用 `ask_user` 收集选择（不可用时在对话中直接提问并等待回答）。
  规格卡必须明确显示背景保留/透明、素材类型、每个动作 loop/oneshot 与边界、
  facing/镜像、cell、pivot、纹理上限、特效/阴影归属和付费任务量；不得静默替
  用户选择或漏项。
- **让用户挑图前，必须先把候选图展示出来**（作为图片资产交付到对话里，
  确认用户可见）再发 `ask_user`——不展示就让人盲选是流程缺陷。
- **消耗确认全流程只有 Step 3 一道门**，一次确认覆盖整份动作清单（含
  验证轮和验证通过后的批量段）。此后不再出现任何「确认/点火/要开始了吗」
  类追问——验证轮产物给用户看是质量检查点，用户不叫停就继续；只有用户
  中途新增动作、改方向数等**扩大消耗范围**时才需要补一次确认。挑卡、
  分流等质量决策不得附带「确认开始」性质的问题。
- 消耗话术：说明「将使用图片/视频生成能力，会消耗积分」+ 任务量
  （几张图、几段视频）+ 时间预估，**不预估具体金额或积分数**。
  **计费通道不是用户决策点，禁止就此向用户提问**——当前生图/视频均走
  平台积分；仅当环境信息明确显示该能力走用户自有 API Key（BYOK）时，
  话术自行改为「将调用你配置的 API」，同样不问。
- 体检发现参考图不合格时，先明确告知「这张图不适合直接生成合适的精灵图」
  及具体原因，不得静默补救；若对残缺内容做了推测（如从半身图推测全身
  造型），必须明确标注哪些是推测，交用户决定下一步，不得基于推测直接生成。
- 生成中途积分不足（如 402）：立即停止提交并明确告知用户；保留已产出的
  中间产物（定妆图、已完成动作段）与剩余任务清单，用户充值后说「继续」
  即从未完成的动作断点续跑，已完成部分不重做、不重复扣费。

## 工作流

```
0 体检   识别静态图/视频/GIF/现有帧图并路由；能直接后处理时不调用 H3
0.5 规格 一张规格卡确认背景、主体、动作边界、方向、cell、pivot、特效与消耗
1 风格   确认游戏类型 → 头身比例 × 渲染画风 → 视角与方向数
2 定妆   抽卡 3-4 张品红底定妆图 → 自查 → 用户挑选
3 确认   动作 × 方向 × 时长 × 分辨率 → 说明消耗积分 → 用户确认后才生成
4 生成   每动作一段 6s 视频；仅用 MiniMax-H3，优先委托可显式锁定 H3 的 video-creater 插件
4.5 校验 每段视频回来先 --check-only 体检，REGENERATE 则叫停该段
5 后处理 scripts/make_atlas.py：抽帧 → 抠像 → 姿势极值选帧 → 打包
5.5 成品质检 对最终播放序列做跳帧/停顿/接缝门禁，再由 M3 看动作语义
6 交付   仅交付质检通过的独立 PNG 帧 + atlas/JSON + manifest + preview
```

用户从文字描述开始则跳过素材质量体检，但不能跳过 Step 0.5 规格卡。

## Step 0 — 输入图体检（用户自带图时）

用多模态能力直接查看图片（看不了图就调 `images_understand`），先分类：

| 输入类型 | 判定要点 | 路由 |
|---|---|---|
| **已有动作视频/GIF** | 动作已经是用户想要的，只需变成帧资产 | **跳过 H3**，直接 Step 4.5/5；不要为“精灵图”三个字重新生成视频 |
| **已有 sprite sheet/编号 PNG** | 已经有逐帧内容 | **跳过 H3**，拆分/排序/重打包并做 Step 5.5；不得重绘 |
| 游戏风角色图 | 卡通/Q版/像素/立绘，单角色 | 过硬性清单 → 重绘品红底，直进 Step 3 |
| **自带纯色键控底的图** | 绿幕/品红/蓝幕等标准纯色底，单角色全身 | **直接当定妆图用**：键色=该底色（抠像自动跟随），跳过定妆重绘，过硬性清单后直进 Step 3 |
| 写实风角色/物体 | 盔甲、雕塑、玩偶、写实插画、3D 渲染 | 三选一分流（见下） |
| 真人照片（含名人） | 含可辨认的真实人脸 | 风格化转换照常做（见真人规则） |
| 有硬伤的角色图 | 半身/剧烈姿势/背景复杂 | 生图修复对应项后重新体检 |
| 多角色/群像 | 无法确定动画主体 | 请用户指定其中一个 |
| 知名 IP 角色 | 马里奥等版权形象 | 提示版权风险，建议原创化改造，不拦截 |
| 场景/风景图 | 云、雾、光、水、植物等可分层运动 | 走原风格序列帧，`asset-kind scene`、`pivot center`、`facing none` |
| 纯文字描述 | 没有可锁定的身份或构图参考 | 先生成并让用户确认一张主参考图，再按对应角色/对象/场景路由 |

若输入是对象、商品、VFX、UI 或场景动效，不套用“必须全身/脚底 pivot”的角色规则：
对象/VFX/场景通常选 `asset-kind object|vfx|scene` 和 `pivot center`；角色通常选
`asset-kind character` 和 `pivot bottom-center`。每个 atlas 只容纳一个主体、一个
统一尺度和一个 view/facing；多角色、多视角拆开打包。

道具物件（宝箱、金币、旗帜）也可做精灵图，动作集不同（open/close/spin），
按需求单独写动作提示词，不走人形动作模板。动物同理是合法角色主体
（写实动物照片走转风格分流），动作集按物种定（四足 walk/run/pounce 等）。

**角色定妆硬性清单**（仅角色动作生成需要）：单主体 · 全身完整入镜 ·
接近中立站姿 · 背景可分离。对象、VFX、UI 和场景改用各自规格卡，不套角色
站姿要求。主体配色与默认键色冲突时按「键色自适应」换键色即可，不算不合格项。

### Step 0.5 — 背景模式（所有分支必问）

进入定妆或视频生成前，必须把以下二选一放进 Step 0.5 的汇总规格卡，不能因为
原图带背景就自动保留，也不能因为用户说“精灵图”就自动抠掉。无需为背景再单独
增加一轮问答，但规格卡中绝不能缺少该字段：

- **透明背景**：最终交付 RGBA。原图背景不是纯色键控底时，先仅替换背景为与
  主体不冲突的纯键色，再用同一键色生成 H3 视频；后处理必须传
  `--background-mode transparent`。复杂原背景直接做边框取色只能去掉主色，
  蝴蝶、文字、水印等会残留，因此禁止跳过纯键色准备。
- **保留原背景**：把原图背景作为画面内容保留，H3 提示词锁定背景和机位；
  后处理传 `--background-mode keep`，输出不是透明精灵图。

用户未选择时停止在此，不进入生成，也不运行正式打包。选择写入项目状态，后续
每个动作沿用；用户主动更改才重新询问并重打包。

**风格不适配时四选一**（附体检结论，说清哪项不合格、为什么，用 `ask_user`）：
① 转 Q 版/游戏风做精灵图（游戏场景推荐）——生图工具以原图 img2img 重绘
品红底定妆，保留辨识特征（发色、服装、标志性道具）；② 保持原风格做游戏
精灵图，只修问题项——并提示小尺寸可读性与逐帧一致性风险；③ **原风格
序列帧**——主体完全不改造，直接做序列帧（见「原风格序列帧分支」）；
④ 换图或改文字描述。

**真人照片规则（放行+提示，少拦截）**：写实人脸不能直接用（恐怖谷+小尺寸
不可读），但「把真人做成游戏角色」是正当诉求——默认走风格化转换，目标是
辨识特征相似（发型、眼镜、服装配色、体型），不做写实人脸复刻。识别出名人
时不拒绝，只附一句「商用发布需自行取得肖像授权」。真正不做的只有两类：
要求写实级还原真人面孔，或明显恶意用途（丑化、色情、冒充）。

## Step 1 — 风格与规格确认

风格 = **头身比例 × 渲染画风** 两个独立维度。先问目标游戏类型，按推荐给
组合，用户可自由搭配。Q 版不是硬性要求——战棋、RPG、横版清版大多不是 Q 版；
**比例不是风险项，细节密度才是**（避免照片级材质与密集花纹，保证剪影清晰）。

| 头身比例 | 关键词 | 典型 |
|---|---|---|
| Q 版（2-3 头身） | chibi, big head small body | 休闲/放置/FFT 系战棋 |
| 半写实（4-5 头身） | stylized proportions | 火焰纹章系/日式 RPG |
| 写实（6-8 头身） | realistic proportions | 格斗/横版动作/暗黑题材 |

| 渲染画风 | 关键词 | 备注 |
|---|---|---|
| 像素（8/16-bit 或 HD） | pixel art, limited palette / hi-bit | 输出为"伪像素"，可后处理降采样+调色板量化补真 |
| 日系赛璐璐 | anime cel shading, clean lineart | 稳 |
| 美式卡通 | western cartoon, bold shapes, thick outline | 稳 |
| 手绘厚涂 | hand-painted, painterly | 横版动作质感之选 |
| 暗黑勾线 | dark gothic ink, heavy linework | 暗黑/肉鸽 |
| 扁平矢量 | flat vector, minimal shading | 益智/超休闲 |
| 手绘水彩 | soft watercolor edges | 软边缘抠像质量略降 |

推荐组合：休闲放置→Q版+扁平/赛璐璐；战棋 SRPG→Q版+像素 或 半写实+赛璐璐；
日式 RPG→半写实+像素/赛璐璐；横版动作→写实+厚涂 或 写实+像素；
平台跳跃/肉鸽→任意比例+像素；暗黑题材→写实+暗黑勾线。

用户已有游戏美术时，请其提供一张游戏截图或已有角色图做风格对齐参考，
比菜单更准。

**视角与方向数**（影响成本，此处确认、Step 3 计价）：横版只需侧视 1 方向，
左右靠镜像；俯视/等距（战棋、RPG）通常需 4 或 8 方向，每方向都是独立的
视频生成。只有角色左右完全对称时才可镜像省一半；武器手、发型、徽记、文字、
伤疤或服装不对称时，镜像会改变设定，必须在规格卡中让用户接受镜像或独立生成。
每份 atlas 写入明确 `facing`；不得靠预览倒放或水平翻转掩盖方向错误。

**输出画布与锚点是必选规格，不允许脚本从视频分辨率猜**：角色常用
128/256/512 正方形 cell + `bottom-center` pivot；商品/物件/VFX 常用
`center` pivot；非正方形角色可选 `256x320`。目标引擎未知时纹理上限用 4096，
padding 4px、透明 RGB extrude 2px。一个 atlas 中所有动作必须复用同一 cell、
scale、pivot、view 和 facing；超限则降低 cell/帧数或拆 atlas，不得输出一个
引擎可能无法导入的超大 PNG。

**特效与阴影归属也要确认**：透明角色默认不带地面阴影；武器拖尾、投射物、
命中特效默认独立成 VFX sequence，避免它们撑大 cell 或让循环接缝崩坏。用户明确
要求烘进角色帧时才合并，并把最大动作外扩计入 cell 安全边距。

**帧密度（必选项，Step 3 确认里让用户显式选，不是隐藏默认）**。
精灵图和序列帧对帧数的期待是两种产品，别替用户猜：

| 选项 | 帧数 | 采样 | 适合 |
|---|---|---|---|
| **A 游戏关键帧**（仅用户明确选择） | 按动作类型给（见下表） | arclength | 像素/刻意低帧游戏美术；使用 `--quality-profile game-keyframes` |
| **B 平滑动画**（序列帧分支默认） | 12-16 | uniform | 网页动效/表情包/展示，接近视频观感 |
| **C 视频级流畅** | 20-24 | uniform | 极致顺滑，提示图集体积和显存翻倍，游戏场景不推荐；使用 `--quality-profile video` |
| 自定义 | 用户报数 | 按分支 | —— |

选 A 时按行业惯例逐动作给帧数（打包用 `动作=路径:帧数` 语法逐动作设置）：
idle 4 · walk 6 · run 6-8 · attack 4-6 · jump 4 · hurt 3 · death 5。
主循环只保留一个完整的正向时间周期。眨眼、耳朵抽动等偶发微事件不要硬插进
idle/walk/run 主循环；需要保留时做成独立 `blink` / `twitch` 一次性动作。

帧密度是纯后处理参数：改选项重打包**不消耗积分**，选错随时换。
规律：风格越写实/笔触越连续帧数越高；像素风低帧才有味道。
用户没有明确选择帧密度时，不得因其说了“精灵图”就静默套用 4 帧 idle；
非像素、细节连续的插画/赛璐璐默认走 B（12-16 帧）和
`--quality-profile smooth`。A 是刻意的低帧美术选择，不是通用省帧默认值。

## Step 2 — 角色定妆（抽卡 + 评估）

用客户端可用的生图工具（从 Step 0 带图转风格时必须用支持参考图的 img2img）
生成 3-4 张候选。提示词模板：

```
{角色描述}, full body, standing neutral pose, side view, game character,
{Step 1 确定的比例+画风关键词}, centered, feet on ground,
flat solid {键色名+色值,如 magenta #FF00FF} background, no shadow on
background, no gradient, single uniform background color
```

键色按「键色自适应」规则先选定，模板中所有 {键色} 保持一致。键色必须避开
主体已有配色；不得用提示词要求模型改变角色或商品本身的颜色来适配键色。

**实验性技巧（社区验证，成本较高时再用）**：H3 本身可当「伪生图器」
（生成短序列后抽单帧，一致性远强于图片模型）。杀手场景是**多方向定妆**：
需要 4/8 方向时，不用图片模型逐方向抽卡，改用 H3 生成一段「角色在品红底
上原地缓慢转身 360°、无其他动作、固定机位」的视频，按方向角抽帧——
一段视频的成本换 8 个方向的同一角色，一致性由模型保证。抽出的方向帧
再各自作为该方向动作视频的 first_frame。

视角按目标游戏定（横版=侧视或 3/4）。定妆图画幅按目标 cell 比例做
（如 3:4 竖版角色）——后续视频比例跟随它。

带参考图抽卡先按 batch 正常提交；遇 500 失败则回退为**逐张独立提交**重试
（可并行发多个单张请求，见硬性事实），不得降级成文生图丢参考图。

生成后逐张自查：背景是否纯色、角色是否完整入镜、有无键色串色。**把通过
的候选图先交付到对话里让用户看到**，再用 `ask_user` 挑选（选项与图的
顺序一一对应）；不满意就带反馈重抽（图片消耗远小于视频，这一步多迭代）。

## Step 3 — 消耗确认（生成前必须过这道门）

用 `ask_user` **一次性**向用户确认（不要拆成多轮追问）：

- **动作清单**。横版动作游戏推荐动作集（社区验证的完整可玩配置）：
  循环类 idle / walk / run，一次性类 jump / punch / kick / block /
  hurt / death——按游戏类型取子集，标注好每个动作是循环还是一次性
  （打包时对应 `--oneshot`）。首次提交默认只含 1 个动作做验证（用户点了
  多个动作时取第一个/最典型的一个），验证通过后其余动作再批量提交——
  把这一点作为默认项写在同一份确认里，不单独再问一轮
- **逐动作播放类型**：每个动作必须且只能标记为 `loop` 或 `oneshot`。通常
  idle/walk/run 是正向 loop，attack/jump/hurt/death 是 oneshot；用户声明的
  特殊动作以用户选择为准。不得把未分类动作静默当作 oneshot，避免第三个动作
  播完莫名回到第一个
- **逐动作边界合同**：loop 写清一个完整周期从哪一相位回到哪一相位；oneshot
  写清开始态、主要动作和结束态。walk/run 必须覆盖完整左右步态且 facing 不变；
  attack/cast/jump/hurt 通常从可接 idle 的姿势开始并回到可接 idle 的姿势；
  death 播完保持最终帧，不回 idle。对象/VFX/UI 要写明结束时保持、消失还是回首帧
- **背景模式**：复述 Step 0.5 已选择的“透明”或“保留”，让用户在消耗确认前
  能发现选错，但不要重复提问
- **帧密度**（A 游戏关键帧 / B 平滑动画 / C 视频级 / 自定义，见 Step 1 表；
  默认值随分支给出，但必须作为选项出现在这份确认里）
- **方向数**（Step 1 已确认，此处算进任务量）
- **输出合同**：asset kind、facing、cell size、pivot、4096/目标引擎纹理上限、
  padding/extrude、特效与阴影是否独立；这些是可用性规格，不是后处理内部参数
- **时长**（默认 6s，必须确认）与**分辨率**（默认 768P）
- 说明将使用视频生成能力、会消耗积分，共几段视频、预计耗时
  （单段可能需要数分钟到 10 分钟）——不给出具体金额或积分数

拿到明确确认后才进 Step 4。

## Step 4 — 视频生成

**路径 A（首选）：委托 video-creater 插件。** 环境中有「视频生成」
（video-creater / `write-h3-prompts`）时，加载它并把每个动作作为 brief
交给它——官方格式 prompt、提交、后台轮询、错误恢复与交付都由它负责。
委托 brief 第一项必须写 `model: MiniMax-H3`，提交前检查插件最终选择的模型；
如果它只暴露默认模型、选择了 H2.5 或不能返回模型身份，则该路径不可用，转到
路径 B 查找可显式指定 H3 的接口。不得因为 video-creater 可调用就假定它在用 H3。
在编写或审核任何 H3 prompt 前，必须读取
[H3 序列帧 Prompt 模板](references/h3-prompt-templates.md)；该文件定义官方字段、
模式选择、结果预设和动作边界模板。本节只保留路由规则。
本 skill 提供的 brief 必须包含：

- 参考图：定妆图（品红纯底）
- 模式：循环动作（idle/walk/run）用 **FL2VA**，同一张定妆图同时做
  Picture 1（0.00s）与 Picture 2（结尾时刻），循环闭合从模型层面解决；
  非循环动作（attack/jump/death）用 I2VA（定妆图做首帧）
- 约束：按 Prompt 模板锁定参考主体、画风、构图、机位、比例、背景、动作边界
  与结束语义；不扩写或重设计参考图外观
- 每动作一段，时长按 Step 3 确认值

循环类不要求模型在整段视频中只做一次动作。特别是 walk/run，应以稳定节奏重复
若干个完整左右步态周期，并在结尾回到与开头相同的接触相位；“整段 6 秒只完成
一次步态”会把动作拉慢并增加月球步风险。眨眼、耳朵抽动、挥手等偶发事件不得
混入基础 idle/walk 循环，需要时单独生成 `blink`/`twitch`/`wave` oneshot。

**路径 B（兜底）：直调会话内可用的视频生成能力。** 无 video-creater 时，
用会话里实际注册的提交工具（原生 `gen_videos`/`submit_video_generation`，
或 `mcode-tools connector call connector__matrix__submit_video_generation`）：
定妆图作 first_frame 参考，**参数形状以当前工具 schema 为准，不要凭记忆
硬编码字段名**（该接口在演进：connector 路径要求本地图先用
`mcode-tools upload-temp-url` 换 HTTPS URL 再传 `input_image.url`）。
提交前必须在当前 schema 中找到模型选择字段并显式设置为 `MiniMax-H3`；不存在
该字段、只提供 H2.5、或无法从预提交信息确认模型时，停止而不是提交。创建任务后
再次检查回执中的模型身份；若不是 `MiniMax-H3`，该任务产物作废并报告真实回执，
不得继续抽帧或静默重试。
单帧模式循环靠提示词兜底，提示词仍按
[H3 序列帧 Prompt 模板](references/h3-prompt-templates.md)中的共享约束与动作边界写。
单帧模式循环靠文字约束只能作为降级方案；最终仍必须通过正向周期和接缝质检，
不得用 ping-pong 掩盖不闭合。

生成后逐段目检：H3 可能中途丢失纯色底（后处理可兜底轻微漂移，崩坏严重
的段落单独重生成）；角色是否走样。

## 原风格序列帧分支（跳过 Step 1-2 的风格化环节）

用户选了「主体原样、只要序列帧」时，流程大幅简化：

1. **不抽卡不转风格**：用户原图直接做 I2VA 首帧（图本身需过硬性清单的
   「单主体、完整入镜」两项；姿势不限——序列帧不要求中立站姿）。
2. **沿用 Step 0.5 规格卡中的背景选择**（若尚未确认，补回同一张规格卡，不另起
   一轮背景追问）：
   - **保留原背景**：原图原样生成，后处理加 `--background-mode keep`（不抠像，整帧打包）。
     适合商品展示、动作参考、带场景的动效；
   - **透明底**：先用生图工具做**仅替换背景**为品红纯底（主体不动），再走
     常规键控。提示用户：背景替换对写实主体可能有轻微失真。替换 prompt：
     `Keep the subject exactly as in the reference image — same pose, same
     proportions, same colors, every detail identical. Replace ONLY the
     background with a flat solid {键色,默认 magenta #FF00FF}, no shadow,
     no gradient.
     Do not restyle or redraw the subject.`
3. **动作描述**照常收集（每段一个动作/运动，循环动作优先 FL2VA 首尾同帧），
   消耗确认（Step 3）照过。
4. **后处理用平滑采样**：`--sampling uniform --frames-per-move 12`（可到
   16/24，帧越多越顺滑、图越大），不用姿势极值帧。
5. **交付**照常出 atlas + json + preview，另附网页动效用法示例：
   CSS `animation: seq 1s steps(N) infinite` 配 `background-position` 步进，
   或 JS 定时切 `drawImage` 源矩形。

## Step 4.5 — 视频校验（切图前必做，零消耗、秒级）

每段视频下载回来后、进入后处理前，先跑体检：

```bash
python3 scripts/make_atlas.py --check-only --out check \
  idle=videos/idle.mp4 --ref 定妆图.png \
  --background-mode transparent --cell-size 256 \
  --asset-kind character --pivot bottom-center --facing right
```

检查项：背景键色漂移（中途变色）、背景纯度、主体存在性、主体触边
（出画/被裁风险）、首帧与定妆图一致性（带 `--ref` 时）。逐段给出判定：

- **PASS** → 直接进 Step 5；
- **WARN** → 进 Step 5，但把告警内容告知用户（如"轻微漂移，成品只用
  干净段"）；
- **REGENERATE** → **不进后处理**，把具体失败原因告知用户并建议重新生成
  该段（重生成属扩大消耗，需用户点头）。验证轮的视频出 REGENERATE 时，
  同时暂停其余动作的批量提交。

机器可读结果在 `check.json`。这道门的意义：坏视频在「重生成还便宜」的
阶段就被拦下，而不是切完图才发现头发被吃了。

## Step 5 — 后处理

```bash
python3 scripts/make_atlas.py --out <输出目录> \
  idle=clips/idle.mp4 walk=clips/walk.mp4 punch=clips/punch.mp4 \
  --frames-per-move 12 --fps-suggest 12 --cell-size 256 \
  --asset-kind character --pivot bottom-center --facing right \
  --max-texture-size 4096 --pad 4 --extrude 2 --edge-erode 1 \
  --loop idle,walk --oneshot punch --quality-profile smooth \
  --background-mode transparent
```

脚本行为：ffmpeg 全量抽帧 → 逐帧从边框像素中位数估计键色（容忍底色漂移）
软阈值抠像+去溢色 → alpha 边缘腐蚀消除键色光晕（`--edge-erode` 默认 1，
黑描边角色可用 2，0 关闭）→ 非循环动作按累计运动量或时间均匀采样；循环动作
先找一个「端点姿势和前后运动方向都一致」的完整周期，再只在 `[start,end)`
内按时间正向抽帧；候选周期还必须覆盖足够的有效运动，不能把动作中的静止停顿
误当作完整周期 → 所有帧按统一 cell 打包。尾端点只用于确认闭合，不重复写入
图集，避免首尾同帧造成一拍停顿。

FL2VA 的慢 idle/眨眼可能整段 6 秒只有一个周期，内部没有第二个可匹配周期。
周期搜索必须同时考虑 H3 的原始首帧→尾帧边界；当内部短区间只是闭眼/停顿，
而整段首尾闭合且最终播放 QC 更好时，应选择完整源片段，不能为追求“最短周期”
截取 `[97..108]` 一类局部闭眼段。

序列帧分支的开关：`--sampling uniform`（均匀抽帧，平滑动效用；默认 `arclength`
按累计运动量等分选帧——快段密采慢段疏采，自动落在姿势极值上）。背景必须显式
传 `--background-mode transparent|keep`；未传时脚本直接失败，避免漏问后静默
保留背景或误抠背景。

**微事件 `--micro-events`（默认 0，仅一次性动作可选）**：该开关检测眨眼、
耳朵抽动等局部事件，并用事件帧替换邻近选帧，最终帧数保持不变。循环动作会
忽略此开关，因为把循环区间外的事件帧插入主循环会直接制造跳帧；需要保留时
把微事件导出为独立一次性动作，由状态机播放后返回 idle。

对齐方式 `--align`：默认 `fixed`——**整份 atlas 的所有动作共用一个 union
canvas 和统一缩放**，保留主体在画面中的真实位置，动作切换时不会因各自动裁而
突然变大、变小或重居中（机位锁定时这是正确做法；逐帧重对齐会在尾巴/手臂
甩出时把包围盒中心的偏移放大成鬼畜平移。社区 sprite 指南称此原则为
preserve-canvas）。仅当生成的视频里主体确实整体漂移、需要强行拉回时
才用 `feet`（逐帧底边中心对齐）。

`--loop idle,walk,run --oneshot attack,jump,hurt,death`：明确标记播放类型。
walk/run 是**正向重复循环**，不是一次性也不是往返；attack/jump/hurt/death
播一次后回到第一个循环动作。只要传了 `--loop`，它就是循环动作白名单，未列入
的动作不会被播放器擅自当作循环。
脚本会校验所有动作恰好出现在一个列表中：漏标、重复标、拼错动作名都直接失败。
oneshot 默认 `end_behavior=return-home`；`death`、破碎物件或需要停在最终状态的
动作还要加入 `--hold death`，导出为 `end_behavior=hold`。hold 只能是 oneshot，
脚本会拒绝把循环动作标成 hold。

`--pixelate <整帧目标高度px> --colors <色数>`：像素风补真——降采样到真实
像素分辨率并量化调色板。**全部帧共享同一调色板**（逐帧独立量化会造成
像素闪烁，社区工具踩过的坑）；常用 128~256 高、8~32 色。产出的 atlas
本身就是低分辨率，引擎里用 nearest 缩放。

产出：`atlas.png`、`atlas.json`（cell 尺寸+每动作帧区与 `playback`，循环
动作为 `forward`，一次性动作为 `once`）、`manifest.json`、
`frames/<action>/*.png` 独立可修帧文件、`preview.html`（自包含播放器：
动作切换/FPS/按各动作 playback 播放）。播放器保留“往返预览”开关，但每次
打开都由脚本强制设为关闭，浏览器缓存不能把它自动打开；它只影响 loop 动作，
不修改 atlas.json。一次性动作的导出语义仍是 `once`，但播放器默认勾选“重复
预览一次性动作”，方便持续观察第三个/最后一个动作；取消勾选才模拟播完回 idle。
每帧 JSON 还必须包含 `duration_ms`、`source_frame`、`pivot`、可见边界、独立 PNG
路径；meta 声明 sRGB、straight alpha、padding、RGB extrude 和纹理上限。脚本会
把同一动作需要的多行自动排入不超过 `--max-texture-size` 的单张 atlas；容量仍
超限时直接失败，不能静默交付超大纹理。

## Step 5.5 — 最终播放二次质检（交付前必做）

源视频 PASS 不代表切出的精灵图 PASS。`make_atlas.py` 会对**最终选中顺序**再
检查一次并写入 `report.json.playback_qc`：

- 相邻帧视觉变化是否均匀，是否出现「几乎不动一帧 → 突然跳一大步」；
- 是否存在重复/近冻结帧、异常跳帧、帧序重复；
- 循环动作实际末帧→首帧是否出现变化尖峰；
- 指定 12/16 帧时是否真的输出足额且唯一的帧；
- 最终缩放后的 cell 是否为空或侵入预留 padding，atlas 是否超过纹理上限；
- 各动作是否保持同一 canvas/scale/pivot，透明像素下是否已清除键色并完成
  RGB extrude。

质量档必须与 Step 1 的用户选择一致：A 传 `--quality-profile game-keyframes`；
B 传 `smooth`（少于 8 帧直接 FAIL，通常仍输出 12-16）；C 传 `video`（少于
16 帧直接 FAIL）。详细非像素插画默认 smooth，禁止只切 3-4 帧后以“游戏精灵
图本来就低帧”为由交付。

循环周期内部默认按累计视觉运动等距抽帧，而不是机械按时间等距；这仍保持时间
正向，但可避免 H3 速度不均时的停顿—跳跃节奏。`playback_qc=FAIL` 时脚本仍写出
GIF/HTML/report 供定位，但默认返回失败状态，**不得作为最终结果交付**；
`--allow-qc-fail` 仅用于查看失败样本，交付命令禁止使用。

确定性门禁通过后，用 M3 **同时看源视频与最终 GIF/逐帧序列**，做语义复核：角色
身份/比例是否稳定、动作是否完整、walk/run 左右脚是否按正向时序交替、支撑脚
是否异常滑动、attack 是否从准备到命中再收势、是否有倒播感或明显抖动。
M3 判定不合格时先对同一视频最多尝试 3 组帧数/FPS（零积分）；仍不合格说明
源动作语义有问题，停止交付并向用户说明需要重新生成该动作。重新调用 H3 会
消耗积分，必须重新取得用户确认。

## Step 6 — 交付与验收

交付时**必须把规格卡报给用户**（make_atlas.py 结尾已打印，preview.html
顶部也展示；atlas.json 的 meta.spec 有机器可读版）：图集尺寸与文件大小、
解码后显存占用、网格行列、单帧 cell 尺寸、每动作帧数与循环类型、建议 FPS、
背景透明与否——关心精灵图的人第一眼看的就是这些。

给用户：preview.html 路径（提醒直接打开预览——**可玩状态机模式**：数字键
1-9 或点按钮切动作；可暂停、前后逐帧、切换棋盘/深/浅背景并显示 pivot；
一次性动作 ▸ 在预览中默认重复便于检查，取消“重复预览”
后才模拟播完回待机，循环动作显示 ⟳。这就是原始社区工作流
"wire to a state machine" 的效果）、atlas 文件位置、引擎接入说明
（Unity：Sprite Editor 按 cell_w/cell_h 网格切割，一次性动作的 clip 关掉
loop；Phaser：`spritesheet` 加载 frameWidth/frameHeight，循环动作
`repeat: -1`）。需要手工精修个别帧时，直接编辑
`frames/<action>/<action>_NNN.png`，完成后重新打包；不要在 atlas 上盲猜帧区。

验收标准，逐动作和用户过预览：

- **report.json 的 `key_drift` 必查**：非 null 说明背景中途漂成了别的
  颜色，脚本已只从干净段采样（告知用户「该段背景第 N 帧起变色，成品只用
  了前段干净帧」）；`regen_recommended: true`（崩坏超 1/3）时明确建议
  重生成该段——重生成属于扩大消耗，需用户点头
- 抠像后边缘无明显键色镶边（特效/半透明部位允许轻微瑕疵）
- `report.json.playback_qc.verdict` 必须为 PASS；WARN 需人工/M3 明确确认，
  FAIL 一律不交付。重点检查 `near_freeze_steps`、`jump_steps`、
  `transition_cv` 和实际 `seam_ratio`
- `report.json.spatial_qc.verdict` 必须为 PASS；任何空帧、padding intrusion、
  cell/canvas 不一致或 atlas 超过纹理上限都属于硬失败
- 循环动作必须是**一个连续、时间正向的完整周期**，并检查 `report.json` 的
  `loop_qc`：`selected_outside_cycle` 必须为空，`chronological` 必须为 true，
  `seam_ratio` 建议不高于 1.75；`loop.motion_coverage` 不能接近 0，否则说明
  选中的是静止停顿而不是动作周期。超出则调整周期/帧数或重做该动作，不得靠
  乱序帧掩盖
- idle / walk / run 只允许 forward loop。walk/run 绝不使用 ping-pong，
  否则后半程会把脚步和身体运动倒放；播放器里的往返开关仅用于人工预览并默认
  关闭，不得改变导出的 `playback: forward`
- 一次性动作 attack/jump/hurt 只要求全程时间正向，按边界合同恢复到可接 idle
  的姿势后由状态机回 idle；death 则保持最终帧，不回 idle。它们都不要求末帧
  与首帧形成循环接缝
- 各动作间角色比例、配色一致（不一致则回 Step 4 检查定妆图与提示词）

不合格的动作单独重新生成对应段落，不重跑全量。

**流畅度不满意不用重新生成视频**：卡顿/太碎只是选帧参数问题，改
`--frames-per-move` / `--sampling` / `--fps-suggest` 对同一段视频重跑
Step 5 即可（零积分消耗），preview 里也可先拖 FPS 滑块找到目标手感
再定参数。
